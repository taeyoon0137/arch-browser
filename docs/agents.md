Terms: "the user's CLI" is Claude Code's `claude` or OpenAI's Codex CLI `codex`, which the user installs and signs in to in the built-in terminal (row 56). An "in-app session" is an agent session that Arch starts. An "outside client" is a program that reaches Arch through `arch-cli` or `arch-mcp` without Arch having started it.

## Purpose and principles

- Browser state, tools, and every check of what an agent may do live in the Arch app. `arch-cli` and `arch-mcp` are thin clients with no policy. No entry point, client kind, or debugging route skips the checks.
- A subscription connects only through the vendor's own CLI, run headless as a subprocess with its own sign-in. Arch builds every argument to disable the CLI's own tools, settings, hooks, plugins, and other MCP servers, leaving only Arch's tools, with two reviewed exceptions: Codex's code-mode host, through which Codex's current models call any tool, and the built-in Claude Code plugins on Arch's list, which no argument turns off. It checks the CLI's start event or stream for anything else.
- All AI work goes through the AI interface (`docs/ai.md`): an in-app session resolves the `agent` feature's route, records usage, and passes page data only as tool results. API-key sessions send them through the interface's part checks. CLI sessions and outside clients receive them from the tool host through `arch-mcp`, never through `AIService`, so the tool host applies the same site exclusions and address reduction itself (Site exclusions). Arch calls no vendor service itself.
- Arch runs no servers. `arch-cli` and `arch-mcp` reach the app through one local Unix domain socket that has no network port and exists only while Arch runs and an agent feature uses it (decision 1).
- Reading is free; the host, not the prompt, gates acting, typing, and going to sites the user did not name. A page cannot approve anything. Approvals happen only in Arch's own interface outside the page area, and an unanswered approval is a denial. No tool, command, or MCP call changes a setting, grant, exclusion, permission, plugin, or Persona.
- Fail closed: a quit, a crash of the client, Stop All Agents, an expired grant, an unknown tool, a failed check, or an unknown stream event ends the call or the session.
- Every tool runs on WebKit and Chromium tabs through the engine protocols. Engines below lists what still differs and why.
- Public APIs only: Unix domain sockets, audit tokens, Security's code signing functions, the process table through `sysctl` (`KERN_PROC_PID`, and `KERN_PROCARGS2` for the path a client was started with), `posix_spawn`, LocalAuthentication, CryptoKit, and the engine protocols. Arch does not use `libproc`, whose header calls its interfaces private. Nothing here needs a private API flag.
- Add types, tools, and engine members only when a feature needs them, as with the AI interface and the engine protocols.

## Using agents

- In the browser: the user adds Claude Code or Codex in Settings ▸ AI ▸ Providers, signs in to it in the built-in terminal, and starts a session with File ▸ New Agent Task, the palette's Ask Agent row, or Continue as Agent Task in the page reader. The session opens its tabs in the background in an agent folder of the space. The agent panel beside the page shows the conversation, each step Arch performed, and the approvals Arch requests. An API-key model with tools serves the same sessions.
- From Claude Code or Codex outside Arch: the user turns on Settings ▸ AI ▸ Agents ▸ Allow Outside Clients, runs `arch-cli setup claude` or `arch-cli setup codex`, and optionally `arch-cli skills install`. The tool then starts `arch-mcp`, and its first call shows a grant sheet in Arch.
- From a script: `arch-cli tabs`, `arch-cli open https://example.org`, `arch-cli snapshot t1`, `arch-cli click t1 e5`, with `--json` for machine-readable output, under the same grant.

## Decisions

Code comments and documents cite these as "agent decision 1" and so on.

1. The control channel is a Unix domain socket served by the app process. Under the plan's Goals, it counts as local inter-process communication, not a server: it has no TCP or UDP port, so no web page, DNS rebinding, or other machine can reach it; it exists only while Arch runs and an agent feature uses it; it accepts only Arch's own bundled tool running as the same user. A loopback port would be reachable from pages and is a server; an XPC Mach service needs a launchd job that can outlive the app. The user may overturn this reading. The fallback is Apple Events (Fallback transport), which keeps `arch-cli`, `arch-mcp`, and subscription sessions working.
2. The executables are `arch-cli` and `arch-mcp`, never `arch`, because macOS ships `/usr/bin/arch`. They share one Mach-O, target `ArchCLI` with product `arch-cli`, in `Arch.app/Contents/Helpers`; `arch-mcp` is a relative symbolic link that the binary distinguishes by `argv[0]`. One binary means one code directory hash for the peer check and one target in `Package.swift`.
3. Subscriptions connect only through the official CLIs (`claude`, `codex`), signed in by the user in the built-in terminal and run by Arch as subprocesses with their own sign-in. Arch never reads a CLI's credential files or Keychain items, never uses a vendor's OAuth client, callback, or endpoint, never imitates a CLI, and reads no usage endpoint. The status Arch shows comes from the CLIs' own status commands.
4. Agent sessions are the only place a command-line tool gets tools from Arch, and only Arch's MCP tools (`docs/ai.md`, Command-line tools). The Claude Code and Codex presets build their own arguments for every request. Their ordinary requests (page reader, questions, hooks, Plugin Writer) run with no tools and therefore accept page data.
5. Every check runs in the app's tool host, the same code for the in-app CLI, the in-app API-key loop, `arch-cli`, and `arch-mcp`. The CLIs' own approval features, MCP elicitation, AppleScript, and the agent itself never approve anything.
6. Tools are atomic browser actions. No tool runs code in a page, fetches outside a tab, reads files, cookies, passwords, or the clipboard, or changes any setting.
7. Page actions use DOM events in the `arch.agent` script world in the first build, and results say so (`inputKind: dom`). Both adapters offer trusted input (`EngineWebContents.input`, Engine members); the tool host uses it where the tab offers it and the call succeeds, and reports `inputKind: trusted` (VII.21). DOM events stay the fallback, because trusted input needs the tab in a window and refuses some input, and they serve most sites.
8. In-app sessions gate the addresses an agent writes by the data they carry, in every mode, including Read Only: an address the session has not seen asks, whatever its site, and so does any address to a site outside the site scope (Site scope and navigation). The page that injects instructions is often in scope itself, since it is the attached tab, so the site alone guards nothing. Typing is the other route off the Mac, and the mode gates it. Outside clients navigate freely in their own agent tabs because they can already send data anywhere themselves. Their grant and Persona limit what they read.
9. Outside clients are offered a separate Persona named Agents, with no sign-ins, and Read Only by default. The Agents Persona is agent-only, an exception to Persona rule 6: remembered permission answers from `permissions.json` are not copied into its profiles, and its permission requests are denied without a card and not remembered.
10. Agent tabs record no history visits, are not saved in `session.json` until the user keeps them, and never join the closed tab list, so `session.json` keeps its schema (version 16). Agent folders exist in memory only.
11. Claude Code sessions run as one long-lived process with `--no-session-persistence`, so the conversation lives only in the process and in Arch's memory; `CommandLineProcess` gains an open standard input mode for it. Codex sessions run one process per turn and resume the thread, which Codex keeps under its own folder; Arch deletes the thread with the session unless the user keeps Codex's copy.
12. Session facts (attached tabs, Persona, mode, scope) never go into a CLI's arguments. Arguments carry only Arch's static harness and configuration. The first message on standard input carries the user's words and a short preamble with tab handles. Details come from the `session_info` tool, whose calls wait for the start check.
13. Refs are stateless: the snapshot script keeps nothing in the page, and the host keeps a fingerprint per ref with the document's address. This behaves the same on Chromium, where every script world shares the page's main world, as on WebKit.
14. `AIModelCapability.agent` is derived from the provider kind and cannot be added or removed in `ai.json`, so the `agent` route holds only models that can run a session.
15. The approval card never edits site exclusions. Navigation to a site excluded from AI is refused, and so is every read of a page on one. The user changes exclusions only in Settings, so a page cannot steer the user into removing one.
16. In-app sessions get Arch's skills as the CLI's own skills where the CLI can read them from a folder that only the session reads, without the user's own skills, and as `guide` topics otherwise (open decision 3, decided by the user). Claude Code can: `--plugin-dir` loads a plugin folder for that process only, and with its skill tool (`--tools Skill`), the bundled and policy skills, `doctor`, and the extra usage commands off, and `plugin-authoring` off through `--settings`, `init` lists only the folder's skills (Facts). `--restricted` keeps the user's and the working folder's own skills and commands out, so a session never needs to restart without the folder; a version that loads them is refused by the start check. Built-in commands stay typable in such a session, and a message that starts with `/` runs one without the model, so `AIAgentSession.send(_:)` refuses such a message while Claude Code may hold the session. Codex cannot: it finds a skill folder in the session's working folder, but lists it only beside the user's own skills, and its model reads a skill by opening its file, which a session without shell and file tools cannot do; Codex sessions keep `skills.include_instructions=false` and the `guide` topics. The skills, the topics, and the entry skill that `arch-cli skills install` writes for outside agents come from the same text in `AgentHarness.swift`, so every agent follows the same guidance, and one source updates with the app. VII.15 wrote the folder's skills in `AgentHarness.sessionSkills`, one for each guide topic but `cli`, and `AgentSkillInstaller.write(_:into:)`, which writes them into a folder; `AIAgentSessionRequest.skills` passes the folder.

## Local control channel

### Transport

- One `SOCK_STREAM` Unix domain socket. Arch adds no TCP, UDP, HTTP, WebSocket, Bonjour, launchd agent, login item, or XPC service. `arch-mcp` is a standard-input process started by its client; it listens on nothing.
- Path: `~/Library/Application Support/Arch/Agent/control.sock`, with both sides taking the home folder from `getpwuid(getuid())`, never `$HOME`. When the path exceeds `sun_path`'s 104 bytes, both sides use `<per-user temporary folder>/xyz.taeyoon.arch/control.sock`, with the folder from `confstr(_CS_DARWIN_USER_TEMP_DIR)`. Only a client outside an app bundle, which fails its check of any listener and sends nothing (Client checks of Arch), connects to the path in `ARCH_AGENT_TEST_SOCKET` when that is set, so that tests of the built `arch-cli` reach no running Arch; Arch and the bundled clients ignore it.
- The `Agent` folder has mode 0700 and the socket 0600 (umask set around `bind`). Before binding, Arch `lstat`s the folder: it must be a folder, not a symbolic link, owned by the user, with mode 0700. Arch creates the folder with that mode and never changes the mode of one it finds. A socket file is removed only after a `connect` to it fails, so a second Arch leaves a live one alone and reports the channel as unavailable; anything other than a socket at the path also keeps Arch from listening. Settings ▸ AI ▸ Agents says why the socket does not listen, with Try Again. Stopping removes the socket file only while it is still the one Arch bound (same device and inode).
- Arch listens only while an in-app session on a CLI runs or Allow Outside Clients is on. Otherwise the socket file does not exist and clients report that agent access is off. API-key sessions need no socket.
- While Allow Outside Clients is off, the socket serves only in-app sessions: Arch answers a `hello` without a valid ticket with `refused` ("outside access is off") and shows no grant sheet, and the client exits with code 69.

### What "runs no servers" allows

Allowed: this socket, while the app runs; child processes that Arch starts with pipes and ends at quit, as command-line providers already do; `arch-mcp` as a standard-input child of whichever client starts it; Apple Events through `Arch.sdef` as today. Not allowed: any listening TCP or UDP socket, loopback included; an HTTP, WebSocket, or MCP streamable HTTP endpoint; an OAuth callback listener; a debugging port (the bridge sets no remote debugging port for Chromium, and check 74's `lsof` would list one); a launchd job or login item; a relay; a process that outlives Arch; any request from Arch to a vendor's service. The CLIs reach their vendors as they do in a terminal, under the user's sign-in.

### Framing and methods

- Frames: a 4-byte big-endian length, then a UTF-8 JSON-RPC 2.0 message, at most 16 MiB (a full-page screenshot fits); a larger frame closes the connection. Length framing keeps page text from splitting messages.
- Arch's first message, once its accept-time peer check passes, is a `ready` notification without params. The client reads it before it sends anything, so a ticket never reaches a process that took the socket's path (Client checks of Arch).
- The client's first message is `hello` with `protocol` (1), `client` (`arch-cli` or `arch-mcp`), the client's version, and an in-app session ticket if it has one. Arch answers with its protocol and version and the connection's status, flat in one object (`AgentHelloAnswer`): `bound` (an in-app session), `granted` with `grant` (`level` `readOnly`, `askBeforeActing`, or `actInAgentTabs`, the Persona's name and the space's, as `persona` and `space`, so that `arch-cli status` names the grant's place as "Agents / Home", and `expiry` `quit`, `revoke`, or an ISO 8601 date), `none` (no grant yet), or `refused` with `refusal` (a `reason` code and a sentence), after which Arch closes the connection. `hello` and its answer keep this shape in every protocol version. Another protocol version is refused with reason `protocol` and Arch's version in the answer's `protocol`, so the client names both versions and exits with code 75; whatever the status, an answer with another `protocol` ends the client so. Reason `outsideAccessOff` exits 69 and `ticket` or any other reason 6. A connection that Arch closes before it answers `hello`, as after its peer check refused the client, also exits 6, and one that closes later exits 69. The client waits 10 seconds for the answer, then exits 70.
- Methods: `tools/list`, `tools/call`, `tools/cancel`, `task/start`, `task/send`, `task/events` (a stream of notifications), `task/stop`, `sessions/list`, `grant/show`, `grant/release` (a client may give up its own grant and can never widen one), and `guide/get`. Notifications from Arch: `progress` (a call ID and a sentence such as "Waiting for your approval in Arch"), `tools/changed` (the client's tool list changed, as after a grant), `revoked` (then Arch closes the connection), and `task/event`.
- Every `tools/call` carries a client-chosen call ID, the request's JSON-RPC ID; Arch answers each once. Its params are the tool's `name` and `arguments` (`AgentToolCall`), and its result is an `AgentToolResult` (Tools ▸ Results). A connection runs at most four calls at a time; more get JSON-RPC error -32002 (`busy`). A client without a grant whose call the user does not allow gets error -32001 (`noGrant`) with a sentence, and `arch-cli` exits 6.
- Tool messages (`AgentToolMessages.swift`): a call's ID is its `tools/call` request's integer ID. `tools/list` takes no params and answers `{"tools": [<name>, …]}`, the catalog tools the connection may call: those that Arch's tool host runs and the grant's level and scopes allow, and before a grant every tool the host runs, since the grant sheet may allow any of them. The client describes them from its own catalog, which the peer checks make Arch's. `tools/call` takes `{"name": …, "arguments": {…}}` and answers `{"status": …, "code": …, "content": […], "structured": {…}, "approval": …}`: `code` (optional) names what went wrong or the rule that refused, `content` holds `{"type": "text", "text": …}` and `{"type": "image", "data": <base64>, "mimeType": …}` parts as MCP writes them, `structured` (optional) is an object with the result's facts, and `approval` names the approval that an `approvalPending` answer waits on. `tools/cancel` is a client's notification `{"call": <id>}`, `progress` is Arch's `{"call": <id>, "message": …}`, and `tools/changed` has no params.
- VII.11 serves `hello`, `tools/list`, `tools/call`, `grant/show`, and `grant/release`, and sends `progress`, `revoked`, and `tools/changed`, the last to a client's connections after a grant; VII.17 binds tickets in `hello`, sends `tools/changed` to a session's connections when its mode changes, and serves `task/start`, `task/stop`, and `sessions/list` (`AgentTaskMessages.swift`) for outside clients, with `task/event` notifications on the connection that started the session. `task/send` and `task/events` are not served, since no command uses them; the other methods come with their tasks, and Arch answers any method it does not serve with -32601 and acts on `tools/cancel` (Approval interface). A message other than `hello` before `hello` is answered is an invalid request, after which Arch closes the connection. Arch refuses a `hello` with reason `unidentified` (exit 6) when it cannot tell which program the client is, as when a process on its chain ends while Arch reads it.

### Peer checks

Arch accepts a connection only when all of these hold, checked on accept before it reads a byte:

1. Same user: `getsockopt(SOL_LOCAL, LOCAL_PEERCRED)` gives the peer's effective user ID, which must equal Arch's.
2. Audit token: `LOCAL_PEERTOKEN` gives the peer's audit token, from which Arch takes the process ID and its version (`audit_token_to_pid`, `audit_token_to_pidversion`), so a reused process ID cannot pass.
3. Code identity: `SecCodeCopyGuestWithAttributes` with `kSecGuestAttributeAudit`, then `SecCodeCheckValidity`, and the code directory hash (`kSecCodeInfoUnique`) must equal the one Arch reads at launch from its own bundle's `Contents/Helpers/arch-cli` through `SecStaticCodeCreateWithPath`. The same rule applies to Apple Development and ad hoc signatures. Each rebuild changes the hash on both sides together, and no signing identity or team is written anywhere (plan Working Rule 8). A copy of the binary elsewhere has the same hash and behavior, so the check does not require the bundle's path.

The audit token names the process that last used the peer's end, as it is now, not a fixed owner of the connection; a process can pass check 3 and then hand the connection to another process, or `exec` a child that writes, so the pair that passed need not be the one that sends the next frame. Arch therefore records the process ID and version it checked and reads the token again before it trusts each frame: the frame counts only while that same process, with the same version, holds the peer's end. A frame from another process, or from the same process after an `exec` (the version changes), fails and closes the connection. A connection that fails any check is closed at once and logged as refused with the reason and executable's name. This keeps other programs from speaking the protocol. It cannot keep the user's own processes from running `arch-cli`, so grants control their access.

### Client checks of Arch

`arch-cli` and `arch-mcp` apply the same checks to the listening process before sending `hello`: same user, valid code, and the code directory hash of `Contents/MacOS/Arch` in the app bundle containing the client. They find the bundle from the client's own path (`_NSGetExecutablePath`, then `realpath`, which follows a PATH link). A client that finds anything else, or runs outside an app bundle, exits with code 77 ("the socket is not Arch's") and sends nothing.

The audit token cuts the same way for the client. A program that bound the path could pass the client's code check and still hand off the connection: it binds and listens, then `exec`s Arch's binary or a valid copy so the token at connect names valid code, while a child it forked holds the accepted socket. So the client sends its ticket only after it reads a frame from the checked process. Arch sends `ready` first, once its own check passes; the client waits for `ready`, confirms the frame came from the process it checked (the same process ID and version), and only then sends `hello`. A frame that arrives while another process holds Arch's end, or after an `exec` changed the version, exits 77 and sends nothing. A program that binds the path first therefore collects no ticket or call: it cannot both pass the code check (which needs Arch's valid code) and run its own logic in one process, and a second process that writes `ready` is a different process than the one checked.

The client connects first. When nothing listens at the path (no file there, or a refused `connect`), it exits 69 before any check, so a client outside a bundle, such as `.build/debug/arch-cli`, still says that Arch is not running. The bundle is the `.app` folder above `Contents/Helpers`, and the client reads the expected hash from it only once something listens. Both ends make the check through `AgentPeerCheck` in `AgentControl`: `LOCAL_PEERCRED` for the user (on the connecting side, the listener's credentials), `LOCAL_PEERTOKEN` for the audit token, then the running code's validity and hash through Security; each reads the token again before it trusts a frame and requires the same process. Only the expected hash differs.

### In-app sessions: tickets

- When Arch starts a CLI for a session, it makes a base64url-encoded ticket of 32 random bytes (`SecRandomCopyBytes`). The ticket reaches `arch-mcp` as `ARCH_AGENT_TICKET` through the CLI's MCP configuration (Claude Code, Codex below). `arch-mcp --session` refuses to run without it.
- Arch binds a connection to the session only when the ticket matches in a constant-time comparison and the session's CLI process is an ancestor of the peer. Arch walks the parent chain with `sysctl` (`CTL_KERN`, `KERN_PROC`, `KERN_PROC_PID`), reading each process's parent ID (`kp_eproc.e_ppid`) and start time (`kp_proc.p_starttime`) from its `kinfo_proc`, and compares process IDs and start times with the process it spawned, whose start time it reads the same way right after `posix_spawn`. A CLI may start its MCP server more than once; each connection binds when it connects. Arch holds the session's calls at the `ready` gate from each CLI process's start until that process's first output (the session's `ready` for the first, `processReady` for each later one, as after a Stop that ended the group or a Codex turn), so a call of a new process runs only after its own start check passed.
- The ticket dies with the session. A ticket from a process outside that tree is refused and logged, and the session shows "Another program tried to use this session's access."
- The ticket is not a secret from the user's own processes, which can read the user's files and environments; the ancestry check binds it. Risks says so.
- Built by VII.17: only a `hello` from `arch-mcp` may present a ticket. `AgentSessionTicket` makes the ticket and compares a presented one byte by byte over the longer of the two, without stopping at the first difference, against every session's ticket; `AgentProcessAncestry` walks the peer's chain, at most 64 steps, through `AgentSystemProcessInspector`. The CLI's start time comes from `AIAgentSession.processDidStart`, which the runner calls right after each `posix_spawn`, and only the process running now counts. A ticket whose session lives but whose peer is outside the tree adds the notice to the session's transcript once and an activity entry `refusedPeer` with the session's ID; a deleted session's ticket names no session.

### Outside clients: identity, grants, revocation

Identity: Arch identifies the client by the peer's nearest ancestor that is not a shell, `env`, `login`, `sudo`, or one of Arch's tools, walking the chain through `sysctl` as for tickets (`AgentClientIdentifier`). Security's `SecCodeCopyGuestWithAttributes` with `kSecGuestAttributePid`, `SecCodeCopyPath`, and `SecCodeCopySigningInformation` give each ancestor's path and signature, and Arch reads the client's start time again afterward, so a process that ended in between is not taken for another. The walk passes over a shell, `env`, `login`, or `sudo` by its path, never its name, so that a program named like a shell is the client rather than passed over: the shells `/etc/shells` lists, which root owns, and `/bin/sh`, `/bin/bash`, `/bin/zsh`, `/bin/dash`, `/bin/csh`, `/bin/tcsh`, `/bin/ksh`, `/usr/bin/env`, `/usr/bin/login`, and `/usr/bin/sudo`. It passes over Arch's tools by the bundled `arch-cli`'s code directory hash. The path rule does not stop a program from taking a process's place on the chain: a program that `exec`s `arch-cli`, or a real shell that runs it, keeps its process, so the walk passes over it and reaches the program's parent (Risks).

- A signature with a team identifier identifies the client by signing identifier and team, once `SecCodeCheckValidity` passes the running code against the requirement `anchor apple generic and certificate leaf[subject.OU] = "<team>"`, which no ad hoc signature meets. Any other signature, ad hoc ones included, whose identifier the signer chooses (`codesign -s - -i <any>`), counts as unsigned: the client is its executable path and code directory hash. Apple's own programs, such as Terminal, carry no team identifier and count as unsigned too. The name of the `.app` bundle around the client, unless the client is that app, or else around its nearest ancestor in one, is for display ("claude in Terminal"). The client's own name is the last part of the path it was started with, which `sysctl` (`KERN_PROCARGS2`) gives as `execve` received it, so a link keeps its name: `claude` for `~/.local/bin/claude`, whose file Security reports as `~/.local/share/claude/versions/<version>`. The key and the path the sheet shows stay the file's, and an interpreter is recognized by either name. An unsigned client's identity changes with each update, so it asks again.
- The walk never stops at launchd (process 1) or at Arch itself, as for a job the system adopted or `arch-cli` in the built-in terminal, since every such process would share the grant. The client is then the process just below them on the chain, by path and code directory hash, bound to that process's ID and start time so that its grant ends with it, and the sheet names its executable ("zsh in Arch's terminal").
- An interpreter such as `node` or `python3` is one identity for every script it runs, and the sheet says so.
- A client that the walk reached through a shell, `env`, `login`, or `sudo`, or a shell it took as the client, is marked (`reachedThroughShell`), and the sheet and its row in Settings say that every program that runs in its shell can use the access too: Terminal's grant from `arch-cli` typed there covers any program started in Terminal, which can `exec` `arch-cli` or a shell running it. A client reached without a shell still shares its grant with a program it starts that `exec`s `arch-cli`.

The first `tools/call` asks for a grant; `hello` and `tools/list` do not, so a client can start and list tools at once. The grant sheet appears in Arch's frontmost main window, opened if none is, a notification without page content ("A program is asking to use Arch") posts while Arch is in the background, and the call waits, with a `progress` notification that `arch-cli` prints on standard error. The calls of one client wait on one sheet. An unanswered sheet closes as Don't Allow after the outside clients' approval window (5 minutes until that setting exists), and quitting closes it the same way. While Allow Outside Clients is off, no grant sheet appears (Transport).

|---|---|---|
| Client | The identity above, with its executable path | — |
| Persona | Agents (created on demand, empty, no sign-ins), or an existing Persona | Agents |
| Space | A space of that Persona, where the client's agent folder goes | Its first space |

A grant in one of the user's own Personas reads with their sign-ins, so it always asks.
- The sheet has no default button, so Return and Space do nothing: neither button takes the keyboard focus, and Escape is Don't Allow. Allow requires a pointer click, so an accessibility press does nothing, and the posted-click check of sensitive cards (Approval interface) applies to it.

Revocation or expiry sends `revoked`, fails the client's running calls with `revoked`, denies its pending approvals, and closes its connections at once. ### Sealed settings

`agent.json` is `{"seal": <base64>, "settings": {…}}`, the seal an HMAC-SHA256 (CryptoKit) over the settings' JSON with sorted keys, members that this build does not know included, so that a later build's fields do not fail an earlier build's check (`AgentSettingsFile`). The 32-byte key is in a generic password item (service `xyz.taeyoon.arch.agent`, accessible when unlocked, not synchronizable). It is read once per launch on a separate Keychain queue off the main thread, as `AIKeychain` does, and only when a file exists or Arch first writes one, so a user who never turns on agents meets no keychain prompt. The settings carry a `generation`, which the seal covers and each write raises, and the Keychain item keeps the last write's generation with the key: 32 key bytes, then 8 bytes of generation, most significant first, an item of the key alone being at generation 0. After writing the file, Arch updates the item on the Keychain queue, in the order of the writes. A file whose seal does not match, as after another program edited it, a file that does not read, a file whose key the Keychain no longer has, which can never be checked again, and a file whose generation is below the item's, as an earlier copy put back after a Revoke, are renamed to `agent.json.unreadable`. A Keychain that does not record a generation leaves the file before it opening until a later write's record lands, and Settings says so; the write at quit, which carries only last-use dates, may not be recorded before Arch exits. Arch starts with the defaults (outside access off, no grants, the Agents Persona an ordinary Persona) and says so in Settings ▸ AI ▸ Agents. This keeps an outside agent with a shell from granting itself access by editing a file. `ai.json` stays unsealed (Risks).

A key the Keychain does not give is not a mismatch: the user may have cancelled the login keychain prompt that follows each ad hoc rebuild (`docs/ai.md`, Keychain), or the keychain may be locked. Arch then leaves `agent.json` untouched and, for that launch, keeps outside access off and uses no grant. It keeps the recorded Agents Persona agent-only, trusting the unverified ID only to restrict a Persona, never to widen one; the Persona the file names is agent-only from launch until the seal is checked. The defaults stand in for the session settings meanwhile, while the file reads and after a key the Keychain did not give, so they must neither raise a session above the user's choice nor delete what the user kept: a new session starts at most in Read Only (`AgentService.newSessionMode`), which the panel's mode menu raises after its confirmation, and a session's end keeps Codex's copy of its thread (`keepsCodexCopy`). Settings ▸ AI ▸ Agents says why, with Try Again. Only a verified mismatch renames the file. A Persona that stops being agent-only, as after a mismatch, has its running profiles follow the remembered answers from then on.

### Fallback transport

If the user overturns decision 1, the channel moves to Apple Events with the same messages: one custom event, class `'ArAg'` and ID `'call'`, outside `Arch.sdef` so AppleScript users see only today's terms. It is handled through `NSAppleEventManager` with `suspendCurrentAppleEvent()` so a long call never blocks the main thread. The handler reads the sender's audit token (`keySenderAuditTokenAttr`) and applies the code identity check above. macOS asks the user once per sending app for Automation consent. A GUI MCP client app whose own Info.plist lacks `NSAppleEventsUsageDescription` may be denied without a prompt, since that description belongs in the sender's Info.plist, not Arch's. Every call answers within 45 seconds, returning `approvalPending` if still waiting, because a sent event waits with a timeout. Tickets, grants, and the tool host stay as designed. None of this is built unless the user overturns decision 1.

- Start check: Claude Code writes no `system` `init` event before the first message reaches standard input (a probe with open, idle input for 6 seconds produced none), so the check gates the tools rather than the first message. It writes an `init` at the start of every user message's turn, and the check applies to each. Arch writes the first message, which holds only the user's words and the preamble of decision 12. Until `ready`, the model's first output after an `init` that passed the check (The runner), the tool host holds the session's tool calls for at most 10 seconds, then refuses them, so no page data flows. The check requires every tool in `tools` to start with `mcp__arch__`. The first `init` must list every tool of the first `tools/list` answer on the session's connection. A later `init` may follow a mode change, after which `arch-mcp` sends `notifications/tools/list_changed` and Claude Code may not have fetched the new list yet, so each tool it lists must be one that a `tools/list` answer on that connection offered, and it must list every tool that all of those answers offered. Arch's two lists start with these names, and a name joins one only after review, so a version that adds a built-in plugin or agent type is refused until Arch's presets are updated. Otherwise Arch ends the process group and shows "Claude Code started with tools Arch did not ask for: …" or "Arch's tools did not connect." The user's first words may already have reached the vendor then; nothing from the browser has.
- Commands: with a session skill folder, a message that starts with `/` runs one of the built-in commands that `init` lists, without the model (Facts), and `/model` would move the conversation to another model. `AIAgentSession.send(_:)` therefore throws `blockedByPolicy(.agentMessageIsCommand)` for a message that starts with `/` after any white space while the session has a skill folder and a Claude Code model may hold it, so no caller has to guard it. Without the folder, `--disable-slash-commands` makes such a message the user's text.
- Follow-up: one `user` message per line on standard input, `{"type":"user","message":{"role":"user","content":[{"type":"text","text":"…"}]}}`, through the open input mode that `CommandLineProcess` gains (today it writes its input once and closes standard input). The stream does not echo input, but it carries `user` events of the tool's own: tool results, a synthetic message (`isSynthetic` true) that asks the model to continue after a reply with no visible text, and "[Request interrupted by user]" after an interrupt. Text comes only from `stream_event` deltas.
- Stop: the interrupt request `{"type":"control_request","request_id":"<id>","request":{"subtype":"interrupt"}}`. The tool answers with `{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"still_queued":[]}}}` and then the turn's `result` (`subtype` `success`, `is_error` false, `terminal_reason` `aborted_streaming`), both within 20 milliseconds in the recorded session. The process stays, and the next message continues the same conversation. If the turn has not ended within 3 seconds, SIGTERM to the process group and SIGKILL 2 seconds later; Claude Code keeps `arch-mcp` in its process group, so the signal reaches it too. Stopping the process ends the tool's conversation. The next message starts a new process whose first message carries the earlier conversation as text from Arch's transcript (the user's messages and the agent's replies, not tool results), marked as earlier conversation.

| Argument | Why |

### Ordinary requests

The presets' requests for other features carry page data with no tools and no MCP server:

- Claude Code: `-p --output-format stream-json --verbose --include-partial-messages --no-session-persistence --restricted --tools "" --strict-mcp-config --permission-mode dontAsk --permission-prompts none --disable-slash-commands [--model <name>]`, with the environment above less the MCP variables, the prompt on standard input, and the text from the text deltas. An `init` that lists any tool or server, or fails the start check's other conditions, ends the request with `blockedByPolicy(.agentUsedOwnTools)` before the model's reply could call one. Ordinary requests on either preset run the probes first, through the same probe store as sessions.
- Codex: `--no-daemon exec --json --ephemeral --skip-git-repo-check --ignore-user-config --ignore-rules` with the session's `-c` arguments other than `mcp_servers` and `developer_instructions`, the derived `--disable` arguments and `--disable code_mode_host`, since the request calls no tool, `[-m <model>]`, and `-`, with the text of the completed `agent_message` item. The stream starts with the code mode `error` item, which the runner skips. The stream watcher applies.

### The session folder

`$TMPDIR/Arch-Agent-<session UUID>/`, mode 0700, is the CLI's working directory. It holds `mcp.json` (Claude Code) and the session's skill folder (Harness and skills ▸ Delivery), and nothing else, so the tool finds no other files there. The skill folder is the Claude Code plugin that `--plugin-dir` names (`AIAgentSkills`), not a `.claude/skills` folder; the CLIs also read a working folder's `.claude/skills` (Claude Code) and `.agents/skills` and `.codex/skills` (Codex) on their own (Facts), which `--restricted` and `skills.include_instructions=false` keep out of a session. Arch removes it when the session ends and, at launch, removes folders left by an earlier run.

### The runner

`AIAgentSession` in `AI` builds the arguments, starts the tool through `CommandLineProcess` in a process group of its own with pipes, and decodes its events:

| Arch event | Claude Code line | Codex line |
|---|---|---|
| `ready` | the first `stream_event` `message_start` after a `system` `init` that passed the start check | the first item other than `error`, after `thread.started` (its thread ID) |
| `text` | `stream_event` with a text delta | `item.completed` of type `agent_message` |
| `thinking` | `stream_event` with a thinking delta (2.1.323 sends an empty text with a signature) | item of type `reasoning` |
| `usage` | `result.usage`, the sum of the turn's completed requests (`input_tokens` and `cache_creation_input_tokens` as input, `cache_read_input_tokens` as cached input, `output_tokens`), as `MessagesFormat` counts; after an interrupt, the stream's own usage (below) | what `turn.completed.usage`, the thread's running total, added since the thread's previous `turn.completed` (`input_tokens` less `cached_input_tokens` as input, `cached_input_tokens`, `output_tokens`), as `ChatCompletionsFormat` counts; a stopped or failed turn's tokens count with the next turn |
| `notice` | `rate_limit_event` | `error` item before `turn.started`, other than the code mode one in ordinary requests |
| `turnFinished` | `result` (`subtype`, `is_error`, `terminal_reason`) | `turn.completed`, `turn.failed`, `error` |

- The decoders are written against the recorded streams in `Fixtures/Agent` (Tests ▸ Fixtures). Unknown Claude Code line types are skipped; 2.1.323 also writes `system` events with subtypes `status`, `thinking_tokens`, and `permission_denied`, and `control_response`. Unknown Codex items end the session, as the watcher requires.
- Usage after an interrupt: in a turn whose `result` has `terminal_reason` `aborted_streaming`, `result.usage`, `model_usage_since_last_result`, and the growth of `modelUsage` leave out the interrupted request (the recorded third turn of `claude-session` reports only the request before it). For that turn the runner sums each request's last `stream_event` usage instead (`message_delta`, else `message_start`), which for a completed turn equals `result.usage`. The interrupted request's `output_tokens` stays at its `message_start` count, so its output is still counted short.
- Timeouts: 120 seconds to the first output, as for command-line tools, and 180 seconds between outputs. The latter timer pauses while one of the session's tool calls runs in Arch's host, since the tool prints nothing while Arch waits for the user.
- The panel's tool steps come from Arch's tool host, not from the stream, so what the user sees is what Arch did.
- Errors map to `AIError`: a signed-out tool to `authentication` with Open Terminal; a usage limit to `rateLimited`, which is Claude Code's `result` with `api_error_status` 429, `api_error` `usage_limit_reached`, or a `rate_limit_event` with status `rejected` in the turn, whose reset time becomes the provider's cool-down, and Codex's `turn.failed` whose message names a usage limit or "Too Many Requests"; a nonzero exit to `providerUnavailable` with the last line of standard error; and the start check and the watcher to `blockedByPolicy(.agentUsedOwnTools(_:))`, a new reason whose text says what the tool showed, such as "Codex ran a command."

### Model choice and fallbacks

- `AgentService` registers the `agent` feature (trigger `user`; data `page`, `selection`, and `file` for screenshots; requirement `agent`). Its route lists models with the `agent` capability (decision 14) and is on by default, like other features the user starts. Without such a model, Arch shows no agent command. Until VII.19.1 starts API-key sessions in the app, only a Claude Code or Codex preset model opens the entry points (`AIService.agentSessionModels()`), so with only HTTP models with tools Arch shows none.
- The composer shows the route's first model, a menu of the other agent models for the session, and an effort menu from `AIService.agentEffortLevels(for:)` where the tool takes one: Claude Code's `--effort` (`low` to `max`), and Codex's `model_reasoning_effort` with the levels `codex debug models --bundled` lists for the session's model (in 0.164.0, `low` to `max` for `gpt-6-luna`, `low` to `ultra` for the other gpt-6 models, and `low` to `xhigh` for `gpt-5.5`), with no effort menu for a model the catalog does not list.
- A session started without a chosen model (the composer as it opened, the palette's Ask Agent, `arch-cli task` without a model) runs on the route's Claude Code and Codex models, with the route's fallback to the default route. When the route has none, as when Agent Tasks has no model and the default route lists only API models, it starts on the first preset model, the one the composer shows first (`AIService.agentSessionCandidates(named:for:)`), so the palette's row and Continue as Agent Task, offered while any preset model can run a session, never lead to a start the route refuses. VII.19.1 adds the route's HTTP models with tools to these candidates and to the composer's menu in the route's order, so a route whose first usable model is such a model starts an API-key session, and the first preset model serves only a route with neither.
- Fallbacks apply only when a session starts: Arch moves to the route's next model when the first fails before `ready`, its first output (tool missing, signed out, a failed probe or start check, a provider in a cool-down longer than 10 seconds, or a first turn that ends before any output with `providerUnavailable`, `authentication`, or `rateLimited`, as at the subscription's usage limit, which both tools report only after their start event). A Codex thread that the failed model began is deleted. Once a tool holds the conversation, a failure ends the turn with the error and offers Retry and Start Over With \<model>. A conversation never moves to another model: Claude Code runs without `--fallback-model`, and every Codex turn, resumed ones included, passes the session's `-m`. The panel and usage still take each turn's model from the stream, so a model the tool chose by itself shows as it is: Claude Code's `result` `model_usage_since_last_result`, keyed by model name (`modelUsage` adds up the whole process), and each `assistant` event's `message.model`.

### API-key sessions

- With an HTTP model that has `tools`, the same session runs as `AgentAPISession` in `Agent` on `AIClient.run(_:tools:maxRounds:conversationDidChange:)`, with `AIToolHandler`s that call the same tool host and policy, at most 50 rounds per user message (`AgentAPISession.roundsPerMessage`); the 50th round's calls do not run, and the turn ends as `turnLimit`. No socket is involved, and the request's instructions are `AgentHarness.instructions`. Each round may use 8,192 output tokens (`outputTokensPerRound`) rather than the interface's 4,096, which a reasoning model can spend on thinking before its first tool call; current models with tools take at least that many. A message whose last reply stops at the limit shows the notice "The reply reached the output limit." before `turnFinished`.
- `AIRequest.pinnedModel: AIModelRef?` serves a request on that one model with no fallback, also one the route does not list, such as a model the composer offers, if it still exists and meets the feature's requirements. `run` pins every round after the first to the model that served the first, and the session pins every later message to the model of its `ready`, so a conversation never moves to another model. A request with tools goes only to HTTP models with `tools`, so no command-line tool serves one, also one whose capabilities the user overrode to list tool calls.
- The session's tools come through `AgentSessionTools`, the tool host bound to one session: `tools`, read at the start of each message, and `run(_:)` for each call. VII.17 built the binding to a space, its Persona, the mode, and the site scope (`AgentToolClient(session:)`), and VII.17.1 gives each API-key session one; the tests use the tool host behind a grant. `run(_:)` takes the CLI sessions' path in `AgentService`, in a function that takes no connection, which both kinds of session call: a call waits while the user has taken the session over, for at most 10 minutes, runs nothing once Stop or the turn's end cut it off (`staleCallResult(arrivedAt:)`), counts against the session limits (`countCall()`: 150 calls per message, 600 per session), and becomes a step in the transcript and an entry in `agent-activity.json`. A call whose arguments are not a JSON object returns an error result without reaching the host. Stop and `end()` cancel the task that awaits a call: a call that waits, as on an approval card, withdraws its approval as denied and returns at once, and the session drops its result.
- Tool results return as `.text` parts for text the host wrote and `.page` parts for page text: each untrusted block with an address becomes a page part with that address, so the interface's part checks (site exclusions, query and fragment removal) apply as well as the host's. `AgentUntrusted.segments(in:)` reads the blocks beside `wrap`, which writes them: a block without its closing tag runs to the end of the text, and text with an `<untrusted` opening that `wrap` does not write makes the result refused ("Arch did not send this result: its page text could not be told apart from Arch's own."). The `guide` tool's result, Arch's own text, which quotes the marking, goes as text. A result that is not `ok` starts with "Status: \<status> (\<code>).", and `approvalPending` with the line `arch-mcp` writes; it is an error result unless it is `ok` or `approvalPending`, as MCP marks it. Screenshots return as `.file` parts with an image type whose source address is the page they show, so a site excluded later refuses them too: the result's `structured` `url`, which VII.13's `screenshot` sets to the tab's address as `read_text` does, or else the one address of the result's page blocks. An image whose page is not known goes as "Arch did not send this image: the page it shows is not known." A model without `images` gets a note in place of each image, and so does a `chatCompletions` model, since that format sends a tool result as text; a screenshot reaches only a `messages` model.
- The service sends a tool result that its part checks refuse, for a page or an image on a site excluded from AI, also one the user excludes after the result arrived, or a kind the feature does not declare, as an error result that says why without naming the site ("Arch did not send this result: it holds data from a site where AI is off."), so the conversation goes on without the data.
- The conversation is the session's `[AIMessage]` in memory, as the last finished round sent it; a round that fails or is stopped is not in it. Before each round, `AIToolHistory` sends the results of rounds more than eight back as their one-line notes, which the session writes without page text ("Earlier read_text on t2: ok, 12,000 characters of page text, left out to save space."), and a screenshot only until a reply follows a request that carried it, so a screenshot whose request failed or was stopped goes again with the next message. While a request is still over the serving model's input limit, the service sends whole results as their notes too, oldest round first and never the newest, before it cuts any page text, so long sessions stay within the model's input limit. The user's messages and the model's own replies stay whole.
- The session reports the CLI sessions' `AIAgentEvent`s: `ready` with the model before the first text or tool call, text, the message's usage (each round also counts as one request under the `agent` feature), and `turnFinished` (`completed`, `stopped`, or `turnLimit`) or `turnFailed`, after which the session stays open, since no process or thread is lost. Messages sent during a turn wait; Stop ends the turn at once, drops the queued messages, and keeps the rounds that finished, and a call the host is running sees its task cancelled.

## Tools

### Catalog

One catalog in `AgentControl` serves `tools/list`, the MCP server, the CLI's commands, and the API-key loop. - The tool host (`AgentToolHost`) runs, for an outside client's grant, every catalog tool, `guide` from VII.15.1, and for an in-app session `session_info`, `list_spaces`, `list_tabs`, `read_text`, and `guide` until VII.17.1 runs its calls on the grant's path, and `tools/list` lists only the tools it runs; another catalog tool answers status `error` with code `notAvailable`, a name outside the catalog `unknownTool`, and arguments that the tool's parameters do not allow, or a call that gives none or several of its alternative inputs, `invalidArguments`. Tab handles carry the pattern `^t[1-9][0-9]*$`, and the per-call limits are the schemas' `minimum` and `maximum`. The catalog's class notes are traits: waits for the user (`request_tab`, `ask_user`, `request_approval`, `hand_to_user`, `approval_wait`), allowed in Read Only (`scroll`, `hover`), needs the history scope (`search_history`), and destructive (`close_tab`).

### Results

Every result has a `status` (`ok`, `denied`, `refused`, `stale`, `timeout`, `approvalPending`, or `error` with a code such as `notInteractable`, `notVisible`, `tabNotFound`, or `navigationFailed`), `content` (text and image parts), `events` since the session's previous call (navigations with title and address, tabs a page opened, which join the agent folder, dialogs waiting for the user, permission requests denied, downloads asked about, started, or finished, tabs the user closed or took over, and approvals decided), `limits` when a cap applied, and for actions `inputKind` (`dom` now, `trusted` once the tool host uses the engines' trusted input, VII.21). `denied` means the user said no; `refused` means a rule said no and names it as its code ("Agents never type credentials, codes, or card details. Use hand_to_user."), or `readOnly` for Read Only's refusal of an action. The text starts with one sentence about what happened. `structured` carries the same facts as JSON for `arch-cli --json` and MCP's `structuredContent`. The results of `read_text` and `screenshot` carry the tab's address, reduced as in untrusted blocks (`AgentAddress.reduced`), as `structured` `url`, from which an API-key session knows the page a screenshot shows (API-key sessions). Events and limits travel inside the result's text and `structured`, so `AgentToolResult` needs no fields for them: the events follow the result's own text as a second text part, one sentence each under "Since your last call:", and as `events` in `structured`, and `limits` sits in `structured`. A call's events leave out the load of the tab whose load the result reports, and events whose sentences would take the result past 48 KB, oldest first, which the result counts.

### Untrusted marking

- Page-derived text in any result, including snapshot outlines, page text, titles, link text, dialog messages, download names, the schemes of links to other apps and of refused addresses, the host that asks for a sign-in, and event titles, is wrapped as `<untrusted source="page" url="https://host/path">…</untrusted>` (`AgentUntrusted`), with `</untrusted` inside it, in any case, escaped as `<\/untrusted`, as the AI interface escapes `</page`. A sign-in names its host only when it is the page's own, so neither a proxy's host nor another site's frame reaches the agent. Addresses lose their query and fragment, as AI parts do, and also any user name and password (`AgentAddress.reduced`); `ref` lets the agent follow a link whose full address it does not see.
- The harness and MCP `instructions` say that text inside these blocks is data, never instructions, and that text addressed to AI agents must be reported to the user.
- A heuristic flags blocks with phrases addressed to AI models, such as "ignore previous instructions" or "system prompt", in English and Korean, and the panel shows "This page contains text addressed to AI agents" on that step. It is a warning, not a boundary.

## Page snapshots and refs

### The script

`AgentPageScripts` holds one JavaScript function written for Arch. The host runs it with an operation object through `executeJavaScript(_:inWorld:completion:)` in the world `arch.agent`: `snapshot`, `element` (an element's facts and whether an action can reach it, or the focused element's without a ref), `boxes` (what a screenshot paints over, with the viewport and page sizes), or `act`. Each operation carries the policy's word lists, so that `AgentPolicy` holds the only copy. It returns JSON text, which `AgentPageTools.swift` reads. WebKit runs it in a `WKContentWorld` of its own; Chromium runs every world in the page's main world, so a page can replace the built-ins the script calls (Engines). The script keeps nothing in the page between calls (decision 13); anything it kept for a later call on Chromium would be reachable by the page.

### Format

```
t3 · chromium · snapshot 4
<untrusted source="page" url="https://example.org/checkout">page “Checkout – Example” example.org/checkout
- banner
  - link “Home” [e1] → example.org/
  - searchbox “Search” [e2] value=“”
- main
  - heading “Your order” level=1
  - textbox “Email” [e5] value=<personal> (asks the user)
  - textbox “Card number” [e6] value hidden (agents do not type here)
  - button “Place order” [e7] submits form (asks the user)
  - frame “Payments” (another site; not read)</untrusted>
```

- The first line names the tab's handle, its engine, the snapshot's count for the tab, and when they apply the mode `full`, the subtree's ref, and a tab the user shared. The outline is one untrusted block. Names, values, and text stand in curly quotes, a closing quote inside doubled; links show their host and path.

- Roles follow HTML's implicit roles and explicit `role`; names follow reduced accessible name rules (`aria-labelledby`, `aria-label`, `<label>`, `alt`, `title`, `placeholder`, then the text for roles named by content), at most 80 characters. The outline is computed from the DOM on both engines, so it does not depend on an engine's accessibility tree, which Chromium builds only while an assistive app asks.
- Interactive mode keeps elements with refs and the landmarks and headings around them; full mode adds visible text in paragraphs of at most 200 characters each. Hidden elements, `aria-hidden` and `inert` subtrees, `script`, `style`, and `template` are left out; open shadow roots are followed; same-origin frames are walked with refs like `f1e3`; frames of other sites are listed, not read.
- `diff: true` returns the lines added, removed, or changed since the session's last snapshot of the tab, which the host keeps.
- Annotations come from the policy, so the model knows before it tries: "(asks the user)" on elements a rule asks about, "(agents do not type here)" on fields rule P1 covers, and "(CAPTCHA: hand to the user)" on frames of known challenge services and elements named as one.

### Refs

Refs are indexes in the script's walk. The snapshot returns a fingerprint per ref (tag, role, input type, and the first 40 characters of the name), which the host keeps with the document's address. An action passes the index and fingerprint. The script walks again; if the element at that index differs or the address changed, the action fails with `stale`: "The page changed since your last snapshot. Take a new snapshot." For links, the host also keeps the full address, which `open_tab` and `navigate` with `ref` use.

### Fields the script never reveals

- No value for: password inputs; fields whose `autocomplete` names a credential, one-time code, or payment token (`current-password`, `new-password`, `one-time-code`, `cc-*`); fields whose label, name, or ID names a secret (password, PIN, passcode, CVV, CVC, security code, verification code, OTP, token, API key, social security number, and Korean equivalents such as 비밀번호, 인증번호, 주민등록번호); hidden inputs. They show `value hidden`.
- Personal data (`autocomplete` tokens for email, telephone, street address and postal code, and birthday; `type=email` and `type=tel`) shows as `value=<personal>`.
- In a tab the user shared, no field values, as `readableContent` already leaves them out, and screenshots paint every field over.
- Elements inside frames from extension origins, including password managers' inline menus, are left out and cannot be targets, so an agent cannot pick a stored credential from such a menu. The script walks open shadow roots only: a field or an extension frame inside a closed shadow root is neither listed nor painted over (Risks 22).
- Screenshots reveal no more: a capture shows the rendered values, as after the user typed a card number during `hand_to_user` or a password manager filled a field. Before every capture that goes to an agent, the host runs the script's `boxes` operation, which returns the boxes of fields in the hidden and personal classes, of frames from other sites (which a snapshot lists but does not read, and where payment fields often live), and of extension frames, and in a tab the user shared of every text field, editable area, and select. Its walk enters every subtree that shows on the screen, `aria-hidden` and `inert` ones too, which snapshots leave out, since a dialog's library often hides the page behind the dialog from assistive apps while its fields still show. On both engines the host paints them over in the captured image before scaling and encoding. It reads the boxes again after the capture; if they moved, it captures once more and then refuses. Chromium's full-page capture (`captureBeyondViewport`) lays the page out again at its full height, where a fixed dialog or a field below a viewport-high banner can move away from the boxes, and the page is back before they are read again, so a Chromium tab with boxes gets no full-page screenshot (`notAvailable`) and the agent takes the viewport while scrolling (Not verified). A tab whose script does not answer gets no screenshot, and nor does one whose capture does not answer within 10 seconds (`timeout`, `notResponding`). The capture on an approval card, which only the user sees, is not painted over.

### Actions

Each action resolves the ref, checks that the element is connected, visible, enabled, and the topmost element at its center (`elementFromPoint`; a cover is named in the error), scrolls it into view, and then acts through DOM events: a pointer and mouse event sequence and `click()`; focus, then the native value setter from the element's prototype with `input` and `change` events, or `insertText` for editable areas; `KeyboardEvent`s, with Enter in a form field calling `requestSubmit()` with the form's default button, its first enabled submit button, as the submitter; `selected` with `change`. These events are not trusted (`isTrusted` is false), and the result says `inputKind: dom`; sites that ignore them need trusted input. DOM events are to give the page's handlers no user activation: WebKit runs the script without a user gesture (Engines), and Chromium's helper evaluates it in the renderer without one, which VII.13.1 checks (Not verified). Where the tab offers `EngineWebContents.input`, the host acts through it instead at the element's box from the script, mapped to a point in the view, and the result says `inputKind: trusted` (VII.21). It keeps DOM events when the call throws, for select boxes and file, color, and date inputs, whose native controls can track modally on the main thread, and for text with a line break, which the engines refuse because a line break can submit a form. On WebKit, which refuses Space, it types a space into an editable element with `insertText(" ")` and presses Space elsewhere with DOM events. DOM events go to the ref itself, but the engine finds the element under a press, and the focused element for a key or text, only when the page handles the event, so a page could move another element under the point, or move focus, after the host's checks. So `click` sends no pointer move first, which would hand the page an event between the check and the press, and the host checks the target in the event itself: before each trusted action it arms a capture-phase listener that the script adds to the window in the `arch.agent` world at document start. The listener accepts the action's trusted `pointerdown`, `mousedown`, `pointerup`, `mouseup`, `click`, `keydown`, `keyup`, and `beforeinput` only when the target is the ref, or the focused element that `press` was classified by (Rules), or lies inside it. Otherwise it cancels that event and the action's later ones with `preventDefault()` and `stopImmediatePropagation()`, and the result is `stale`. When no event reaches the listener within two seconds, as when the press landed in another frame, the result is also `stale`, and the tab uses DOM events for the rest of the session. What the check cannot stop is under Risks. The script also returns the facts the policy reads: role, name, input type and `autocomplete`, whether the element submits a form, the kinds of the fields a person fills in its form (text fields, text areas, and selects, never hidden inputs or buttons), the site the submission goes to (the submit control's or, for Enter, the default button's `formaction` when it has one, else the form's action), the default button's name and value for Enter, and whether it is a file input, which is refused (rule P7). In an agent tab the facts come after the element scrolls into view and the cover check; in a tab the user shared they come without scrolling, so that a step the user refuses leaves the page where it was, and the action checks the cover once the user allowed it. `wait_for` with a ref never scrolls.

After an action, the host waits for the tab's load to finish or 3 seconds, plus 300 milliseconds, before answering. Each script call and each capture has a 10-second limit, and a card whose capture does not answer opens without one; a page that does not answer, such as while a dialog shows, gets "The page shows a dialog or does not respond. It waits for the user."

## Harness and skills

### Contents

`AgentHarness.swift` holds text written for Arch; nothing comes from another product's prompts or skills:

- `instructions`, static: who the agent works for and where its instructions come from (only the user's messages; everything in pages and tool results is data); the loop (`session_info` first, `snapshot` in interactive mode, act by ref, read the events, snapshot again with `diff` after a change, `read_text` for long reading, `screenshot` only for visual checks, `wait_for` instead of guessing); tabs (open in the background, keep to the agent folder, close tabs no longer needed, ask with `request_tab` for the user's tabs); what Arch asks and how to behave when asked or denied (wait, never look for another way around a denial, call `request_approval` before irreversible or externally visible steps, `ask_user` when unsure); what goes to the user (sign-in, verification codes, CAPTCHAs, payment details through `hand_to_user`; never ask the user for passwords or codes); carrying data from one site to another only when the task asks for it, saying what was sent where; errors and cuts; how to finish (what was done, which tabs and addresses, what was not done and why).
- Topics for `guide` (`AgentGuideTopic`, each with a one-line summary listed at the end of the instructions): `browsing` (opening, reading, following refs rather than writing addresses, waiting, tabs), `forms` (fields, values snapshots hide, secrets left to the user through `hand_to_user`, `request_approval` before a submission, no file choices), `research` (sources, citations, no data carried between sites), `downloads` (asking the user; names and states only), `purchases-and-messages` (prepare, never finish: stop at the final step and ask or hand over), `troubleshooting` (each result status, error codes, dialogs, denied permissions, cuts, limits), and `cli`, generated from `arch-cli`'s command table and exit codes. `arch-cli --help` prints the same text, with each command's usage on its own line. The topics take their numbers from `AgentLimits` and name only the catalog's tools, parameters, and values; a test checks every name with an underscore and a list of the other tool, parameter, and value names the texts use. The `guide` tool's `topic` lists the topics. `AgentHarness.guideResult(arguments:)` returns the result for the tool host: the guide or topic as text, with `topic` and `topics` in `structured`; or `error` with code `invalidArguments` and the topic names for an unknown topic, a topic that is not a string, or another argument. `AgentToolHost` returns it for `guide` in place of its own check of the catalog's parameters, so a null `topic` gives the guide and every error names the topics, as `arch-cli guide` does.
- `mcpInstructions`: a summary of at most 2,000 characters, sent by arch-mcp's `initialize`, that names the `guide` tool and topics.
- `entrySkill(cliPath:)`: the short `SKILL.md` for outside agents (Skills for outside agents).
- `sessionSkills`: the skills in an in-app session's folder, one `arch-<topic>` skill for each topic except `cli`. Each skill uses the topic's text as its body and the topic's summary as its description. In-app sessions have no shell, so `cli` remains a guide topic only.
- `AgentSkill` writes each skill's `SKILL.md`: front matter with only `name` and `description`, followed by the version line `arch-skill-version: 1 sha256=<digest>` and the body. The digest is the hex SHA-256 of the same text with the bare `arch-skill-version: 1` line, so Arch can tell its own text from a copy edited later. The description is a YAML double-quoted string, so its characters cannot change the front matter. Both tools parsed it (Facts).

- Targets, each written only when named: `--target claude` → `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/arch-browser/`; `--target codex` → `$HOME/.agents/skills/arch-browser/`; `--target codex-home` → `${CODEX_HOME:-$HOME/.codex}/skills/arch-browser/`; `--path <folder>` → `<folder>/arch-browser/` for any other agent, in an existing folder. `--target` and `--path` can repeat. Claude Code reads only the first folder; Codex reads the other two. Codex lists a skill installed in both folders twice, so one Codex target is enough (Facts). `HOME` comes from the same environment as the two variables, the process's for `arch-cli` and the login shell's for the app, since both tools read their folders under it; when it is unset or empty, the account database's home folder is used. The tools use these values as they are, so a value of `HOME`, `CLAUDE_CONFIG_DIR`, or `CODEX_HOME` that a named place needs and that is not an absolute path, one starting with `~` included, exits 2, as does a folder inside an app bundle, whose signature covers its files, or a `--path` that is not a folder.
- A skill folder is Arch's if it is a folder, not a link, containing only `SKILL.md` and optionally Finder's `.DS_Store`. The skill file must be a regular file of at most 1 MiB whose body starts with a version line. A copy whose text no longer matches the digest in its version line, as after the user edited it, is modified and also stays unchanged. An empty folder counts as absent. Anything else belongs to the user or another program and stays unchanged.
- `install` prints the exact paths before writing and writes copies, not links, so a sandboxed agent that cannot read the app bundle can still read them. It checks every place first; if any folder is not Arch's or holds a modified copy, it exits 4 before printing or writing any path. `remove` deletes only Arch's unmodified copies and reports places with none. It processes every place: a folder that is not Arch's or holds a modified copy stays unchanged and makes it exit 4, and a place it cannot resolve, such as a `--path` that is not a folder, makes it exit 2; with both, it exits 4. `list` shows each place's path and state: not installed, installed with this Arch's text, outdated (Arch's copy with different text, written by an older Arch or a copy elsewhere, with the command to update it), modified (Arch's copy changed since Arch wrote it), or a folder Arch did not write. Without a place, it lists the three targets. `list` and `install` need the bundle whose `arch-cli` the skill names and exit 77 outside one; `remove` works anywhere.
- Settings ▸ AI ▸ Agents ▸ Skills has a row for Claude Code (`--target claude`) and one for Codex (`--target codex` only, since Codex lists a copy found in both of its folders twice), each with the skill's folder and its state from `AgentSkillInstaller`. The installer takes `HOME`, `CLAUDE_CONFIG_DIR`, and `CODEX_HOME` from the login shell's exported environment, which Arch reads with PATH once per launch, since the app's own environment lacks what a profile exports; the shell starts with the app's own `CLAUDE_CONFIG_DIR` and `CODEX_HOME`, as `launchctl setenv` gives them to every app and the built-in terminal passes them on, and a profile can change them. Install… and, for an outdated copy, Update… show the `SKILL.md` path and the bundle's `arch-cli` that the skill names before writing; Remove removes Arch's unchanged copy at the path the row shows. A modified copy and a folder Arch did not write show that Arch leaves them alone, with no buttons, and a variable that is not an absolute path leaves its row without a folder. ## arch-cli

- It ships in the bundle at `Arch.app/Contents/Helpers/arch-cli`. Settings ▸ AI ▸ Agents ▸ Install Command-Line Tools… and `arch-cli links install [--dir <folder>]` show both paths, then link `arch-cli` and `arch-mcp` into a writable folder on the login shell's PATH, trying `~/.local/bin` first when it is there. They never write outside the user's folders or inside an app bundle, whose signature seals its files, never replace a file that is not a link into an Arch bundle, and check both places before writing either. When no folder is writable, they say how to add one to PATH; `links remove [--dir <folder>]` removes only links into an Arch bundle's `Contents/Helpers`, from the named folder or PATH's folders inside the home folder and outside app bundles, so a bundle's own `arch-mcp` link stays even when its `Contents/Helpers` is on PATH. A named folder outside the home folder or inside an app bundle exits 2, no writable folder 1, and a file in the way 4. Nothing is downloaded. A link follows the bundle, so a rebuilt app brings its own CLI.
- Output: text by default; `--json` prints the result's `structured` value, one JSON object per line for streams. `status --json` prints Arch's answer to `hello`, and `tools --json` the catalog as MCP's `tools/list` result; `guide` and `--help` print text. An error is one sentence on standard error. Text to type can come from standard input (`--text -`), so it stays out of argument lists and shell history. Handles belong to the grant, so `t3` from one `arch-cli open` works in the next `arch-cli click`.
- Exit codes (`AgentExitCode`): 0 done, 1 tool error (such as a stale ref), 2 usage error, 3 denied by the user, 4 refused by a rule, 5 timed out, 6 no grant, the grant was refused, or Arch refused the connection, 69 Arch is not running or agent access is off, 70 internal error, 75 protocol mismatch, 77 the socket is not Arch's. A result's status maps to them: `ok` 0, `error` and `stale` 1, `denied` 3, `refused` 4, and `timeout` 5, as is `approvalPending` should a command still end on one. `setup` exits 3 when the user answers No and 1 when the tool is not on PATH or its command fails; `mcp-config`, `setup`, and `links install` exit 77 outside an app bundle, which has no `arch-mcp` to name.

## arch-mcp

`AgentMCPServer` in `AgentControl` is the MCP core without I/O, and `MCPServerLoop` in `ArchCLI` runs it on standard input and output.

- A stdio MCP server: JSON-RPC 2.0, one message per line, logs on standard error; standard output carries only MCP messages. `initialize` answers with the client's protocol version when it is 2024-11-05, 2025-03-26, 2025-06-18, or 2025-11-25, otherwise with the newest; `serverInfo` `{ "name": "arch", "version": <app version> }`; capabilities `{ "tools": { "listChanged": true } }`; and `instructions` (`AgentHarness.mcpInstructions`). No resources, prompts, sampling, logging, or elicitation. `ping` is answered at any time; `tools/list` and `tools/call` before `initialize` get -32600, and a second `initialize` too.
- `tools/list` comes from Arch for the connection's grant or session: Arch names the tools, and arch-mcp describes them from its compiled-in catalog, with annotations from 2025-03-26 on. While Arch is not running, or the connection fails, the list is the whole catalog. arch-mcp sends `notifications/tools/list_changed` after Arch's `tools/changed`, as after a grant or mode change, and when a new connection follows a list the client already has.
- `tools/call` becomes one control `tools/call`. An unknown tool, a call without a name, and arguments that are not an object get -32602 and never reach Arch; the tool host checks the arguments themselves. Arch's text and image parts become MCP's `content`, `isError` is true unless the status is `ok` or `approvalPending`, and from 2025-06-18 `structuredContent` holds the structured facts with `status`, any `code`, and any `approval`. A call that waits for the user answers after at most 45 seconds with `approvalPending` and an approval ID, and arch-mcp puts "Waiting for the user in Arch; call approval_wait with this ID: \<id>" before Arch's content, which works under any client's tool timeout; in-app sessions raise their tools' timeouts (Claude Code, Codex) so a call simply waits. While a call waits, Arch's `progress` becomes `notifications/progress` when the client gave a progress token, with a count that grows by one and, from 2025-03-26, the message. `notifications/cancelled` becomes `tools/cancel`, which cancels the call in Arch and withdraws its approval, and the call's late answer is dropped. A cancellation sent while arch-mcp connects is read after the connection's outcome, when the call has already reached Arch, so it too becomes `tools/cancel`. A call while Arch is not running returns an error result: "Arch is not running, or agent access is off. Open Arch and turn on Allow Outside Clients in Settings ▸ AI ▸ Agents."
- An outside client connects when a request first needs Arch, ignores a ticket in its environment, and the grant applies. The connection is made before the client's next line is read, so a failure answers in order: lists from the catalog, calls with the failure's sentence (`notArch` and the others included), and the next request tries again. Calls running when Arch closes the connection end with "Arch closed the connection."
- With `--session`, it presents `ARCH_AGENT_TICKET` and exits 2 without it. It connects before the client's first message, so the CLI's first `tools/list` is the session's, and exits with its connection: 69 while nothing listens or after Arch closes it, 6 when Arch refuses the ticket or answers anything but `bound`. It never falls back to the catalog.
- It answers a method it does not serve with JSON-RPC error -32601, before `initialize` too. Claude Code 2.1.323 sends `server/discover` (with protocol version 2026-07-28 in its `_meta`) before `initialize` at 2025-11-25 and initializes after that error; Codex 0.164.0 sends `initialize` first with `clientInfo` `codex-mcp-client` and protocol version 2025-06-18, and a progress token with `tools/list` (Facts).
- It exits 0 when its standard input closes, without waiting for calls still running in Arch, which end with the connection. Codex runs MCP servers in a process group of their own, so a session's Stop reaches `arch-mcp` that way, not through the signal to the CLI's process group; Stop closes no connection, and the calls it cut off are refused with `stopped`.
- MCP elicitation is never used for approvals: a client can answer it by itself, and some clients have automatic reviewers. Approvals are Arch's (decision 5).

## In the browser

### Agent folders

- A session belongs to one space and its Persona. Its tabs sit in an agent folder among the space's open tabs. The folder takes its name from the task's first words, and the user can rename it. It is a `TabFolder` with an `agentSessionID` that is not encoded, and `SessionStore` leaves agent folders and their tabs out of `session.json` (decision 10).
- Agent tabs are ordinary tabs otherwise: they use the Persona's profiles on either engine, so the agent works with the user's signed-in sites, and the Persona's plugins' page scripts and web extensions run in them. They open in the background with the default engine, never take focus, and never switch the window's space. A page that an agent tab opens joins the folder with its opener's engine.
- VII.17.1 builds the session's agent folder on VII.12's (`AgentTabOwner` with the session's ID and title), its rows, take-over by drag, and Keep Tabs; VII.17's sessions open no agent tab of their own yet.
- A tab is an agent's while an agent folder holds it (`Tab.agentOwnerID`, read from the folder at each use). The user can select any agent tab to watch it or drag it out of the folder to take it over; deleting the folder takes its tabs over too. Taking over a tab removes it from the agent's reach and makes it an ordinary tab that is saved and records visits; the agent hears of it as an event, and P17 refuses its handle from then on. Keep Tabs in the folder row's menu turns the folder into an ordinary folder. Close Other Tabs and the archive timer skip agent tabs. Unkept agent tabs are gone after quit, since `session.json` never has them.
- Closing an agent tab, by `close_tab`, by the user, or by its page, adds it to neither the closed list that `session.json` saves and ⇧⌘T reopens nor the tab close log, and ⌘Z after it reopens no older tab in its place. An agent folder goes when its last tab closes or leaves it, by a drag, a pin, or a move to another folder or space.
- An outside client's tabs go to an agent folder named after the client and the app it runs in ("claude · Terminal") among the open tabs of its grant's space, made with its first tab. When the grant ends, its folder and tabs stay, unsaved, until the user closes or keeps them or Arch quits; the client's handles and events go with the grant.
- `Browsing` applies the rules of agent tabs in `Tab` and reports what they did through `BrowserAgentHost` (`AgentTabReport`): P8 denies a permission request without asking, P10 dismisses an alert, P9 leaves a `confirm`, `prompt`, leave-page question, or HTTP sign-in to the user on Arch's card over the tab's pane (`TabPromptQueue`) without bringing the tab forward, each with the origin of the frame that shows the dialog, so that the agent gets a dialog's text only from a frame on the page's site that AI may read, P6 stops a download the user has not allowed, which then does not ask again on the card over the tab about a page's further downloads (`PageDownloadGate`), and P11 a link to another app, and the service asks about each on a card (Approval interface). Each navigation of the main frame, each redirect hop, and a popup's first address go to the service for P16.
- Deleting the space stops its sessions; deleting a Persona stops and removes its sessions and grants.

## Permissions, approvals, and injection defenses

### Modes

| Mode | R | N in agent tabs | I | S |
|---|---|---|---|---|
| Read Only | yes | yes, by the site scope rule for in-app sessions | refused, except `scroll` and `hover` | refused |
| Ask Before Acting (default) | yes | yes, by the site scope rule | asks, with Allow on This Page and Allow on \<site> for This Session | always asks |
| Act in Agent Tabs | yes | yes, by the site scope rule | free in agent tabs on sites in scope (in-app) or in the client's own agent tabs (outside); asks once per site elsewhere | always asks |

- An in-app session starts in the mode set in Settings. The user can lower it at any time and raise it only from the panel's mode menu with confirmation. An outside client's mode is its grant's level, which the client cannot raise. A session an outside client starts with `arch-cli task` starts at the lower of the grant's level and the Settings default, and the client's `--mode` can only lower it.
- `session_info` and the panel's header show the mode and scope, so the agent knows what requires approval.

### Site scope and navigation

An in-app session's scope contains registrable domains: the sites of tabs attached at the start or shared later; the sites of addresses the user wrote in the task or a later message; and sites the user allows during the session. The search engine set in Settings ▸ General is in it only through its results address (`SearchEngine.resultsURL` with nothing but the search terms set), not as a domain, so its redirect endpoints are not. In a session an outside client started, the client's task text adds nothing, since the user did not write it. Rule P13 below applies the scope in every mode, and P16 refuses excluded sites in every session.

- Seen addresses: the host keeps each address the session has seen verbatim, compared after normalizing scheme, host case, default port, and an empty path: the committed address of each of its tabs, the full address behind each link ref in its snapshots, the addresses in the user's own messages, and each address the user approved.
- A link the agent follows, by `ref` or a click, opens without asking because the page wrote its address, which can carry only what the page already has.
- An address the agent writes (`open_tab` or `navigate` with `url`) opens without asking only when it is a seen address, the search engine's results address, or the bare origin (`https://host/`, no path, query, or fragment) of a site in scope. Any other written address asks in every mode, also on a site in scope, because its path, query, or fragment can carry what the agent read elsewhere: the card shows the full address with the parts the session has not seen highlighted ("The agent wants to open shop.example/t?d=… — an address no page showed"), and a site outside the scope adds "a site you did not name".
- Redirects: the host applies P13 and P16 again at each redirect hop of a navigation the agent started, before the hop's request (Engines). A hop to an excluded site is refused; a hop of a navigation by a written address that leads to a site outside the scope stops the navigation and asks with the hop's full address.
- Built by VII.17 as `AgentSiteScope`, which VII.17.1 applies in VII.12's `open_tab`, `navigate`, and redirect checks: `add(_:)` for attached and shared tabs and approved addresses, `addAddresses(inUserText:)` for the user's messages, which reads addresses as a link detector (`NSDataDetector`) finds them, so `example.org/plans` reads as `https://example.org/plans`, `see(_:)` for committed addresses and link refs, `followed(_:)`, `written(_:)`, and `hop(to:ofWrittenAddress:)`, the last two answering `.opens` or `.asks` with an `AgentAddressQuestion` that names the unseen parts (path, query, fragment) and whether the site is outside the scope, and its card sentence. A bare origin opens only on the scheme's own port and without a user name, since a port can carry data too, and only for a host the session has seen or the name of a site in scope (its registrable domain, or `www.` before it), since a host's label can carry data as a query can; another host of a site in scope asks and names the host as the unseen part (`host`). Sites are registrable domains from `AgentSite.registrableDomain(of:)`: an IP address, `localhost`, or a one-label host is its own site; otherwise the last two labels, or three under a two-label suffix of Arch's list (country codes' second levels and hosting platforms such as `github.io`). macOS has no public interface to the Public Suffix List (Risk 20). P5 compares the page's site and the form's by the same function (`AgentPolicy.site(ofHost:)`). The search engine's results address (`AgentSearchResultsAddress`, from `BrowserAgentHost.searchResultsAddress`) matches only its scheme, host, port, and path with the `q` parameter alone and no fragment. An outside client's session never adds the client's text.

### Site exclusions

- Every reading tool (`snapshot`, `read_text`, `screenshot`, `wait_for` with `text`) and every event and tab title checks, at call time, the tab's committed address and the address of each same-origin frame it reads against the current exclusions in `ai.json`, with the AI module's `AISitePattern` matcher, which compares hosts without a trailing dot, since `localhost.` and `example.org.` reach the same hosts and both engines keep the dot. A page on an excluded site returns `refused` (P16), and events and lists name it with no title. A site the user excludes during a session is therefore refused at the next call.
- P16 applies to every navigation in an agent tab, not only the agent's: each redirect hop, each navigation a page starts by itself, and each popup that joins the agent folder. A hop's request leaves before its page commits, so the host refuses it before the request where the engine asks (Engines), and the read checks keep any page that still commits on an excluded site from the agent. An empty document (`about:blank`, `about:srcdoc`) may load, as a page's popup often starts there, and reading one is refused.
- CLI sessions and outside clients get these checks, with the same matcher and the same query and fragment removal, in place of the AI interface's part checks; API-key sessions get both.

### Rules

`AgentPolicy.swift` holds these rules in a table tested for every mode and both client kinds. The host classifies each call by the tool, the page script's element facts, the page's address, and the session's state.

| Rule | Trigger | Result |
|---|---|---|
| P1 | Typing or pressing keys into a password, credential, one-time-code, or payment field, or a field whose label names a secret | Refused: "Agents never type credentials, codes, or card details. Use hand_to_user." |
| P2 | Typing into a personal-data field | Asks, showing the exact text |
| P3 | Submitting a form (a submit control, or Enter in a field) that contains password, one-time-code, payment, or personal fields that a person fills (hidden inputs and buttons do not count) | Asks |
| P4 | Clicking a control, or submitting a form by Enter (`type` with `submit`, `press` Enter) with a default button, whose name or value reads as an irreversible step: buy, purchase, order, checkout, pay, subscribe, donate, transfer, send, post, publish, share, reply, comment, submit, delete, remove, cancel subscription, unsubscribe, confirm, agree, accept, sign, and Korean equivalents such as 구매, 결제, 주문, 구독, 송금, 보내기, 전송, 게시, 공유, 댓글, 제출, 삭제, 탈퇴, 확인, 동의, 수락, 서명 | Asks |
| P5 | Submitting a form whose action, or its submitter's `formaction`, is on a different site from the page, after the session typed into it, or by `type` with `submit` | Asks |
| P6 | A download from an agent tab (`shouldDownload`) | Asks, with Allow Downloads from This Site for This Session |
| P7 | A file input or a file chooser in an agent tab, whatever started it | Refused until VII.22's tool host part; then asks, naming who asks from the request's `origin` and `pageOrigin`, never the tab's address, what the page asks for, and its accepted types, and the user picks in Arch's open panel; the agent never names a local path and learns no file name |
| P8 | A permission request (camera, microphone, location, screen, notifications, and others) from an agent tab | Denied without asking; the result tells the agent to hand the tab to the user |
| P9 | A `confirm`, `prompt`, or leave-page dialog, or HTTP authentication, in an agent tab | The user answers on Arch's own card over the agent tab's pane; the agent waits, hears from the tab's report through `BrowserAgentHost` that the dialog waits, and sees the dialog's text as untrusted, only when the frame that shows it is on the page's site and not excluded |
| P10 | An `alert` in an agent tab | Dismissed and reported as an event, with its text under P9's condition |
| P11 | A link to another app (`openExternally`) from an agent tab | Asks, naming the app |
| P12 | Any interaction in a tab the user shared | Asks every time, whatever the mode |
| P13 | In-app navigation by an address the agent wrote that is not a seen address, the search engine's results address, or the bare origin of a host the session has seen or of a site in scope's own name; a redirect hop of a written address's navigation to a site outside the scope | Asks, in every mode (Site scope and navigation) |
| P14 | In-app typing on a site outside the scope in Act in Agent Tabs | Asks, showing the exact text |
| P15 | `request_approval` | Asks |
| P16 | Navigation, a redirect hop, a page's own navigation, or a popup to a site excluded from AI, an internal page, a `file:` address, or another scheme; any read of a page on an excluded site | Refused; events from an excluded page carry no title; the card offers no change to the exclusions (decision 15) |
| P17 | Closing a tab the session did not open; acting on a tab of another session or Persona | Refused; an unknown handle returns not found |
| P18 | A CAPTCHA or bot check | Refused: "Hand the tab to the user." |

- P4's word list reads page-controlled text, so a page can label a button to avoid a match. The words can only add approval requests, never remove one. The harness tells the model to call `request_approval` before any irreversible step, and the default mode asks before every action. This remains under Risks.
- `press` acts on the element that the page script reports as focused when the host classifies the call. Enter or Space on a button, a submit or reset input, a link, a checkbox, a radio button, or a file input counts as a click on that control for P3, P4, P5, and P7, and the card names the control; Enter in a field is P3's Enter. Untrusted key events activate no control by themselves, but a page's own key handlers act on them, as a script's `role=button` that places an order on Enter does, and trusted ones activate controls too (VII.21), so the policy classifies `press` this way on the DOM path already (`AgentPolicy.pressActivates`, with a switch among the controls; P7 refuses a file input whatever the tool), and Enter on a submit input submits with that input. The target check (Actions) holds the key to that element.
- A JavaScript dialog never gets an automatic OK, and no CAPTCHA is solved.
- No mode, grant, or setting turns P1 to P18 into automatic approvals, whatever the amount, site, or client. Arch has no "pay under an amount" or "send without asking" setting, and approvals never outlive their session.

### Approval interface

- Cards appear in the agent panel beside the page and in the sidebar's folder row, never over the page, so a page cannot draw or cover one.
- A card leads with facts the host computed: the action in a sentence ("Click “Place order” on shop.example"), the tab and site, the element's box marked on a fresh viewport capture when the tab can be captured, and the exact text or address that would be sent. The model's explanation follows under "The agent says:", marked as the agent's.
- Buttons: Allow Once, Allow on This Page (I class in Ask Before Acting, until the tab shows another page: its address changes other than in its fragment, which comes as a navigation starts or commits, before the document finishes, or another document finishes loading), Allow on \<site> for This Session (I class, P14), Deny, Deny and Stop, and Reply…, which sends an instruction instead of yes or no. These allowances cover typing too, so the card for a `type` call says that the site then receives whatever the agent types there (Risks). Cards for P2 to P5, P11 to P13, and P15 are sensitive: they offer only Allow Once, Deny, Deny and Stop, Reply…, and Take Over (the user does it). A P13 card allows only its one address, whose site then joins the scope.
- The host applies P1's secret words to the text of `ask_user`, `hand_to_user`, and `request_approval` cards. On a match, an Arch-written line leads the card: "Agents never need your passwords or codes. Type them only into the page after Take Over." An answer goes to the agent, and an address that would carry it on to a site asks under P13.
- No card has a default button and no button takes the keyboard focus, so Return and Space answer none. Allow on a sensitive card, Share on `request_tab`, Done on `hand_to_user`, and Allow on the grant sheet take only the click that the button's own tracking loop runs for, a mouse-down in its window and within its bounds, so an accessibility press or `performClick` presses nothing, whatever event the app handled last. A click that a program posts with Quartz events names that program in `CGEventField.eventSourceUnixProcessID`. Arch reads that process by its running code, never by the path it was started with, which the starter chooses: it takes a click whose source is none, Arch, or a process of another user such as the window server, and from a process of the user only when Security finds its code valid, signed by Apple (`anchor apple`), and with the signing identifier of one of the system's programs that click for a person: Universal Control, VoiceOver, Dwell Control, the accessibility interface server, and Screen Sharing's agent. It refuses every other program of the user, `osascript`, System Events, Script Editor, and `automator` among them, and a source it cannot read, as one that exited after it posted (`AgentPointerCheck`). A person's click counts under each of those readings of a hardware click's source, which VII.13.1 checks with a posted click beside it. For outside clients, and in sessions an outside client started with `arch-cli task`, Allow on a sensitive card and Share on `request_tab`, which hands the client one of the user's tabs, also ask for Touch ID or the login password, so a program that drives the interface through accessibility cannot approve.
- Several approvals can queue per session. An approval for a page that has moved on is withdrawn and its call fails with `stale`; a step whose card the user allowed runs only while the tab still shows the page and address it was allowed on. One download card per tab waits at a time; a page's other downloads meanwhile do not start, and the agent hears so as an event. The notification goes out once while a client's cards wait. A client's `tools/cancel` from the connection that sent the call withdraws its approval, and for `approval_wait` that of the call it waits on, which then never runs, or stops its wait on the grant sheet, which stays open for the client's next call; the call ends with status `error` and code `cancelled`, which `arch-mcp` drops, and frees its slot. Unanswered approvals are denied (`timeout`), as are pending approvals at Stop, Stop All Agents, revocation, and quit. Stop, Deny and Stop, Stop All Agents, revocation, expiry, and the close of a call's connection also cancel the client's running calls, which then run no further step and open no card. An ended card leaves memory with its capture.
- A call that answers `approvalPending` goes on, and when it ends the activity log records its entry with the user's decision and the panel its step, whether or not the client calls `approval_wait`; the call's first entry says `pending`, and `approval_wait` is logged as a plain read.

## What the agent can never change

No tool, command, control method, or MCP call exists for: Settings and `ai.json` (providers, keys, routes, exclusions, limits); `agent.json` (modes, grants, outside access); site permissions; plugins and web extensions and their grants; Personas and spaces of other Personas; cookies and site data; passwords and passkeys; the clipboard; local files; internal pages; AppleScript; and other apps. `Arch.sdef` gains no agent or approval term. Only the user can change modes, grants, scopes, and approvals, through Arch's interface.

## Personas, history, and permissions

- A session belongs to one Persona from its creation: the Persona of the space where the user started it, or the grant's Persona for an outside client. Its tools see only that Persona's spaces and tabs.
- The Agents Persona is an ordinary Persona with storage of its own on both engines (Persona rule 2), so it holds no sign-ins until the user signs in there. `agent.json` records its ID. The app reads the ID without the key before it creates the session, which hands it to `SitePermissionAnswers` before any engine starts, so a profile that a restored favorite's tab starts during the session's creation is agent-only too; the service then keeps the session's choice in line with the checked seal through `BrowserAgentHost`. `SitePermissionAnswers` leaves its profiles out of `follow(_:of:)` and denies its permission requests without a card or a record, also clearing the answer from the profile, since Chromium keeps every answer it receives (decision 9). The default Persona is never agent-only. If `agent.json` loses its seal, the Persona becomes ordinary again, and its running profiles take the remembered answers from then on; a profile that took them before its Persona became agent-only keeps them until quit, which cannot happen to the Persona Arch creates. Deleting the Agents Persona removes its grants and its record.
- In the user's own Personas, `BrowserSession` copies the remembered answers from `permissions.json` into every profile. On Chromium, `CEFBridgeRequestContext` sets them as content settings, so Chromium answers a remembered request without asking the delegate. A site the user allowed the camera, microphone, or location keeps that access in Chromium agent tabs of that Persona. P8 applies on WebKit, which asks the delegate each time, and to every request that is not remembered. The composer says so when the session's Persona has such answers.
- Agent tabs record no history visits, so pages an agent visits enter neither suggestions nor the app-wide history (Persona rule 6). `search_history` reads that app-wide history, which spans every Persona. It is off unless the user turns it on for in-app sessions or grants it to an outside client with Touch ID. Its results omit excluded sites, queries, and fragments.
- Downloads: an agent sees only those its own tabs started, by name and state.
- Arch has no private window. If one is added, agents never see its tabs, cannot open one, and a request to read one is refused.

## Usage and cost

- Each turn's tokens come from the tool's stream (for Codex, what the turn added to the thread's running total), or the provider's reply for an API-key model, and go to `AIUsageStore` under the `agent` feature, provider, and model. For a CLI turn, an Activity entry stays in memory (feature, model, tool step count, tokens, result; Show Content shows the turn's text and tool names, not tool results). An API-key session adds an entry for each round, as every AI request does, and its Show Content shows the request as sent, tool results included: page blocks without query or fragment, notes, and refused results as their refusal.
- The panel shows the model and tokens under each turn. A subscription shows "Included in your subscription" and no cost; Claude Code's `total_cost_usd` is ignored, since Arch shows cost only from prices the user entered. An HTTP model shows the estimated cost.
- A rate-limit or quota notice shows only when the tool's stream reports one. Arch reads no usage endpoint and shows no quota meter.
- The monthly spending limit applies to API-key sessions; the daily limit for automatic requests does not apply, since every turn is the user's. The session limits apply to every model.

## Engine members

The first build adds no engine protocol member; `executeJavaScript(_:inWorld:completion:)`, captures, `readableContent`, navigation, and the UI delegate reports cover it. VII.12 changed which navigations the adapters ask about: both ask the navigation delegate about every main frame navigation and redirect hop, the Chromium adapter from `OnBeforeBrowse`, and the WebKit adapter no longer about frames inside the page, so the host can refuse a hop before its request (Site scope and navigation; Site exclusions). Later tasks add these with their features:

- VII.21, trusted input: the optional `EngineWebContents.input` (`EngineInput`) moves the pointer, clicks one to three times, turns the wheel, presses a key, and inserts text at a point in the page's view, in points from its top-left corner; `EngineInput`'s comment maps an element's box to that point (`(x - visualViewport.offsetLeft) * visualViewport.scale * zoomFactor`). Each call sends all of its events or throws `EngineInputError` and sends none: `notInWindow`, `outsideView`, `noPage`, `notFocused`, or `unsupported`. Both adapters refuse a click with Control, which opens the context menu, a count outside 1 to 3, and text with a line break, which submits a single-line field's form as Enter does. A click sends no pointer move before its presses, so the page gets no event between a caller's check of the point and the press; the press itself makes the element under it the hovered one. Wheel deltas are rounded and clamped to ±100,000 points (`EngineWheelTurn`), within the engines' 32-bit wheel fields, and a delta that is not finite is refused. Neither uses a private API, and neither posts events through the window server or `NSApplication`, so the input reaches only the page, never Arch's own controls, sheets, and cards, or another app; the one way back, a key the page leaves unhandled, stops before any of Arch's own handling, as below.
  - Chromium: the bridge's methods over `CefBrowserHost::SendMouseMoveEvent`, `SendMouseClickEvent`, `SendMouseWheelEvent`, and `SendKeyEvent`, while the browser's view is in a window. Text goes as one character event per character, because `ImeCommitText` serves only pages that CEF draws offscreen; a character outside the Basic Multilingual Plane, such as most emoji, is refused. Every key and modifier goes, since CEF passes the key to the page past the input source. CEF builds the AppKit event of such a key with window number 0, and the bridge's `CefKeyboardHandler::OnKeyEvent` stops it when the page leaves it unhandled, before CEF offers it to the main menu; the user's keys carry their window's number and go on as before.
  - WebKit: `NSEvent`s made with public constructors and sent to the web view's `mouseDown`, `mouseUp`, `mouseMoved`, `scrollWheel`, `keyDown`, and `keyUp`, the wheel event made from a `CGEvent`, and text through `insertText(_:)`. Keys go only while the web view is the first responder of the key window, or of its window while no window is key, never with Command or Control, and with no function key flag, so AppKit offers none to the menus; WebKit hands a key down that the page leaves unhandled back to the application with `NSApplication.sendEvent(_:)` once the page has answered, as the event the input sent. The page can put that off for seconds, by which time another window or the address field can be key, and AppKit calls local event monitors in no fixed order, so the app's `NSApplication` subclass (`ArchApplication`) drops every key down the input sent in `sendEvent(_:)`, before AppKit's monitors, the menus, and the key window see it (`WebKitEngine.isTrustedInputKey(_:)`, which knows each sent key while WebKit holds it, however many went since), and `WebKitWebView` drops one that reaches it through its window. Character keys and Space are refused, because they pass through the user's input source, which could type another character, such as a full-width space, or convert text it is composing; `insertText(_:)` types text, a space included. A click that focuses a field makes the web view its window's first responder, as a script's `focus()` does.
  - The tool host's use of the member is the rest of VII.21, after VII.22's tool host part (plan, Work Queue; Risks).
- VII.22, file choosers: `EngineWebContentsUIDelegate.webContents(_:runFileChooser:completion:)` reports a page's file choosers on both adapters as an `EngineFileChooserRequest`: its mode (one file, several files, a folder, or, only on Chromium, a place to save), the page's accepted types as lowercase MIME types and dotted extensions, a suggested name for saving, and who asks: `origin`, the asking frame's, which only WebKit names, and `pageOrigin`, the page's from its committed main frame address, never from an address the page started loading. Neither engine shows a panel of its own for a tab's chooser; the default answer is no file, and the page receives only file addresses, only the first for a chooser of one item (`answer(from:)`). The report says nothing of what started the chooser: a trusted click, a DOM `click()`, or the page's own script after an earlier activation.
  - Chromium: the bridge's `CefDialogHandler::OnFileDialog` takes every chooser of a tab's or preview's browser, a browser without an owner included, which gets a cancel, and passes CEF's mode, the page's `accept_filters`, and the main frame's committed address, since `OnFileDialog` names no frame; a save chooser suggests only the file name of CEF's default path. ## Risks

1. A site in an Act in Agent Tabs session's scope can disguise an irreversible control so that P4 misses it. The default mode asks before every action, the harness requires `request_approval`, and the user picks Act knowingly.
2. On Chromium, the agent's script runs in the page's main world, so a page can alter its own outline, the element facts P2 to P5 read, and the boxes that screenshots paint over. Until VI.6, Chromium agent tabs trust those facts only as far as the page's own content; navigation, downloads, dialogs, permissions, and links to other apps come from the engine and are not affected.
3. Outside clients with their own shell or network can be steered by page text. Arch marks it and warns in the grant sheet; the Agents Persona and Read Only defaults limit what such a client can read.
4. Programs running as the user can start the signed CLIs, read tickets, or post input events. They can also take the socket's path when Arch is not listening; `LOCAL_PEERTOKEN` names the process that last used the peer's end, so a program that binds the path and then `exec`s valid Arch code, with a child holding the socket, can pass a one-time code check. Each end therefore reads the token again before every frame and requires the same process ID and version, Arch sends `ready` first so the client sends its ticket only after a frame from the checked process, and the handoff child's differing process ID fails the recheck. These, with sealed grants, the ancestry check, Touch ID on grants outside the Agents Persona and on outside clients' sensitive approvals, and the click check, raise the bar but are not a sandbox against the user's own account; Settings says so.
5. CLI flags, features, and events change between versions. Arch probes before trusting a version, checks Claude Code's start event, derives Codex's disables from its own list, watches both streams, and refuses rather than guesses. A release can still break sessions until Arch's presets are updated.
6. Codex keeps agent conversations, with page text, in its own folder until Arch deletes them. A crash before deletion leaves them there.
7. On Chromium, a site the user allowed the camera, microphone, or location keeps that access in agent tabs of the user's own Personas.
8. Chromium agent screenshots attach a DevTools client for the tab's life, which turns off Chromium's hung-page timeouts for that tab.
9. `ai.json` is not sealed; a program that edits it can remove site exclusions that agents also obey.
10. Approval fatigue in Ask Before Acting may lead users to Act in Agent Tabs; grouping per page and per site keeps the count down.
11. An agent session can use much of the user's plan, and Arch shows only what the tool reports.
12. Whether the socket fits "Arch runs no servers" depends on interpretation (decision 1, open decision 1).
13. Typing sends data to the page's site as the agent types, since the page's scripts read each field. In Act in Agent Tabs on sites in scope, and after Allow on This Page or Allow on \<site> for a `type` card, a page that steered the agent, often the attached tab itself, receives whatever the agent types there without another card. The card says so, and Ask Before Acting is the default.
14. Address checks cover what an address carries, not every route: an agent steered by a page can still leak a little by which of the page's own links it follows, and the search engine receives the terms the agent searches for. The panel shows each followed link and each search as a step.
15. Codex's current models call tools only through its code-mode host, which runs the model's JavaScript beside `codex`, so Arch keeps it on. Arch sees only the calls that reach `arch-mcp`; what that JavaScript can reach besides `tools.*` was not checked. Codex's sub-agent tools stay offered to the gpt-6 models, and the watcher ends a session that uses them.
16. Claude Code loads built-in plugins that no session argument turns off. The start check accepts only reviewed names, but `init` shows what a plugin adds to tools, skills, and commands, not what it does inside the tool.
17. A program that a client starts can use the client's grant: it `exec`s `arch-cli`, or a shell that runs it, and keeps its process, so the walk passes over it and the start time check passes. For a client reached through a shell, such as Terminal, that is every program started there, and the sheet and Settings say so; Arch cannot tell such a program from the user's own command.
18. Trusted input gives the page user activation, as the user's click or key does: after an agent's trusted action, the page may open a popup, enter full screen, write the clipboard, or open a file chooser. Popups join the agent folder, and permission requests in agent tabs are denied (P8). Both adapters report a tab's file choosers to the UI delegate, and Arch's panel waits among the tab's prompts (VII.22), so neither engine opens a panel of its own for them; the tool host uses trusted input only after VII.22's tool host part, whose P7 card asks before any panel. On WebKit the DOM path gives activation too only while the page script runs with the public evaluation's user gesture, with a private API flag off or the private member gone (risk 21): `evaluateJavaScript` runs with one, also in an app's own world, so the agent script's `click()` on a file input then opens the chooser (Facts), and P7 covers every chooser report from an agent tab, whatever started it. A clipboard write and full screen are not checked.
19. Trusted input acts on whatever lies under the point or has focus when the page handles the event. The target check (Actions) cancels a press, key, or text that the page moved to another element of its own document, but a page can still move another site's frame under the point, or focus into one, between the host's check and the event. That frame then receives one trusted click or the text, which no listener in the page sees and which DOM events never reach; the host returns `stale` and keeps the tab on DOM events from then on. On Chromium the check runs in the page's main world until VI.6, so the page can remove or outrun it, as it can change the facts the rules read (risk 2).
20. The site scope counts sites by Arch's list of two-label suffixes, not the Public Suffix List, which macOS offers no public interface to. A platform missing from the list counts its customers as one site, so a redirect hop on another customer's site goes without asking, and so does the bare origin of its registrable domain or `www.` before it. A written address with a path, query, or fragment that no page showed asks whatever the list says, and so does a bare origin on a host the session never saw, so a host label cannot carry data out.
21. On WebKit, the agents' page script runs without a user gesture only through a private member behind the private API flags. With a flag off, or the member gone in a later WebKit, `executeJavaScript` falls back to the public evaluation, whose gesture gives the page's handlers for the agent's click, type, press, select, and hover events transient user activation, so a page in an agent tab could write the clipboard or open a share sheet, a passkey prompt, or fullscreen during an agent's step.
22. The page script cannot see inside a closed shadow root: on both engines, `shadowRoot` is null in the script's world, so a field or an extension's frame there, as a password manager's inline menu inside one, is neither listed nor painted over in screenshots, and the menu's stored names can show in a capture. WebKit has a private content world configuration that opens closed shadow roots to a world, which a later task could use for the agent's world behind the private API flags; Chromium gives the page script no such access.
