# Password manager plugins design

## Purpose and scope

- This note describes the design for running the 1Password and iCloud Passwords extensions in Arch as web extension plugins on both engines: the host discovery and proof gate that IV.21 built, the install script and the status in Settings that IV.22 built, queue task IV.13 in `docs/plan.md`, the user's steps IV.23 and IV.24, and row 39 of `docs/features.md`. Both extensions come from the Web Store (`docs/web-store.md`), and both reach a native app on the Mac through native messaging (`docs/plugins.md`, Web extensions as plugins).
- Arch handles the work that needs no outside action: finding the native apps' host manifests, which the vendors install only for browsers they know; distinguishing a real extension from a package that copies its identifier; installing Arch into `/Applications`; and showing status and guidance in Settings ▸ Plugins. The user adds Arch in 1Password, and for iCloud Passwords opens the pull request to Apple's list of browsers once Arch has a public website and download link (IV.24).
- Arch bundles no third-party code, reads other browsers' folders without changing them, and never changes 1Password's files or settings.
- Nothing here uses a private API or needs a flag on `flags://`.

It has a service for adding a browser (`browser-addition`), so 1Password may ask the user to trust an unknown browser when it connects. The names of 1Password's settings and prompts need verification in IV.23.
- Apple's helper is `/System/Cryptexes/App/System/Library/CoreServices/PasswordManagerBrowserExtensionHelper.app` (bundle identifier `com.apple.PasswordManagerBrowserExtensionHelper`, version 27.2). Its host manifest `com.apple.passwordmanager.json` is in the system host folder of one other browser, as a symbolic link into the system's App cryptex, and allows `pejdijmoenmkgeppbflobdenhhabjlaj` and `mfbcdcnpokpoajjciilocoachedjkima`. Another copy, in another browser family's folder, uses that family's manifest format, which Arch does not read.
- Apple's `password-manager-resources` repository explains that from macOS 15.5, Apple turns its file `quirks/web-browser-extension-distribution-information.json` into launch environment constraints signed into that helper, so a browser added to the list needs a macOS update to work. `codesign -d -vvvv` on the helper shows them as its parent launch constraints, an `$or-array` of conditions on the process that starts it. The first admits a parent whose entitlements set `com.apple.developer.web-browser.public-key-credential` to true, the browser passkey entitlement, which Arch does not pursue, whether or not the browser is listed. Each of the others is an `$and` of a listed browser's signing identifiers and its team identifier. Arch meets none of them on this Mac. A browser signed with the entitlement therefore starts the helper without a list entry or a macOS update. `codesign` writes the kinds of constraints (`Has Self Launch Constraints`, `Has Parent Launch Constraints`) to its standard error and their trees to its standard output; on 2026-11-14, `HelperLaunchConstraints` read the helper's parent constraints as the entitlement condition and 34 pairs, with no member it could not read, and found that the test process that read it meets none.
- Each entry in that file has `long_name`, `short_name`, `supported_platforms`, `platform_specific_information` (for `Mac`, the required `bundle_identifier`, `code_signing_identifier`, and `code_signing_team_identifier`, and the optional `extensions_install_path_relative_to_user_library_directory` and native messaging process fields), and `supported_store_identifiers`, where `1` is the Web Store. The pull request template requires the browser's official website, a download link, and `codesign -d -vvvv` output from a copy downloaded there.
- Arch keeps its host manifests in `~/Library/Application Support/Arch/NativeMessagingHosts/`, which does not exist on this Mac; no vendor writes there. Chromium reads them through a link the engine creates at `NativeMessagingHosts` under its root cache path (`docs/plugins.md`, Native messaging). For a name that has nothing there, following links, Chromium's `NativeProcessLauncher::FindManifest` then reads its system folder, `/Library/Application Support/Chromium/NativeMessagingHosts` on the Mac, which the pinned framework names (read with `strings` on 2026-11-14) and which does not exist on this Mac. Arch's links do not decide what Chromium finds there; check 65 confirms that Arch's engine reads it.
- macOS protects another installed browser's data folder as its app data: reading it fails with `EPERM`, without a prompt (`docs/import-browsers.md`, Permissions). Vendor-created folders for uninstalled browsers were readable from a shell; IV.13 checks whether Arch can read them.
- `scripts/bundle_app.sh` writes `build/Arch.app` with the bundle identifier `xyz.taeyoon.arch`, signed with the user's individual team: its newest Developer ID Application identity on the Mac, then its newest Apple Development identity; without either, with the first Apple Development identity, or ad hoc without one (`ARCH_SIGN_IDENTITY` overrides the choice). It does not enable the hardened runtime.
- Both engines start a native app from Arch's own process: Chromium's browser process is the app's main process under CEF, and `NativeMessaging` starts it with `Process`. The helper's parent is therefore Arch on both engines.
- A Chromium profile can start the extensions it ran in an earlier launch before the runtime's first load pass of the run ends; the pass stops those it does not load once its loads end (`WebExtensionRuntime`, `profileDidStart(with:of:)` and `loadEnabledExtensions()`). An extension that the runtime unloads leaves Chromium at once.

## Decisions

1. Install from the Web Store: both extensions install as store packages, so their identifiers are proven (`docs/web-store.md`, Package proof). A vendor package from a file works when its `.crx` signature verifies.
2. Host discovery: Arch reads the host folders listed by `BrowserSource.nativeMessagingHostFolders` in the `Import` module (`docs/import-browsers.md`, Native messaging hosts) without changing them, and links each valid manifest into its own `NativeMessagingHosts/` folder. Vendors install manifests only for browsers they know, so otherwise the user would have to copy them by hand and recopy them after every vendor change. A link follows the vendor's changes. Chromium follows manifest links, as it does for the system's manifest above. The user's own files in Arch's folder take precedence, and a host whose native app is known not to start for Arch gets no link (Held hosts).
3. Proof gate: a version of an extension reaches a native app through one of Arch's own links only when Arch has proof of its identifier. A package can copy any extension's public `key` and thus its identifier, and the native app trusts the identifier that the browser passes it. A manifest the user puts in Arch's folder takes its name's place for both engines and keeps the current rule, since the user set it up for Arch. Chromium also reads its own system folder under a name that Arch's folder lacks (Facts), so on Chromium the gate also covers every manifest there, whether Arch would link it or not. The gate never switches a whole plugin off: on Chromium, which reads the links itself, a gated version leaves only the Chromium engine, as for a failure to start there, and WebKit refuses each of its calls.
4. `/Applications`: `scripts/install_app.sh` copies the signed `build/Arch.app` into `/Applications` as a real bundle, since 1Password refuses a browser outside `/Applications` or behind a link. A script fits the build procedure, which creates a new bundle with every build; copying from inside the app would replace a running app's bundle. The script replaces only an earlier Arch or a link, and keeps the earlier bundle until the new one is in place.
5. Signing: the install script takes the bundle as `scripts/bundle_app.sh` signs it (Facts), so on a Mac with a Developer ID Application identity of the user's team, 1Password sees that identity, and otherwise an Apple Development identity. If 1Password refuses Arch for the hardened runtime, a later task signs with it and the entitlements Chromium's helpers need.
6. Guidance: Settings ▸ Plugins shows, for each web extension with a native app, which app accepts it, whether Arch meets the app's known conditions, and the user's step for 1Password and iCloud Passwords. The two vendors' host names and guidance text are in `NativeAppGuide.swift`.
7. iCloud Passwords: Apple's helper starts for a parent with the browser passkey entitlement or for a browser in Apple's list (Facts). The entitlement is not pursued: only an organization can request it, and the user keeps the individual team and the bundle identifier `xyz.taeyoon.arch` (decided November 23). Arch goes through Apple's list (IV.24), whose pull request template requires a public website and download link, so the user opens it once those exist. The entry and steps are below, with a placeholder for the team identifier. While Arch meets neither condition, Arch holds the helper's host, so neither engine starts the helper, and Settings says why.

## Host discovery

- `NativeMessagingHostLinks` keeps the links. The session creates one per app with Arch's folder and the folders the app shell passes from `BrowserSource.nativeMessagingHostFolders`. Passes run off the main thread. `update()` runs one only if none has run in the current run, and `update(force: true)` always runs one. They are called:
  - by each runtime, `update()` before its first load per run of an enabled extension whose grant has `nativeMessaging`, and `update(force: true)` after installing or updating one;
  - by staging, `update()` for a package that asks for `nativeMessaging`;
  - by Settings ▸ Plugins, `update()` when it first shows, in a run, the section of a plugin whose grant has `nativeMessaging`, enabled or not (`NativeAppGuide.look(for:in:)`, Status).
  A Mac without such an extension never reads the folders. The session keeps the app's links as `BrowserSession.nativeMessagingHosts` and gives them to every Persona's runtime and manager (`PluginManager.nativeAppGate`).
- A pass reads each folder's `*.json` files in the list's order, each a regular file of up to 64 KB, followed through links, so that a pipe with a manifest's name cannot stall it. It keeps a manifest whose `name` matches its filename without `.json` and follows the naming rule, whose `type` is `stdio`, whose `path` is absolute and names an executable file, and whose `allowed_origins` can be read. For each name, the first folder with a valid manifest wins.
- In Arch's folder, the pass creates `<name>.json` as a symbolic link to that manifest, unless something else has that name: a regular file or a link outside the listed folders, which remains the user's. It replaces its own link when the winner moves and removes its own links whose names no longer have a winner. A new link is made under a temporary name and renamed into place, so that the engines never find the name missing while a link changes. Arch's links are the links in its folder whose destination is a file directly in a listed folder.
- Order: a pass that would create a link or change a link's destination first counts the links it will make in the gate (`gatingHosts`) and calls `gateWidens`, through which the session has every Persona's runtime take out of Chromium the versions that the gate refuses under those links and stop what Chromium runs that the runtime has not loaded (`takeGatedVersionsOutOfChromium()`, Proof gate). That covers a copy that the profile kept of an extension that the Persona's list lacks, as one whose package no longer reads, whose identifier the gate cannot check; in the run's first pass, it also stops the kept copies of enabled extensions, which the pass then loads again. A runtime does so outside its queue of changes to the engines, since its own pass of loads may be waiting for this pass, and waits for a load in Chromium under way, which it then takes out too if the links gate it; a load that starts later already counts the new links. It then waits until Chromium has switched all of it off (`EngineExtensions.waitForUnloads()`), since Chromium applies a switch-off only once the profile's extensions have loaded, after it has started the copies it kept. Only when every runtime has done so does the pass create or change the links. After the change, the pass reads the manifests behind Arch's links and in Chromium's system folder for the gate and calls `gateWidens` again when they refuse a caller that the gate did not count, as when a vendor adds an origin to a manifest behind a link that stays or a manifest to Chromium's folder, or a manifest no longer reads; Chromium may already read such a manifest, so this step comes after the fact. Removing a link needs no such step, since the gate counts Chromium's folder under Arch's links too. This covers a Persona that did not start the pass, such as one whose plugins did not change, and the first pass of a run in which a host is new.
- Held hosts: a host whose native app is known not to start for Arch is held. The pass keeps it in `hosts` with the reason, creates no link for it, and removes its own link under that name. For `com.apple.passwordmanager`, the pass asks `HelperLaunchConstraints` (Status) about the manifest's `path`, at most once per run, and holds the host while Arch meets none of the helper's parent launch constraints. When the constraints cannot be read, it holds nothing, since the helper enforces them itself. A held host keeps its reason in `hosts` also while the user's file takes its name in Arch's folder. So neither engine starts the helper only for macOS to refuse it. The pass also asks about the helper that a user's manifest under such a name names, for Settings, and keeps every answer of the run by the helper's path in `launchConstraintAnswers`, nil for constraints that do not read.
- A folder that cannot be read because of a permission error is skipped and listed in `unreadableFolders`, which Settings uses (see Status). A missing folder is skipped silently.
- `hosts` keeps the winners by name, with the manifest's `description`, its `allowed_origins`, the folder they came from, and whether the host is held and why, for the gate and Settings. `userHosts` keeps the user's valid manifests in Arch's folder by the same rule, for Settings. `linkedHosts` gives the names under Arch's own links with the `description` and `allowed_origins` of the manifests behind them, which it reads from Arch's folder and those manifests when no pass has run in the current run. A manifest without a `description` is named by its name. A link whose manifest does not read, as while its vendor writes it, has no `allowed_origins` there (nil), and the gate counts it as allowing every caller until a pass reads it. `hasLooked` says whether a pass has ended in the run.

## Proof gate

- The gate covers a name while Arch's folder has one of Arch's own links under it, and on Chromium also each name in Chromium's system folder (`NativeMessagingHostLinks.chromiumFolder`, which the session gets from `ChromiumEngine.systemNativeMessagingHosts`), where Chromium reads itself when Arch's folder lacks the name (Facts). There it counts every `<name>.json` with a valid name, whether a pass finds it valid or not, since Chromium reads it by its own rules, and also a name under one of Arch's links, since removing the link leaves the name to that folder. The gate reads that folder with Arch's links, at a profile's start before the run's first pass and at the end of each pass. A user's file under a name is what both engines read, so it gates nothing, even when a discovered manifest elsewhere or Chromium's folder has the same name. A version of an extension is gated when its grant has `nativeMessaging`, its package has no proof, and a manifest behind one of Arch's links or in Chromium's folder allows its identifier or does not read (`gatingHosts`).
- The gate's sentence names the manifest's `description`: "Arch cannot prove that this extension is the one that 1Password BrowserSupport expects. Install it from the Web Store or from its signed .crx file." For a version installed from a `.crx` file before Arch checked signatures, whose install entry has `source` (`docs/web-store.md`, Package proof), it is "Arch cannot prove that this extension is the one that 1Password BrowserSupport expects. It was installed before Arch checked signatures; install it again from its .crx file or from the Web Store."
- WebKit: for each message and port of a version without proof, `NativeMessaging` first checks whether Arch's folder has one of Arch's links under the name, or a pass is about to make one, and then refuses the version with the gate's sentence when the manifest it reads there allows it. A vendor's change to that manifest during the run counts at once. The version keeps running on WebKit tabs.
- Chromium reads the links and its system folder itself, so the gate acts on what Chromium runs. The load pass does not load a gated version in Chromium and takes it out where it is loaded, and the manager keeps the gate's sentence for the run as the version's failure on Chromium, as for a failure to start there. The version keeps running on its other engines; one that runs on no other engine goes off with that sentence, as one that failed on every engine does. A reinstall with proof, which is an update, clears the failure.
- As a Chromium profile starts, the runtime first unloads its gated versions by what the gate reads behind Arch's links and in Chromium's folder, so that a version the profile kept from an earlier launch stops before the load pass ends. Chromium applies the switch-off only once the profile's extensions have loaded, so under a link that stays from an earlier launch, such a copy runs from the profile's start until then; a link that a pass makes waits for it (Host discovery, Order).
- Before a pass creates or changes a link, and after one whose reading of the manifests behind the links or in Chromium's folder refuses more callers, each runtime takes the versions that the gate refuses out of Chromium in the same way (Host discovery, Order).
- Review: the review of a package that the gate would refuse under Arch's current links shows the gate's sentence in its Chromium line instead of refusing the package. Staging runs `update()` first.
- Pairs: a version without proof cannot join a proven counterpart under an identifier that the gate covers, so that a proven plugin does not appear to vouch for an unproven package; each version of an existing pair is gated on its own. Staging then offers no join, and Install \<Engine> Version… and Join With… refuse with "Arch can prove the identifier of only one of the two, and a native app on this Mac accepts the other's, so they cannot be one plugin."

## Installing Arch into /Applications

`scripts/install_app.sh`, after `scripts/bundle_app.sh`:

1. The source is `build/Arch.app`, or `ARCH_APP_SOURCE`. The script refuses a missing source with "missing \<path>; run scripts/bundle_app.sh first", and one that `signed_with_team` refuses with "1Password connects only to signed browsers. Set up a Developer ID Application or Apple Development identity, or set ARCH_SIGN_IDENTITY, then run scripts/bundle_app.sh again." `signed_with_team` reads `codesign -dv` output on standard input and accepts only a signature with a team, not an ad hoc one or none. The script prints neither the identity nor the team.
2. It refuses while Arch runs from the destination, as `ps` lists its executable there: "Arch is running from \<path>. Quit it, then run the script again."
3. `may_replace` allows replacing `Arch.app` in the destination only when it is missing, a symbolic link, or a bundle whose `CFBundleIdentifier`, read with `plutil`, is `xyz.taeyoon.arch`. Anything else stays where it is, and the script ends with "\<path> is not Arch (bundle identifier \<identifier>). Move it elsewhere, then run the script again.", or without the parenthesis when it has no bundle identifier.
4. `replace_app` copies the source with `ditto` to a temporary name in the destination and checks the copy with `codesign --verify --deep --strict`, so that a bundle changed after signing leaves the destination as it was, with "The signature of \<source> does not verify, so \<path> stays as it was. Run scripts/bundle_app.sh again, then run the script again." It then moves a link or an earlier bundle there to a second temporary name, moves the copy into place, and only then deletes what it moved aside: a link goes as a link, and an earlier bundle is a copy of an earlier build. If a step fails, `undo_replace` deletes the temporary copy and moves what it moved aside back, as a trap does when the script is interrupted; when the interruption comes after the copy took its place, it leaves what it moved aside under its temporary name and says so, rather than move it into the new bundle. When macOS refuses the change for lack of the App Management permission (`Operation not permitted`), the script adds "macOS kept the script from changing \<path>. Allow your terminal app in System Settings ▸ Privacy & Security ▸ App Management, then run the script again."
5. It prints the path of the copy in place.

The destination is `/Applications`, or `ARCH_INSTALL_DIR` for checks. With `ARCH_INSTALL_FUNCTIONS_ONLY=1`, sourcing the script defines `signed_with_team`, `may_replace`, `replace_app`, and `undo_replace` and runs nothing, for the checks under Tests. The Build Procedure adds `./scripts/install_app.sh` and `open /Applications/Arch.app` for password manager checks, and the README's Scripts table lists the script.

## Status and guidance in Settings ▸ Plugins

- A web extension plugin whose grant has `nativeMessaging`, on or off, lists its native apps in its section's footer, and for a pair, those of either version (`NativeAppGuide.lines(for:links:installation:outcomes:)`, which the section shows in order). Until a pass has ended in the current run, which the section starts (Host discovery), it says "Looking for native apps…". Then it lists, by host name, each manifest in Arch's folder (Arch's link or the user's file, `linkedHosts` and `userHosts`) or among the discovered hosts (`hosts`) that allows its identifier: a held host as "\<description>, which macOS does not start for Arch on this Mac."; else one in Arch's folder that allows it as "1Password BrowserSupport, set up for Arch."; else a discovered one, as when the user's file takes its name and does not allow it, as "1Password BrowserSupport, set up for another browser." Without one, it says "No native app on this Mac accepts this extension." Only in that case, when a folder could not be read, it adds "macOS kept Arch from reading another browser's native app setup." It names no folder, since the folders name other browser products.
- `ArchInstallation` reports Arch's location, the folder of its bundle after links, whether the bundle is directly in `/Applications` and is not a symbolic link, and whether it is signed with a team, without one (ad hoc), or unsigned. It reads signing information from `SecCodeCopySigningInformation` once per run (`ArchInstallation.current`) without showing or keeping the team. A plugin with a native app adds, after the native apps, "Arch runs from \<folder>; some native apps accept only browsers in the Applications folder.", with the folder under the home folder written from `~`, and "Arch is not signed by a developer team; some native apps accept only signed browsers." when those conditions hold.
- `NativeAppGuide` then adds, for each listed host name it knows:
  - `com.1password.1password`: "1Password connects to a browser it does not list only after you allow it. When 1Password asks about Arch, allow it, or add Arch in 1Password's settings for browsers."
  - `com.apple.passwordmanager`: "iCloud Passwords starts its helper only for the browsers that macOS lists, which come with macOS updates, and for browsers with Apple's browser passkey entitlement." `HelperLaunchConstraints` reads the helper's parent launch constraints from `codesign -d -vvvv` output, off the main thread and at most once per run, when a pass or the section first needs them. Arch meets them when its own signature, from `SecCodeCopySigningInformation`, matches one condition: a listed pair of signing identifier and team identifier, compared in memory and never shown or kept, or the entitlement condition, when its entitlements set `com.apple.developer.web-browser.public-key-credential` to true. It adds "Arch is among them on this Mac." or "Arch is not among them on this Mac." from `NativeMessagingHostLinks.launchConstraintAnswers` for the helper that Arch's folder names under the host name, else the discovered one. Unreadable output gives neither sentence.
- WebKit tabs: `NativeMessaging` records each plugin's last outcome during the run with the date of its install (`NativeAppOutcomes`, which the Persona's runtime gives as `nativeAppOutcomes`), so that an update or a reinstall, as one that brings a proof, starts without one, and the section shows it last: "On WebKit tabs, 1Password BrowserSupport answered." once the app sends a message, or "… ended without answering, as a native app does when it does not accept the browser." when it ends without one, or, for a held host, whose name has no manifest in Arch's folder, "On WebKit tabs, Arch did not start \<description>, which macOS does not start for Arch.", whose sentence without "On WebKit tabs," the extension also gets as its error, or the failure message, such as the gate's sentence. A port that the extension ends before the app answers records nothing. Arch does not see Chromium's native messages, so it shows no outcome for Chromium tabs.
- Settings ▸ Plugins shows one Persona's plugins, so these lines name no Persona; Arch's folder is shared by every Persona.

## Steps that need the user

### 1Password (IV.23)

1. Run `./scripts/bundle_app.sh` and `./scripts/install_app.sh`, then open `/Applications/Arch.app`.
2. Install 1Password from the Web Store in each Persona that needs it, with Install and Enable, and confirm with Touch ID.
3. When 1Password asks whether to trust Arch, allow it. If it does not ask, open 1Password's settings for browsers and add `/Applications/Arch.app`.
4. Unlock 1Password and fill a login on a WebKit tab and on a Chromium tab.

### iCloud Passwords (IV.24)

Either path makes macOS start the helper for Arch; Settings ▸ Plugins then says "Arch is among them on this Mac."

1. The passkey entitlement: not pursued. On November 23 the user decided to keep the individual team and the bundle identifier `xyz.taeyoon.arch`, and only an organization's Account Holder can request `com.apple.developer.web-browser.public-key-credential`, so passkeys stay limited to what each engine offers without it, and iCloud Passwords goes through Apple's list.
2. Apple's list (IV.24):
   1. Decide whether to publish Arch with an official website and a download link for a copy signed for distribution, as the pull request template requires.
   2. If so, fork `apple/password-manager-resources` and add this entry to `web_browsers` in `quirks/web-browser-extension-distribution-information.json`, with the team identifier from `codesign -d -vvvv` of the downloadable copy in place of the placeholder, and check its identifier against the entry's. The optional install path is omitted because Arch keeps extensions in each Persona's plugin folder.

      ```json
      {
          "long_name": "Arch",
          "short_name": "Arch",
          "supported_platforms": [
              "Mac"
          ],
          "platform_specific_information": {
              "Mac": {
                  "bundle_identifier": "xyz.taeyoon.arch",
                  "code_signing_identifier": "xyz.taeyoon.arch",
                  "code_signing_team_identifier": "<TEAM ID>"
              }
          },
          "supported_store_identifiers": [
              1
          ]
      }
      ```

   3. Run `tools/validate-json-schemas.sh`, open the pull request from its template, fill the web browser section with the name, website, download link, and the `codesign` output, and check only the statements that are true.
   4. After the merge, wait for a macOS update, then check iCloud Passwords as in IV.13.

## Tests

- Discovery (`ExtensionsTests`, `NativeMessagingHostLinksTests`, built), with temporary folders: a pass links each valid manifest, the first folder winning per name; it skips manifests whose name, type, path, or executable is wrong, files over 64 KB, and missing folders; it lists a folder it cannot read; it leaves the user's files and foreign links in Arch's folder; it replaces and removes its own links as the folders change; `update()` runs once per run and `update(force: true)` every time; a runtime without a `nativeMessaging` grant runs no pass; a held host gets no link and loses Arch's link, and a host with unreadable constraints is not held; `HelperLaunchConstraints` on output written for the test: a pair matching Arch's signing identifier and team, the identifier with another team, the entitlement condition with and without the entitlement in Arch's signing information, none, and unreadable output. Order, with two Personas and a recording Chromium engine: a host that appears during the run, and one that is new at the run's first pass, takes an unproven version under its identifier out of Chromium in the Persona that installed nothing before the link exists; removing a link does not wait for the runtimes. `BrowserSource.nativeMessagingHostFolders` names user and system folders (`ImportTests`, `BrowserSourceTests`).
- Gate (`NativeMessagingHostLinksTests`, built): on WebKit, a version without proof cannot reach a host behind Arch's link and gets the gate's sentence, while one with proof can, also once a vendor adds the version's identifier to the manifest behind the link with no pass after it; any extension can reach a manifest the user put in Arch's folder that lists it, also when a discovered manifest elsewhere has that name and allows it. A link whose manifest does not read gates every version without proof, and a pass that reads more origins behind a link that stays asks the runtimes again, which takes such a version out of Chromium. ## Risks

1. 1Password may require more than its text shows, such as the hardened runtime or a signature for distribution. The check records its requirements, and a later task changes the signing.
2. 1Password's approval list is tied to Arch's signature. A build signed with another identity is a browser 1Password does not know, and the user allows it again. `scripts/bundle_app.sh` signs with the team's Developer ID Application identity from the build after one appears on the Mac, in place of its Apple Development identity, so the user may need to allow Arch again then.
3. iCloud Passwords needs Apple's list, which needs a public Arch and a macOS update (the entitlement is not pursued). Until then it stays unavailable, and the Passwords app and its AutoFill remain the way to reach those passwords.
4. A vendor may install its manifest only in a folder macOS protects. Discovery then finds nothing, and the user must copy the manifest into Arch's folder by hand.
5. `build/Arch.app` and `/Applications/Arch.app` share the bundle identifier and the Application Support folder, and links from other apps may open either. Checks name the copy they open.
6. Apple may change the helper's constraints or how `codesign` prints them. Unreadable constraints hold no host, so the helper then decides itself, as before this design.
7. Chromium reads its own system folder whatever Arch links (Facts). The gate keeps versions without proof from what is there, but a held host's manifest there still reaches proven versions on Chromium, so Chromium may start a helper that macOS then refuses, and a vendor's change there counts for Chromium before the next pass reads it. An engine change in `arch-chromium` that points `chrome::DIR_NATIVE_MESSAGING` at Arch's folder or an empty one would close both.
