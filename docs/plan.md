# Arch Browser Development Plan

This plan gives the context needed to continue work in another session, on another Mac, or with a less capable model. Progress lives only here and in `docs/features.md`; there is no external context store.

## Goals

- Build a sidebar-first macOS browser with its own implementation. `docs/features.md` lists every planned feature and its status.
- Run no servers of our own. Use alternatives such as iCloud for features that need servers, including sync (`docs/features.md`, sections 5 and 8).
- Give both engines the same experience. Context menus, dialogs, sheets, find, downloads, extensions, and tools use the app's own interface and work alike whatever a tab's engine; only engine-drawn surfaces such as popups may differ. `docs/features.md` notes any feature an engine cannot support and why.
- Keep features lightweight. Delegate autofill to Apple Passwords or 1Password. Features use macOS facilities by default on both engines to fit macOS as closely as possible. Follow the Platform integration table in `docs/features.md`.
- Prefer public APIs. Use private APIs only behind flags on `flags://`. Check each API's availability quickly at runtime (see Decisions).
- Offer AI features through one AI interface. The user connects providers they subscribe to with an API key or a command-line tool in the built-in terminal. They choose a provider and model for each feature. Arch ships no model or provider account.
- Use ARCH prefixes throughout: `ARCH*` for packages, `Arch` for the app module, and `ARCHKit` for the core layer.
- The browser is for internal use. No distribution is planned. Manage replacement names, images, fonts, and similar items outside this repository.

## Approach

- Write new code for each feature. Start from a row in `docs/features.md`. Design the smallest module that delivers the feature and add it to `Package.swift`.
- Design type names, module boundaries, method signatures, and file layout for Arch. A row in `docs/features.md` describes what a feature does, not how to build it.
- Add engine protocol members only when a feature needs them. The current protocols are a starting point, not a list of requirements to implement.
- Build AI features on the AI interface and plugin system. This lets built-in features, hooks, and features that AI adds at run time use the same calls.
- The sidebar holds navigation, the address field, favorites, and tabs grouped by space. The window background shows the current space's tint. Nothing sits above the page. Only the code is written anew.
- Use the system framework whenever macOS provides the user experience. Do not build or retain an engine-specific version; for example, picture in picture on Chromium uses AVKit. Keep Chromium's existing native integrations. Route the remaining engine events to these frameworks and disable the engine's equivalent user interface.

## Current State

### Engine abstraction

`ARCHEngine` holds the protocols features use, and both adapters implement every member. Members no feature uses yet are queued for removal (I.19), except `executeJavaScript(_:inWorld:completion:)` and `postPageScriptMessage(_:toWorld:)`, which the page members of the plugins' context will call (V.11). `Engine.capabilities` lists the optional capabilities each adapter implements; the session reads it before starting an engine for web extensions. Both adapters route page events through `EngineWebContentsUIDelegate`; feature code implements only the callbacks it handles, and the defaults give the safe answer (dialogs dismiss, permissions deny). `ScriptMediaSession` gives both adapters one media session, and `EngineCaptureAccess` one camera and microphone check: a site's request for a device the system denies the app is denied without asking. When the user grants a request, the check asks for the system's permission before the page gets the device. It follows the media each document's script reports and shows the playing document, or otherwise the last to report. Between reports, it advances the position at the playback rate. `FaviconLoader` loads both adapters' site icons outside every profile's store, without cookies or stored credentials, so an icon request carries no Persona's sign-in and no cookie set by a response reaches any page. An icon a site shows only to signed-in users does not load. Because a page names its icon's URL, `FaviconLoader` loads only web and data URLs and drops a body past 1 MB, also one without a stated length, and a download not finished after 30 seconds. Both adapters report a link the user clicks with Shift and without Command to `EngineWebContentsNavigationDelegate` as a user-initiated `newWindow` action; the WebKit adapter asks the navigation delegate about every navigation, the Chromium adapter only about these links. `EngineWebContents.readableContent(limit:completion:)` returns the main frame's visible text (headings as `#` lines, list items as `- ` lines, paragraphs separated by blank lines), its address, title, `lang`, and the selection outside fields and editable areas. Both adapters run the same script, `EngineReadableContent.script`, which skips scripts, styles, templates, hidden and `aria-hidden` subtrees, the content of closed `details`, field values, and editable regions, follows open shadow roots and their slots, and stops at the limit. Page scripts (`EnginePageScript`) run in each new document of a web contents, from its configuration's list or, after `setPageScripts`, from the next document on, at document start or once the document is parsed, in the main frame or every frame. Each is a function expression that the engine calls with its world's channel: `channel.send(value)` passes the value as JSON to the `pageScriptDelegate` and returns a promise of the reply, and `channel.onMessage(listener)` receives what `postPageScriptMessage(_:toWorld:)` delivers to the main frame. `executeJavaScript(_:inWorld:completion:)` calls a function with a world's channel in the main frame, opening the channel if the document has none, and returns the string it returns. Both adapters hand the delegate an `EnginePageScriptReply`, which sends the first reply only and sends nil for a reply the delegate drops, so a script's promise always settles. A page that a web contents opens starts with its scripts. Engines that run Manifest V3 web extensions name their extension runtime's version (`Engine.extensionRuntimeVersion`) and give each browser context an `EngineExtensions` (Tier 2): the app checks a package without starting it (`check(_:)`), loads an extension's package with the API permissions and sites the user granted (`EngineExtension`), unloads it, deletes its storage, reads and runs its action for a tab, allows it on a tab's site where the engine kept it from running (`grantSiteAccess(of:for:)`, for an action whose `wantsSiteAccess` is set), and reports its windows with their tabs and the focused one (`setWindows(_:focusedWindowID:)`). The engine asks its `EngineExtensionsDelegate` to open a tab or a window, which completes once the app has reported it, activate and close tabs, show an action's popup (`EngineExtensionPopup`: a popover that the engine filled, as WebKit's, or a popup page's view that the app shows in a popover of its own), ask about access an extension requests while it runs (`EngineExtensionAccess`) and the engine's own questions (`EngineExtensionPrompt`: more access in the engine's sentences or a reload of a tab), and pass native messages and ports as JSON. It also tells the delegate when an action changes.

### WebKit adapter

`ARCHEngineWebKit` adds to its user agent the version tokens that full browsers on this system send; without them, some sites serve pages for old browsers. A script in its own content world reports whether each document's media elements play sound. It describes the last element to play sound, its position, and the page's Media Session metadata. A script in the page's world records the page's Media Session action handlers and runs them for the media keys. It reports and restores `interactionState` as a tab's restorable state, preserving the back-forward list and page positions. It enables element fullscreen, so the Fullscreen API moves the element into WebKit's own full-screen window, as in the system's browser.

It implements loading, reloading, stopping, back and forward navigation with the back-forward list, find with match counts (WebKit reports only whether a match exists; a script in its own content world counts matches in visible text and places the selected one), viewport snapshots, and full-page captures from `createPDF` drawn off the main thread at the window's backing scale (or lower to keep every side within 16,384 pixels), because `takeSnapshot` draws only what is on screen, PDF export (a paginated PDF on the system's default paper with the page's print styles, which WebKit's print operation saves without a panel, running modal for the window because `run()` never finishes for a web view; `createPDF` draws the whole page as one tall page and serves only a page outside a window), printing through the system panel, downloads with `WKDownload` (pause, resume, cancel), popups, page-initiated closing, favicons, and cookies. Every web view sits in a page view of its own and sets `isInspectable`, so the browser bundled with macOS can inspect it. While the private API flags allow it, ⌥⌘I opens WebKit's Web Inspector through the private `_inspector` object (`show`, then `attach`). WebKit attaches it beside the web view inside the page view and resizes the web view. The inspector stays with the tab across tab switches. Its toolbar docks it to another side or into its own window. Web views turn on developer extras (`_developerExtrasEnabled`), without which WebKit does not open the inspector, when they are made while the flags allow it and again before the inspector opens, so a tab made while the flags were off opens it too (needs verification, regression check 12). The page context menu still leaves WebKit's Inspect Element item out, as it holds only items both engines run (Decisions).

Its `WebKitWebView` subclass hands WebKit's context menu to the delegate in `willOpenMenu(_:with:)`, keeping only WebKit's own editing and spelling items (matched by tag), and learns the clicked link, image, and selection from a script in its own content world; menus a page element provides, such as a video's playback speed menu, and elements the script cannot see, such as those in a closed shadow root, keep WebKit's menu. It forwards JavaScript dialogs, HTTP authentication, links with schemes it does not load, media capture permission with the origin's port when it is not the default (after the system's own camera and microphone permission), and web content process termination to the delegate.

Each Persona's context has its own data store: the default Persona uses `WKWebsiteDataStore.default()`, and any other `WKWebsiteDataStore(forIdentifier:)` with the Persona's UUID, whose data, caches included, WebKit keeps in `~/Library/WebKit/xyz.taeyoon.arch/WebsiteDataStore/<uuid in lowercase>`. `removeStoredData` deletes such a store with `removeDataStoreForIdentifier:completionHandler:` at launch, before the engine starts. It deletes cookies accepted by a test through `WKHTTPCookieStore`. It removes other site data with `WKWebsiteDataStore.removeData`, using records that match the given origins' hosts, one per registrable domain. A closed page leaves its media presentations, pauses its media, and moves to a blank page without its delegates and observations, because a web view keeps its page as long as anything holds it. Neither its tab, whose closed-tab record keeps the page's address, nor the profile's extensions hear of the blank page.

Its navigation policy reports a link clicked with Shift and without Command, unless it is marked for download, as `newWindow`, as Chromium reads the click. It reads a page's readable text with that script through `callAsyncJavaScript` in its own content world. Page scripts run as `WKUserScript`s in a content world of their own per world, after a channel script that defines the world's channel there; a `WKScriptMessageHandlerWithReply` added only to that world carries the channel, and a world keeps its handler once added. The web contents' `WKUserContentController` subclass holds the page scripts. WebKit removes user scripts only all at once, so replacing page scripts adds the controller's other scripts again, telling them apart by a marker comment at the start of each page script's source. A popup uses its opener's content controller and so shares its page scripts. `executeJavaScript(_:inWorld:completion:)` runs the channel script first and then the function through `evaluateJavaScript(_:in:in:)`; `postPageScriptMessage` delivers through `callAsyncJavaScript`.

From macOS 15.4, the engine has the `extensions` capability, and each profile has one `WKWebExtensionController` (`WebKitExtensions`), which every web view of the profile, popups included, uses. Its configuration follows the profile's store: non-persistent for incognito, the default configuration for the default store, and otherwise `WKWebExtensionController.Configuration(identifier:)` with the store's identifier; extensions reach cookies in the profile's store. An extension loads as a `WKWebExtensionContext` whose `uniqueIdentifier` is the app's identifier for it and whose base URL is `webkit-extension://<identifier>/`, so its storage lasts across launches, with the granted API permissions and match patterns, inspectable from the browser bundled with macOS. Each web contents keeps a `WKWebExtensionTab` object for its lifetime, which answers from its web view and from the windows the app last reported and passes activating and closing to the delegate; its title, address, and loading changes reach the extensions. `setWindows` keeps a `WKWebExtensionWindow` object for each window while the window stays, lists only the profile's own web contents, and tells the controller, in this order, which windows opened, which tabs closed, opened, and moved to another window, which windows closed with the tabs that closed with them, each window's active tab, and the focused window, so a tab leaves a closing window before the window closes; a tab that only changed its place in a window is not reported. The controller delegate lists the windows with the focused one first, hands an action's popup over as WebKit's own `popupPopover`, which sizes itself to the popup and closes when the popup closes itself, for the app to show, and closes the popup when the app cannot, opens the tabs that extensions ask for, options pages among them, and windows with their addresses through the app, following only a window's addresses and focus, turns permission, address, and match pattern prompts into `EngineExtensionAccess` questions whose answers last while the extension stays loaded, and passes native messages and ports as JSON. WebKit loads an extension's page only in a web view made from the configuration the extension's context gives (`webViewConfiguration`), and loads no other page there. So a web contents that starts at a loaded extension's page, as a tab that `tabs.create` opens at `runtime.getURL(…)` or an options page does, starts from that configuration, and a web page that such a page opens in a new window gets a web contents of its own, without an opener. A web contents keeps its web view, so a navigation in place into or out of an extension's pages loads nothing, and a restored tab at an extension's page stays blank, since the extension loads after the tab (I.21). The navigation policy hands the `webkit-extension` scheme to WebKit rather than to other apps, so a page also loads an extension's web-accessible pages in its frames, as a password manager's menu. Content scripts run only in pages of a persistent store, because WebKit treats web views of a non-persistent store as private. `removeStoredData` also deletes the extension data records of the storage identifier; WebKit keeps a small state file for each extension it loaded there, which no public API removes.

### Chromium adapter

`ARCHEngineChromium` embeds a CEF browser (Alloy style) beside the sidebar through `CEFBridge`, with an external message pump on the main run loop and the `ArchHelper` subprocess. It implements loading, navigation with the back-forward list (from CEF's navigation entries; selecting an entry checks its URL against the menu's URL, stops any main frame navigation in progress, then calls the page's `history.go`, because CEF has no equivalent call and the DevTools protocol's call would leave a debugger attached), title, URL, and loading state, favicons from Chromium's icon URLs (Chromium reports them once a document finishes loading and never for a page back from the back-forward cache, so the icon stays while the tab stays on one host, also through same-document navigations such as `history.pushState`, until the next report's icon replaces it, which an earlier report's icon that loads later never does, and a page on another host starts with the icon that host's pages last showed in the tab, or with none), zoom level, popups as new tabs that keep `window.opener`, closing, restored tabs that load their last address (CEF cannot fill a back-forward list), the page's audible state and media (the helper's renderer process adds a script to each frame before page scripts run; the script reports media elements and Media Session metadata, records the page's action handlers, and runs them or plays and pauses the media through `ExecuteJavaScript` for the media keys), the page's theme color after each load (the helper's renderer process reads the matching `theme-color` meta and answers a process message; `ExecuteJavaScript` returns no value, and the DevTools protocol would attach a debugger), fullscreen requests from the Fullscreen API (CEF sizes the content; the app transitions the window and ends fullscreen with `ExitFullscreen`), the accessibility tree of every page while VoiceOver runs or while an assistive app asks for it by setting `AXEnhancedUserInterface` or `AXManualAccessibility` on the application (a private API behind flags), find with match counts, printing through Chromium's dialog, PDF export on the system's default paper (CEF's default is US Letter), viewport and full-page capture through the DevTools protocol's `Page.captureScreenshot` (`captureBeyondViewport` for the whole page), as images sized in points, a capture still waiting when the page's process quits or the browser closes ending without an image, downloads (pause, resume, cancel, refusal), media and permission prompts routed to the delegate (camera and microphone also ask the system, and a request for a device the system denies the app is denied without asking; Chromium stores its permission prompt's answers in the profile and reuses them without asking, so `setRememberedPermission` sets those content settings through `CefRequestContext::SetContentSetting` to match the app's remembered answers), and renderer crash recovery (one reload, then a blank page).

Closing a browser detaches its view in `DoClose`, so CEF never closes the app's window, also when the app has already released the browser object. Before that, the page gives up the window's focus and is muted, so a closed page is not heard while anything still holds its view. CEF creates and closes browsers on later tasks, so the bridge keeps each browser object, with its container view and CEF's view, from `CreateBrowser` until `OnAfterCreated` and from the app's close until `OnBeforeClose`, as it keeps a popup until CEF creates it; a close that comes before `OnAfterCreated` takes effect then, and releasing an open browser that the app did not close closes it. JavaScript `alert`, `confirm`, `prompt`, and `beforeunload` dialogs go to the delegate through `CefJSDialogHandler`, and closing a tab runs the page's `beforeunload` handlers first, except while the tab has a download in progress or interrupted: asking would mean closing the browser, which stops the download, so that tab closes at once, and its kept page answers its own handlers with Leave when it moves to a blank page. While the runtime runs, a page's own `window.close()`, or its opener's, does not close a browser that such a download needs: `DoClose` leaves the browser's view in place, so CEF keeps the browser open, and the delegate learns on the next turn of the run loop that the page closed itself. The bridge tells these closes from the app's own, which `close` and `tryCloseWithCompletion:` request. `CefContextMenuHandler::RunContextMenu` hands each context click to the delegate: the bridge copies CEF's parameters, shows the app's `NSMenu` from a run loop block once CEF's current work returns, so CEF keeps running while the menu tracks, and cancels CEF's request exactly once when the menu closes or the browser goes, so Chromium's own menu and commands never run. Its spelling and edit items run on the frame the menu opened on.

Cookies, stored data, and permission settings go through each Persona's request context (`ARCHCEFRequestContext`): the default Persona uses CEF's global context, whose profile is `Default` under the root cache path `Cache/Chromium`, and any other Persona a context whose profile is `Persona-<UUID>` beside it. Browsers use a new context at once; its cookie, storage, and permission calls wait in order until Chromium reports the context and its cookie store initialized. Browsers of different Personas never share a render process, and a popup keeps its opener's context. Chromium keeps a profile's HTTP and code caches at the same relative path under `~/Library/Caches`. `removeStoredData` removes nothing while CEF runs; at launch it renames a Persona's profile directories under both roots and deletes them in the background, and `makeApplication` deletes renamed leftovers before CEF starts.

HTTP authentication requests for sites and proxies reach the delegate through `GetAuthCredentials` as a `URLAuthenticationChallenge`, with a failure count the adapter keeps until a page finishes loading; the `disable-chrome-login-prompt` switch keeps Chromium's own sign-in window from taking them first. Navigations and popups to schemes Chromium does not load stop in `OnBeforeBrowse` and `OnBeforePopup` and go to the delegate as links for other apps.

Its developer tools open through `ShowDevTools` with a layer-backed container view of the bridge's as the parent view. Arch's engine fills the container with the DevTools front-end, in Chromium's docked mode without a DevTools browser and without the front-end's docking controls (an experimental CEF API, VI.3). The bridge reports the container when `HasDevTools()` is true right after the call, which CEF runs at once on the main thread. It reports the close at `CefLifeSpanHandler::OnDevToolsInViewClosed`, or at `OnBeforeClose` when the browser closes first and CEF does not report the tools' close. CEF holds only a raw handle to the container, so the browser's client keeps it until then, even after the browser object is gone. While the tools close, from when `HasDevTools()` turns false until that report, `showDevTools` does nothing. A discarded web contents reports its tools closed at once, because CEF's report may come after the web contents has gone. The tools pass the keys they do not handle to the inspected browser, so they reach the main menu as the page's keys do. At quit, the runtime first closes the tools in views and runs CEF's work until they report their close, then closes every browser and runs CEF's work until they close, for up to two seconds in all. It then shuts down. The tools go first because their front-end's contents would otherwise close on their own after their browser, unreported, while CEF shut down. Shutting down with browsers open crashed after Chrome-style developer tools had opened.

It deletes cookies accepted by a test by visiting the context's cookie manager and reports after that store flushes. It clears an origin's other storage with the DevTools protocol's `Storage.clearDataForOrigin` in a separate hidden browser of the same context. That browser then closes, so no tab keeps a DevTools client. The bridge turns off Chromium's own media key handling and Now Playing (`--disable-features=HardwareMediaKeyHandling`), which would use the same process-wide `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter` as the app.

`OnOpenURLFromTab` and `OnBeforePopup` ask the navigation delegate about a link the user clicked with Shift, which Chromium gives the new window disposition; a link the delegate allows loads in place, as Alloy style does, or opens as a popup. It reads a page's readable text through a process message to the helper's renderer process, which evaluates the script in the main frame's page world and replies with its JSON string (`evaluateScript:completion:`, which shares its evaluation with the theme color); a request without a reply ends after ten seconds, when the renderer quits, or when the browser closes. Page scripts run in the page's main world: the bridge passes them to the renderer in the browser's extra info, and in a process message to each of the browser's frames when they change and to each frame created after a change; each renderer keeps them per browser object. CEF does not order that message before the frame's first document, so in a renderer process that had none of the browser's frames, such as after a cross-site navigation, the first document may still run the scripts the browser was created with (needs verification). The helper's `OnContextCreated` makes the document's channel opener before the page's scripts run, so every channel, also one that `executeJavaScript(_:inWorld:completion:)` opens later, calls the built-ins as they were then. It opens each world's channel with a native function that it passes to the channel script as an argument, so it never reaches `window`, and runs the scripts before the page's own; channels keep their state in objects without prototypes, and document-end scripts wait for `DOMContentLoaded`. The page can still see the values a script sends and receives through built-ins it replaces, such as a `then` getter on `Object.prototype` for object replies. Values a script sends carry a request number unique in its renderer process; the browser answers through the sending frame. `executeJavaScript(_:inWorld:completion:)` shares the process message of `readableContent`, and `postPageScriptMessage` sends one to the main frame.

For a popup it does not stop, `OnBeforePopup` hands CEF a browser object of the bridge's own, with its own client, a container view of the opener's size, and the opener's page scripts in its extra info, and returns false, so CEF creates the popup in the opener's browsing context and request context, as CEF's sample client does on macOS. The page keeps the window `window.open` returns, and the popup keeps `window.opener`, which sign-in popups need to report back. `OnBeforePopup` stops a popup while the runtime shuts down, when the opener's `ChromiumWebContents` has no UI delegate to adopt it, as WebKit stops one, and for a Document Picture-in-Picture window, which would become a tab, so the page keeps its own interface. The bridge holds the object until the popup's `OnAfterCreated`, when the opener's `ChromiumWebContents` wraps it in a new one and reports it to the UI delegate with Chromium's disposition, or until `OnBeforePopupAborted` drops it. CEF owns a popup's page only once the opener shows the popup, which Chromium does after `OnAfterCreated` in the same task, and closing the popup before then crashes CEF, as CEF's `CreateInternal` and `AddNewContents` read the browser's released platform delegate. So a popup that the UI delegate dropped closes on the next turn of the run loop.

A video a page puts in picture in picture plays through AVKit in the system's window (VI.2). The bridge's client gives Arch's engine a picture-in-picture handler, so Chromium's own window never opens; the engine captures the video's frames into IOSurfaces and reports its start, with the video's place in the page, its playback state, and its end, all on the main thread. `ChromiumPictureInPicture` puts an `AVSampleBufferDisplayLayer` in a view below the CEF browser view, at the video's place in the container view, where the page covers it, and shows it through an `AVPictureInPictureController` as live content: play and pause only, no timeline, and no skip buttons. Each frame's IOSurface becomes a sample buffer without a copy, shown at once, with a clean aperture for the frame's content rectangle; the engine leaves a surface unchanged until three later frames have arrived. The window's play and pause button reaches the page's Media Session handlers or the video through `SetPictureInPicturePlaying`, and does nothing for a video the page offers no control for, such as a camera stream. Its close button ends picture in picture through `ClosePictureInPicture`, pausing the video unless the page offers no control, and its return button asks the UI delegate to show the tab (`webContentsDidRequestActivation`), then ends picture in picture without pausing. AVKit asks to restore the interface for every stop, also one the app requests, so that request counts as the return button only while the engine has not ended picture in picture. When the page ends picture in picture, navigates, crashes, or closes, or a video in another tab enters picture in picture, the adapter stops AVKit's session; a second video in the same tab replaces the first in the same session. Stops stalled in the prototype (`picture-in-picture.md` in `arch-chromium`, fact 29 and Risk 12): the controller's stop led to no delegate call while the layer's view was in no window, as a page's view is while another tab is selected, and releasing the controller's content source ended a stop only while the view was in a window. So before a stop that the engine asks for, the adapter moves a source view that is in no window to the top left of the content view of the app's front visible window that can become key, below the window's content, and a stop that has not finished a second after it began ends when the adapter releases the content source. This does not help while the app is hidden, where the prototype's stops stalled too. The prototype ran with the screen locked, and its stop checks have not run again with the screen unlocked, as the design's Order of work asks before the app commit: whether stops stall on a drawn screen, and whether the moved source view lets them end, is unverified (regression check 51). A new session immediately ends one still stopping, and a closed web contents stops its session, which keeps itself until it finishes. None of this has run in the app yet (regression checks 50 and 51).

Web extensions run in each profile's own Chromium extension system through the extension runtime that Arch's engine adds to CEF (an experimental API, VI.1), while every tab stays an Alloy style browser. `ChromiumExtensions`, which each context makes as it is created, loads an installed package unpacked from its folder, whose manifest's `key` gives it Arch's identifier, switches it on, and sets its host permissions to every site its manifest asks for when the grant has them all, comparing schemes and hosts in lowercase, or else to wait for a click, as for a pattern that no grant holds, such as one for `file:` pages or with a port; Chromium grants the API permissions the manifest asks for, which are those the install grants. Chromium keeps the extensions it loaded in the profile and starts them with it, so once the app says so (`stopUnloadedExtensions()`), after the runtime's first pass of loads or as the profile starts while the Persona has no enabled extension, the adapter switches off every extension that the app has not loaded or is not loading in the run as soon as Chromium lists it, and the first load in a run of a package installed before the engine started (`EngineExtension.installedAt`) that Chromium already has from the same folder and version keeps Chromium's copy instead of installing it again; later loads, and packages installed in the run, reload the package. Unloading switches an extension off, and deleting its storage uninstalls it. Chromium lets an unpacked extension reach `file:` pages, and Arch's engine does not turn that off yet, so an extension whose host permissions apply on every site also runs its content scripts on `file:` pages in Chromium tabs and can open them with `tabs.create` and `tabs.update` (VI.4). CEF's runtime has no call that reads a package without installing it, so `check(_:)` reads the files for what keeps Chromium's loader from running a Manifest V3 package: a manifest that does not read, a background of `background.scripts` or `background.page` alone, which Chromium leaves out of Manifest V3, and a service worker, content script, icon, or default locale file that the package lacks; anything else shows when the package loads. The extension runtime's version is the CEF version. Each reported window becomes a client window (`CefExtensionWindow`) that lists the profile's tabs in the window's order with its active tab and focus; CEF reads a client window's frame and state from an AppKit window it keeps for the window's life, while the AppKit window that shows a space changes and can be none, so each client window sits over a hidden stand-in window of the adapter's, which answers with the frame and the minimized, zoomed, and full screen state of the window that shows it at each question, never shows, and does nothing for `windows.remove` and focus requests. The bridge lists a browser once CEF has created it, answers a request for a tab once a window lists the new tab, and answers a request for a window once it lists every tab the app gave it, or with none when one of them closes first. Chromium's own windows, as `identity.launchWebAuthFlow` opens, get the bridge's default client, which logs and closes each one once CEF has created it, and shutdown waits for them. The popover reads the actions from CEF with their icons at the window's scale, including the disabled action that Chromium makes for an extension without one; a popup page's view reaches the app, which sizes it as the page asks, and the keys the page leaves reach the main menu; requests for tabs, windows, and prompts reach the delegate, and store install prompts are refused. Chromium's own native messaging reads host manifests from `NativeMessagingHosts` under the root cache path, which the engine links to the app's folder of that name before CEF starts while nothing is at that path (whether Chromium follows the link needs verification). None of this has run in the app yet (regression check 52).

Chromium keeps its cookie encryption key in the login keychain (item `Chromium Safe Storage`), which every build signed with the same identity reads without a prompt. Cookies that earlier builds saved under Chromium's mock keychain cannot be decrypted with that key, so Chromium sign-ins started over once.

### Private API flags

`ARCHPrivateAPI` keeps the private APIs registered by engines and features. Each API has an availability check that runs on a background queue when the API is registered, or at first use if it has not finished; a check at first use is recorded after that turn of the main actor, since the flags page asks while it draws. The result lasts until the app quits. The WebKit engine registers its APIs when it is created, so the flags page lists them before WebKit starts. Flags for all private APIs, each API, and each feature are on by default and saved in `UserDefaults`. A feature may use its APIs only while all its flags are on and every API exists. The Chromium engine registers the accessibility attributes that assistive apps set on the application when it starts.

### Browsing module

#### Window and sidebar

Each browser window shows the system's translucent sidebar material with a wash of its current space's tint, and a sidebar with a top row on the line of the window's traffic light buttons (the sidebar button, then back, forward, and reload, which becomes stop while a page loads; in full screen the sidebar button takes the traffic lights' place), the address pill, favorites, one page per space with its pinned tabs, its open tabs, and a New Tab row below them, and a bottom bar with the library button at its leading end and, centered on the sidebar independently of that button (shifted 2 points right for visual alignment), one symbol per space followed by a small, dim plus for a new space, 20 points apart; when they do not fit beside the library button, the symbols and the plus scroll sideways together. Three items appear at full size: the current space and its neighbors, or the three at the end nearest it. The others shrink with their distance from those three. While scrolling, items also start shrinking three items before either end of the strip so none is cut off. The strip centers the current space when it changes. Dragging the sidebar's trailing edge sets its width between 240 and 400 points; the width persists across launches. Hiding the sidebar slides it and the window buttons away and lets the page fill the window. The card appears only when the pointer next reaches the window's leading edge. The sidebar then slides in over the page as a card with 16-point corners; on macOS 15 and later, the window buttons slide in with it. The card hides when the pointer leaves, unless a menu, popover, sheet, or command palette opened from it remains open or the user is dragging one of its tabs, favorites, or space symbols. The card's sidebar button docks the sidebar in the card's position. The card stays above the page while the page narrows, then gives way to the docked sidebar. With no tab open, the controls stay, the address pill shows a placeholder and opens a new tab, and the page frame shows the window's material and the space's tint, slightly darker than the sidebar.

#### Dragging and dropping

Dragging a tab lifts it above the window so it follows the pointer anywhere, including outside the list. While the pointer is over the rows, they move aside, leaving a dimmed empty slot and giving a light haptic at each new position. On release, the tab returns to its slot wherever the pointer is. Its shadow and the slot's dimming fade in and out over 0.4 seconds. Dropping it among pinned or open tabs pins or unpins it. Releasing a tab over another space's symbol in the bottom bar, which lights up with a light haptic while the tab is over it, moves the tab after that space's own pinned or open tabs and shrinks the lifted row into the symbol; a selected tab takes the sidebar to that space. Favorites and space symbols drag the same way: the item lifts above the window, the others make room with a light haptic, and the order persists in `session.json`; only the symbol strip animates a space's move, so the current page stays in view. Links, files, and text that is an address, dropped from other apps or pages onto the favorites and tab list, open in new tabs of the current space in the default engine, in the order dropped, while a ring around the list shows where they land; other text and links with other schemes, such as `mailto:`, open nothing. A drag that reaches the window's leading edge while the sidebar is hidden shows the card.

#### Tab rows

Double-clicking a tab or choosing Rename Tab in its context menu renames it in place. An empty name or the page's own title restores the page's title; `session.json` stores the names. ⌘Z reopens the tabs the user just closed, newest first, until the user presses a different key or clicks in the page. The monitor compares each key with the current shortcuts of Edit ▸ Undo, Close Tab, Close Other Tabs, and Reopen Last Closed Tab, so it follows changes in Settings ▸ Shortcuts. Holding ⌘ alone for 0.2 seconds fades in the number from each tab's ⌘-number shortcut in place of its close button. Releasing ⌘ immediately fades the numbers out. Under the pointer, the close button appears instead. A tab row shows a speaker after its title while its page plays sound. A tab that a page opens behind the selected tab shows a dot in place of its close button until selected. This applies to links from the context menu's Open Link in New Tab and popups from unselected pages, which open in their page's space without taking the selection. Hovering a tab row shows its full title and address.

#### Spaces

The sidebar has several spaces, each with a tint. Each space has a menu, from the button beside its name and from the context menu of its symbol, to rename it (also by double-clicking the name), choose its theme (Automatic or one of seven colors) and symbol, move it left or right, add a space, and delete it; a deleted space's tabs move to its neighbor. A two-finger horizontal swipe over the sidebar, above the bottom bar, drags the space pages with the fingers and settles on the nearest space with a spring and a haptic at the halfway point; the switcher and the Spaces menu slide the pages the same way. Each space can have a home page. Set Current Page as Home in the space's menu stores the selected tab's web address with the space in `session.json`. Clear Home removes it. History ▸ Home (⇧⌘H) loads the current space's home page in the selected tab, or in a new tab when none is selected. It is disabled without a home page and under an internal page. Each space's theme is one of seven colors or Automatic. Automatic follows the accent color chosen in System Settings, including changes while the app runs; `session.json` stores the theme as the space's `tint`. The window resolves the current space's tint in its own appearance and washes the window material with it at the strength chosen in Settings ▸ Appearance. When the sidebar's text on that wash falls below WCAG's 4.5:1 contrast and the other appearance's text has more contrast, the sidebar and a dragged tab row use the other appearance. A space symbol whose tint contrasts less than 1.5:1 with the wash takes the sidebar's text color.

#### Folders

Folders group a space's pinned or open tabs. Each list starts with its folders, each followed by its tabs indented below it. Clicking a folder's row collapses or expands it; a collapsed folder still shows its selected tab. New Folder in the space's menu adds an empty folder among the pinned tabs, and Add to New Folder, Move to Folder, and Remove from Folder in a tab's context menu move the tab. A new folder opens its name field, and Rename Folder in its context menu renames it in place; an empty name keeps the old one. A tab dragged over another folder's row lights the row up with a light haptic and, on release, goes to the end of that folder, taking its pinned state, while the lifted row shrinks into the folder's row. Dragging a tab among a folder's tabs moves it into the folder, and among the tabs outside folders moves it out. Pinning or unpinning a tab, or dropping it on another space's symbol, takes it out of its folder. Delete Folder keeps the folder's tabs and puts them first among the tabs outside folders. A deleted space's folders move to its neighbor with its tabs. `session.json` stores the folders, their collapsed state, and each tab's folder; a reopened or restored tab returns to its folder while the folder is still in that list.

#### Split view

Split view shows two to four tabs of one space side by side in the page area, in panes of equal width 8 points apart. Tab ▸ Open in Split View (⌥⌘=) puts the selected tab in its space's split view or, without one, beside the tab selected before it. A tab row's Open in Split View opens that tab as a pane after the panes on screen. A tab dragged from the sidebar onto a pane opens before or after it, by the half under the pointer, which lights up with a light haptic. A split view started beside a tab shown alone replaces the space's earlier one. The page area shows a space's split view while one of its tabs is selected. The selected tab is the focused pane, marked by a ring in the space's tint, and a click in another pane selects that pane's tab. The address pill, the find bar, the question popover, the menus, the internal page, the region capture overlay, page fullscreen, and docked developer tools follow the focused pane; a sheet from another pane shows once the focused pane has none waiting. The other panes' rows show a lighter selection. Each pane's close control takes its tab out of the split view and leaves the tab open; on the focused pane it selects the pane beside it, or else another pane, that no other window shows. Closing the focused pane's tab selects the pane beside it, and a split view with one tab left ends. `session.json` stores each space's split view as tab indexes.

#### Windows

File ▸ New Window (⌘N) opens another main window on the active window's space, cascaded from it at its size, or centered at 1200×800 while it is in full screen, with no tab selected and the New Tab palette open. Each window has an empty unified toolbar, which gives the title bar the standard height of the system's apps and centers the traffic light buttons on the sidebar's top row, and hides it in full screen, showing it again, with the sidebar's top row back beside the traffic lights, when the window fails to enter full screen; AppKit's window tabbing and window restoration are off. Spaces, favorites, tabs, folders, split views, the closed list, and downloads belong to the app, and the sidebar's width is the same in every window. Each window has its own current space, selected tab, sidebar visibility, library, internal page, page fullscreen, command palette, find bar, renaming, region capture, tab switcher order, docked developer tools, preview panel, page reader, question popover, and sheet. Two windows can show the same space. A window shows its selected tab and, in a split view, the panes whose tabs no other window shows, because a page's view has one superview. Selecting a tab that another window shows, from a sidebar row, the palette, the switcher, a ⌘-number, Next or Previous Tab, or a favorite, moves the tab: the other window first selects its most recent tab that no window shows, or shows the empty page, or leaves the pane with a placeholder that has Show Here, which moves the tab back, and the pane's close control. Switching spaces, the selection after a tab closes, a new window, and restore never take a tab that another window shows. Page commands act on the browser window that last became main, also while Settings or History is key; sidebar commands act on the last main window, or open one while none is open. File ▸ Close Window (⇧⌘W) closes a window and keeps its tabs, and ⌘W in a window with no tab selected closes it while another browser window is open. Closing the last browser window quits, unless Settings, History, or the tab close log keeps the app running; a Dock click, the global shortcut, History's Open, or a link then opens a main window as the last one was. A window's hidden title, which the Window menu and Mission Control show, is its selected tab's title, or its space's name with no tab selected. `session.json` keeps the open main windows, front to back, each with its ID, frame outside full screen, space, selected tab, and sidebar visibility; frames save as windows move and resize, and after the last window closes, `session.json` keeps that window. At launch the windows open back to front, so that the front one becomes key, each on its selected tab, or on its space's first tab that no other window shows when that tab has closed. A window that was in full screen opens at its frame from before, a frame that reaches less than 100 points across or down onto every screen opens centered on the main screen at its size, at most the screen's, and a file from before windows were saved opens one window centered at 1200×800 on its selection.

#### Small windows

While Settings ▸ General allows it, a link that another app sends while Arch is in the background, or less than 0.5 seconds after Arch became active, opens in a small window, which comes forward alone: 900×640 and at least 480×360, the first centered on the screen with the pointer and later ones cascaded from the last. Its one row, on the line of the traffic light buttons, has the page's icon and site, which open the palette to edit the address, then back, forward, reload or stop, share, and Move to Main Window, and the page below it lies over the window material with the tint of the tab's space: the last main window's current space when the small window opens, or the last closed main window's, or the first space, in that space's Persona, with the default engine. That space's list, ⌘-numbers, the tab switcher, the palette, Close Other Tabs, the selection after a tab closes, and archiving leave the tab out. Find, sheets, page fullscreen, the docked developer tools, the page reader, the question popover, the preview panel, and the palette work in the small window, but its palette lists no tabs; sidebar commands act on the last main window, which comes forward, and ⌃Tab goes to the page. A page that the small window's page or preview opens, and the preview's Open in Tab, open in another small window. Move to Main Window, from the button or Window ▸ Move to Main Window (⌥⌘N), puts the tab at the end of its space's open tabs and selects it in the last main window, which comes forward with the page focused; the small window closes, and the page moves without loading again. Closing a small window closes its tab into the closed list, after the page agrees, and a small window closes with its tab, which cancels a print or save panel on it; a download's save panel opens as a panel of its own over a small window. `session.json` keeps no small windows; their tabs are saved as open tabs of their spaces. Links that arrive during launch or while Arch is active open as tabs of the main window.

#### Engines, Personas, and cookies

Each tab has its own engine: tabs from the palette, favorites, and other apps' links use the default engine, tabs a page opens use that page's engine, and `session.json` (snapshot version 12) records each tab's ID, engine, and that engine's restorable page state, and each open tab's suggested title. It also records the Personas and the Persona of each space, favorite, and tab record; a file from before version 9 loads into the default Persona, `Persona.defaultID` (`D59DAF4B-E372-4AF9-890E-455B8B3860F3`). Personas partition the sidebar: every space, favorite, tab, and closed-tab record belongs to one, a tab keeps its Persona for life, and each Persona has its own profile in each engine and its own plugins. New Persona…, Rename Persona…, and Delete Persona… in the space menu and the Spaces menu ask with a sheet on the window; an empty name changes nothing, and New Persona adds a Persona with one space named Personal and shows that space. With the default Persona alone, nothing names Personas. With two or more, the bottom bar groups the space symbols by Persona with a 1-point divider between groups, each space's header shows its Persona's name above the space's, the window title ends with " — " and the window's Persona, and the Clear Site Data sheet names the Persona. The favorites grid shows the window's Persona's favorites and cross-fades when the window moves to another Persona's space; swipes and Next and Previous Space cross into the next group. A tab moves only to a space of its Persona: another Persona's space symbol does not light up under a dragged tab and refuses its drop. Move Left, Move Right, and dragging a symbol stay within the space's group, Delete Space is disabled for a Persona's last space, and New Space adds the space at the end of the window's Persona's group. The palette and the tab switcher list only tabs of the window's Persona, and palette commands run through its plugins. A page that a page or a preview opens joins a space of the page's Persona: the window's current space, or else the last main window's while it belongs to that Persona, or else the Persona's first space; Open Link in New Tab from a favorite's page does the same. Delete Persona…, disabled for the default Persona, says what goes and asks first. Then every main window on the Persona's spaces moves to the first remaining Persona's first space, its tabs close into the closed list without asking their pages, which closes its small windows, its unfinished downloads stop and the pages kept for them close, its spaces, folders, split views, and favorites go, its browsers close, its plugins stop, and its web extensions leave the engines, and its ID joins `removedPersonaIDs`, which saves at once. Its runtimes stay without tabs until quit, because download rows refer to their profiles. A reopened tab whose space is gone opens in its Persona's preferred space, or in the sidebar target's current space once its Persona is gone. At the next launch, before any engine starts, the session deletes the Persona's `Plugins/<UUID>` folder and its plugins' Keychain items and has both engines remove its storage; the ID stays listed until both report removal, and its plugin data goes first. Cookies are copied between the two engines' profiles of one Persona, never to another Persona's, so a site stays signed in, and signed out, on both engines: into an engine when it starts after the other and before a tab switches to it, from WebKit as its cookie store reports changes, and from either engine after its pages finish loading. Copies run one at a time. A copy carries what the source changed since the two stores last agreed, a record `CookieSync` keeps in memory: the cookies the source added or changed, and the deletion of those it removed, so a sign-out in one engine signs the other out too. A cookie only the target changed stays and travels with the next copy the other way, so an older value never replaces a newer one; when both engines changed one cookie, the source's version wins, but a deletion leaves a cookie the target changed. The first copy between the two engines in a launch has no record: it writes the cookies the target lacks or holds with other contents and deletes none, so a cookie deleted in one engine while the Persona's other engine was not running can come back (I.20). A copy keeps each cookie's `SameSite` policy as far as the target store holds it: WebKit keeps Lax and Strict but no difference between `SameSite=None` and no policy, both of which it sends with requests from other sites, so such a WebKit cookie reaches Chromium as `SameSite=None` when it is secure and with no policy (Lax to Chromium) otherwise. A copy writes only the cookies the target lacks or holds with another value, flag, or expiry, so a Chromium cookie without a policy that comes back from WebKit unchanged keeps no policy in Chromium; one that a WebKit tab changes reaches Chromium as `SameSite=None` when it is secure.

#### Saving and restoring

Tabs keep their IDs across launches: a restored or reopened tab comes back under its saved ID. At launch every restored tab of a space creates its page and loads it at once, while a favorite's tab waits for its first click; III.14 loads only the tabs that windows show. The session saves half a second after the last change to what `session.json` keeps, and after each finished load; a tab's loading state, icon, sound, and crash notice save nothing. The snapshot is taken on the main thread, and `SessionStore` encodes and writes it on a queue of its own; quitting writes it before the app ends. The session keeps its files in the folder the app gives it, the app's Application Support folder (`userDataDirectory`): `session.json`, Chromium's profiles, the plugins, the browser import's `imports.json`, and, through the stores it makes there, `history.sqlite`, `permissions.json`, and `site-search.json`, which Settings, the History window, the palette, and imports reach through the session. Spaces, favorites and their tabs, tabs, folders, split views, the closed list, and the main windows persist in `session.json`; quitting keeps the open tabs because the bridge does not report the browsers that close when the runtime shuts down. A `session.json` that does not decode moves to `session.unreadable.json`, so the fresh session never overwrites it, and a file from a newer build first leaves a copy, `session-v<version>.json`.

#### Tabs

Tabs open, close, pin, reorder, switch, and reopen; unpinned tabs not activated for a configurable number of hours are archived to the closed list by a timer and at restore. Both count the tabs windows show as active: the timer when it runs, and each save, which records them as active at that moment. The closed list keeps the newest 100 records, without page state, activation dates, or hooks' names; a file from an earlier build loses them at launch. Popups become tabs, selected in the window that shows the page that opened them; `window.close()` closes the tab, and the window then selects the tab of the page that opened it, as a sign-in popup closes once it has reported back, while that tab is listed and no other window shows it. A page cannot bring a tab it opened forward, as with `focus()` on the window `window.open` returned or `window.open` with that window's name: CEF's Alloy style ignores Chromium's `ActivateContents`, and `WKUIDelegate` has no such callback. A page whose process quits and does not come back (WebKit at once, Chromium after its one automatic reload) is covered by a notice with a Reload button; the session is the engines' application delegate and keeps their crash count for the tab close log. A tab that opens straight onto a file closes, without a closed-list entry or a history visit, once the download its own page started appears; another such tab waits for its own download, which closing it earlier would cancel. A restored tab like that does not download the file again.

#### Favorites

Favorites are shared by all spaces of their Persona. The first click on a favorite opens a tab of its own in the default engine; the tab stays out of every space's list and is never archived, and a dot below the tile marks the favorite as open. Later clicks, from any space, select that same tab, so its page keeps its state across space switches; switching spaces selects the space's own tab and leaves the favorite's tab open behind it. Links and popups that the favorite's page opens in new tabs go to a space of its Persona: the current space of the window that shows it, or the Persona's preferred space. Close in the tile's context menu, ⌘W, or the page's `window.close()` ends the tab, which then opens again at the favorite's address; ⌘Z does not reopen it. Remove from Favorites closes the tab first, and a page's `beforeunload` handler can keep both. While a favorite's tab is selected, Pin or Unpin Tab, Move Tab Up and Down, Next and Previous Tab, and Close Other Tabs are disabled. `session.json` keeps each favorite's tab (address, engine, and restorable page state) and whether it was selected: at launch the selected one opens, and the others keep their dots and load where they were on their first click.

#### Preview panel

Holding Shift alone for 0.25 seconds while the pointer rests on a favorite, or clicking a web link in a page with Shift, shows the page in a floating preview panel over the page area, with its title and site, Open in Tab, and Close above it. A favorite previews in the default engine and a link in its page's engine. The panel's web contents belongs to no tab: the page never enters the tab list, `session.json`, or history, cannot download, and asks nothing (dialogs and sign-in requests get the safe answers, and permission requests are denied, after which Chromium's kept answers return to the remembered ones). Open in Tab loads the page the panel shows in a new selected tab of the same engine; a page the preview opens, such as a link to a new window or a sign-in popup, becomes a selected tab in place of the panel, after the previewed page, which becomes a tab without loading again, so the opened page keeps its opener. Escape (unless a field of the app's own, such as the palette's or the find bar's, has focus), ⌘W, or a click anywhere outside the panel, which still reaches what it hit, closes the panel and its web contents, except a page that has just become a tab.

#### Share and site settings

The share button before the site settings button in the address pill and File ▸ Share… show the system share picker (`NSSharingServicePicker`) for the selected tab's address. Its preview shows the page's title and icon. Services that take a subject, such as Mail, get the title. The picker opens below the button, or from the top of the window while the sidebar or the library hides it. Internal pages and windows without a tab have nothing to share. The site settings button at the end of the address pill opens a popover that switches the current tab's engine, loading its page again in the other engine in the same place, and sets the engine for new tabs. Below the engine, it lists the actions of the enabled web extensions of the tab's Persona with their icons, labels, and badges for the tab, a pair once with the action of the version that the tab's engine runs, dimmed on a tab of an engine without extensions, where the note says on which engines' tabs extensions run; an extension that Chromium kept from the tab's site offers Allow on This Site, which allows it there; on a tab whose engine runs extensions but none of a plugin's versions, the row says where the plugin runs and, while the plugin asks for that engine's version, offers Install <Engine> Version…, which opens Settings ▸ Plugins at the plugin with the open panel through `installEngineVersion`, which the app shell sets, and Dismiss; a click closes the popover and runs the action, and an action's popup shows from the site settings button of the window that shows the tab, or from the top of the window while the sidebar or the library hides the button, through `ExtensionPopupPresenter`: WebKit's own popover, or Chromium's popup page in a popover of the presenter's, sized as the page asks between 25 × 25 and 800 × 600 points and closed with it.

#### Web extensions

Each Persona's plugin manager runs its web extensions through a `WebExtensionRuntime` that the session makes with the manager, keeps in the Persona's `PersonaEngines`, and drops with it; its native messaging host manifests are in `NativeMessagingHosts/` in the app's Application Support folder. `SessionWebExtensionHost` gives the runtime the Persona's profiles in the engines with the `extensions` capability, starting them if they have not started, and reports the Persona's spaces and small windows as the extensions' windows on the next turn of the run loop after the spaces, the tabs, a tab's engine, space, pinned state, or folder, or a window's space, selection, or order change: each space's tabs in sidebar order, after the open favorites' tabs that a window shows on it (a favorite's tab that no window shows is in the Persona's first space); its active tab is the one a main window shows there, or else the one selected last; each small window is a window of its own with its one tab; and the window that last became main is focused when it is the Persona's, as the small window itself or a main window's space. An extension's `tabs.update` selects the tab in the window that shows it, or else in the front main window that shows its space, or else in the last main window, `tabs.remove` closes it into the closed list, and its questions about access and the engines' prompts show as sheets on the tab, or on the selected tab of the window that last became main for a question without a tab. A tab that an extension opens, with `tabs.create`, an options page, or a link its popup opens, opens in the asking engine in the space of the window it names, or else of the Persona's focused window, or else the Persona's preferred space: before the tab at the asked index among that window's tabs of the engine while that one is an open tab outside folders, else after the window's active tab while that one is, else at the end of the space's open tabs, selected when asked; the host reports the windows at once. `windows.create` opens a small window with its page, or the new tab page for none, as its one tab, which belongs to the Persona's focused space or its preferred one, and leaves the window that was key in front when it does not ask for focus; extensions see a new window that lists only that tab, and a request for several pages opens none, since a small window holds one tab. A tab that an extension asks for in a small window opens in that window's space.

#### Command palette and site search

The command palette (⌘L edits the current address, ⌘T opens a new tab) accepts URLs and search queries, which go to the search engine chosen in Settings. A file address loads as typed, so Return on the address of a file dropped on the tab list reloads the file instead of searching for its path. Site search keeps keyword shortcuts in `site-search.json` in Application Support. It writes four defaults (`yt`, `w`, `gh`, and `m`) when the file is missing. A file that does not decode leaves the defaults in memory and moves to `site-search.unreadable.json` at the first write, so that neither Settings nor an import overwrites it. Palette text that starts with a keyword, ignoring case, and a space shows a Search <site> for "…" row. Return opens the site's results page with the percent-encoded query in place of `%s`. With only the keyword and space, it opens the search page without a query. A keyword whose template, edited by hand in the file, makes no web address searches the web for the whole text instead. The palette also lists matching plugin commands and open tabs of the window's Persona, and history suggestions. Up to five commands of the enabled plugins of the window's Persona (its current space's) follow the primary row, each with its symbol and its plugin's name. A command matches when every word of the typed text starts a word of its title or keywords, ignoring case and diacritics. Clicking one closes the palette and runs it on the selected tab, or on no tab while an internal page or the preview panel covers it or the tab belongs to another Persona, as a favorite's tab can. The palette has a glass capsule search field and, once the field has text, a glass results panel below it. Before macOS 26, both use the system material. The address pill sends the palette out along the line from the pill in 0.32 seconds. Meanwhile, the whole pill moves the same way and fades out. It returns when the palette closes. The New Tab row slides the palette in from the sidebar's side in 0.32 seconds; a shortcut raises it from below in 0.16 seconds. It animates its own arrival so its contents move with it; the palette and its dimming fade out together in 0.2 seconds when it closes. Selecting another tab closes it, as when a link from another app or Move to Main Window selects a tab. Each window builds a hidden palette as it opens so the first opening animates like later openings.

#### Plugins in the sidebar, menus, and pages

Below the favorites, the sidebar shows the sidebar items of the enabled plugins of the window's Persona, each with its symbol, its title, the badge its plugin sets, and its plugin's name in its tooltip; a click runs its command on the selected tab or opens its plugin's panel in a popover beside the row, which lets the panel go when it closes, and a second click closes it. A tab row's context menu and the space menu end with the plugins' items for them, one section per plugin under its name; a tab row's item runs on that tab, and a space menu item runs with the space, on the selected tab while it belongs to the space's Persona. The page context menu adds, after the app's own items, the items of the tab's Persona's plugins for what the user clicked on, which they receive with the tab. Each tab's pages run the page scripts of its Persona's enabled plugins: the session passes them to every web contents it creates for a tab, a tab takes them again when it joins the session, and every tab of the Persona takes new ones when a plugin is switched on or off, from its next document on. The values the scripts send reach the plugin manager through their tab.

#### Internal pages, find, and page fullscreen

Typing `flags://` in the palette opens an internal page over the page area. It shows the switch for all private APIs, whether this system has each API, and whether each feature is active. Close, Escape, ⌘W, selecting a tab, Back, Forward, or going to another address leaves it. While it is open, the address pill shows its address, keys do not reach the page under it, and Reload does nothing. The find bar floats over the top trailing corner of the selected tab's page (⌘F, ⌘G, ⌘⇧G, Escape). A Chromium page that enters fullscreen fills the window without the sidebar or margins and takes the window into full screen. Escape, selecting another tab, closing the tab, or leaving the window's full screen ends it. The window leaves full screen with the page if it entered for that page; a page that ends fullscreen while the window is still entering takes the window out once it is in.

#### Library and downloads

The library button (⌘⇧J) pushes the whole sidebar aside. The column widens by 76 points, and the library takes the sidebar's width, with downloads at the top, followed by Reopen Closed Tab and Settings. #### Permissions, sheets, and dialogs

A sheet asks before a site gets a permission such as the camera; the system's own camera and microphone prompt follows. Arch remembers Allow and Don't Allow per origin (scheme, host, and a port other than the default) and permission type in `permissions.json`. The sheet says so. Arch grants a request without a sheet only when every type in it has a remembered Allow. One remembered Don't Allow denies it without a sheet. Screen recording and pages without an http or https host always ask. Arch does not remember a sheet closed without an answer, as when its tab closes. Identical requests from one tab that arrive while their sheet waits share its answer. The session's `SitePermissionAnswers` copies the remembered answers into each engine's profile when the engine starts, after every change, and after each answer, so an answer the user did not give does not stay with the engine. `permissions.json` also lists the answers removed in Settings ▸ Websites until a new answer replaces them, and a profile that starts takes those away too, so a profile that was not running at a removal asks again. Permission and page dialog sheets wait in a queue per tab, and each window shows one at a time for the tabs it shows, its selected tab's first, once no other sheet, such as a Persona's name prompt or the print panel, is on the window; closing a tab gives its waiting sheets the safe answer. JavaScript `alert`, `confirm`, and `prompt` show sheets titled with the page's host on both engines. When the user reloads, goes back or forward, or loads another address while a page dialog is open, the dialog gets its safe answer and closes, and the page cannot open another until that load ends; Back or Forward without an entry leaves the dialog open. Such a cancellation ends only the page's own dialogs: a permission, sign-in, leave-page, or other-app question stays. A sheet put away because its tab left the window, as when a link from another app opens a tab or another window takes the tab, shows again first when a window shows its tab. Closing a tab on the Chromium engine asks with a leave-page sheet when the page's `beforeunload` handler wants to stay, unless one of its downloads is in progress, paused, or interrupted, when the tab closes at once; WebKit has no public `beforeunload` callback, so its tabs close at once. Quitting gives every open and waiting sheet its safe answer, so no sheet holds the app open. When a site or proxy asks for HTTP authentication, a sheet asks for a user name and password on both engines. It names the site's realm, says when the last attempt failed, warns when the connection is unencrypted, and keeps the credential in memory for the session only.

### Plugins module

`Plugins` holds the parts of the plugin system in `docs/plugins.md` built so far. A built-in plugin is a Swift type that conforms to `BuiltInPlugin` and declares a `PluginManifest`: a reverse-DNS `PluginID` (at least two dot-separated labels of ASCII letters, digits, and `-`, at most 128 characters, lowercased so that identifiers that differ only in case name one plugin and one folder), a name, a version, a summary, the permissions it asks for (`tabs` and `clipboard` so far), the sites it may reach as match patterns, and its contributions: commands, menu items, sidebar items, settings, and page scripts. A `MatchPattern` is `scheme://host/path` or `<all_urls>` and covers http and https addresses only: the host is `*`, a name, or `*.` and a name for its subdomains too, a pattern covers every port, and each `*` in the path matches any run of characters of the address's path and query. A command can have a `PluginShortcut`, written like `ctrl+opt+r`: the modifiers `ctrl`, `opt`, `shift`, and `cmd`, each at most once, and a key (a printable ASCII character other than `+`, `plus`, `space`, an arrow, or `f1` to `f20`), with `cmd` or `ctrl` unless the key is a function key.

The app passes its built-in plugin types to the session, which creates a `PluginManager` for each Persona when a tab or window of the Persona first needs it and keeps it in the Persona's `PersonaEngines`, with its files in `Plugins/<persona id>/` in the app's Application Support folder. The manager gives built-in plugins everything their manifests ask for and enables those that are on by default, except the plugins the user switched on or off in that Persona, which `plugins.json` records (a file that does not read or decode moves to `plugins.unreadable.json`). Its `PluginContributionIndex` holds the enabled plugins' palette commands, their menu items for each location in one section per plugin, with titles falling back to their commands' (a command with a shortcut and no item in the Plugins menu gets one there, and only the first of its items there has the shortcut; a page context item shows when the click has one of its contexts, where `page` means no link, image, media, selection, or field), their sidebar items, and their page scripts. The manager starts a plugin's code on its first command, panel, or page script value: it creates the plugin and activates it with a `PluginContext` scoped to the plugin, its grant, its storage, and its secrets. Uses that arrive during activation wait for it, and a failed activation starts again at the next use. Switching a plugin off drops its contributions and badges and calls its `deactivate()` once its activation ends; switching it on again starts a new instance. An instance's context stops acting when the plugin is switched off, its Persona is deleted, or the activation fails: its storage and secrets only read, its other actions throw `stopped`, and its badges do nothing. Deleting a Persona closes its manager (`close()`): its plugins leave the list, their running instances stop, and storage changes not yet written to the files are dropped; from then on it stages, installs, and stores nothing, and throws `PluginError.closed` for such calls, as for a review whose install waited for Touch ID. The next launch's removal pass calls `PluginManager.removeData(ofPersona:in:)`, which deletes the Keychain items of every plugin whose account starts with `<persona id>/` and the Persona's `Plugins/<persona id>/` folder before any manager of the Persona exists. The invocation's tab carries its title and address only when the grant has `tabs` or its sites cover the page; a page context menu item's link, image, and selected text and a space menu item's space pass as they are. The context throws `permissionDenied` for calls the grant does not cover, reads the plugin's settings (the user's value, or the default for one the user has not changed or whose stored value no longer suits its field), and sets badges on the plugin's own sidebar items. A failed command beeps. `Plugin.panel(for:)` gives a sidebar item's panel each time the item opens it.

Each plugin's storage keeps JSON values (`PluginValue`) by key in `Plugins/<persona id>/<plugin id>/storage.json`, up to 5 MB counted as the bytes of each key plus the JSON of its value; a write that grows it past the limit throws `quotaExceeded`, and a value JSON cannot hold, such as one nested more than 510 levels deep, throws an encoding error. Changes reach the file atomically 0.5 seconds after the last one, or 5 seconds after the first one that has not reached it while changes keep coming, and at quit. A file that does not read or decode moves to `storage.unreadable.json`, and the plugin starts empty. Setting values live in the same file under keys that start with `arch.setting:`, which the plugin's own storage refuses with `reservedKey` and leaves out. Secrets, secret settings among them, are generic passwords in the login keychain with the service `xyz.taeyoon.arch.plugin.<plugin id>` and the account `<persona id>/<key>`, up to 64 for a plugin in a Persona and 16 KB each; a longer secret or a new key past the limit throws `quotaExceeded`.

The built-in Page Address plugin adds Copy Page Address, which copies a tab's address, with ⇧⌘C, in the Plugins menu, in the page context menu on the page itself, and as Copy Address in a tab row's context menu for that row's tab, and a setting that copies a Markdown link of the title and address instead.

A built-in plugin's page scripts (`PluginPageScript`) carry their JavaScript, their match patterns, when they run, and whether they run in every frame. The index gives the engines the scripts of the enabled plugins, each plugin's in its world `ARCHPlugin.<plugin id>`. Each script's function first checks the document's `location` against the script's patterns and the plugin's granted sites with a JavaScript copy of `MatchPattern.matches(_:)`, which calls no built-in function and reads only own properties, so built-ins a page replaced cannot change its answer. Then it runs the script as the body of a function with the world's channel as `arch`. A script whose source does not parse as a function body on its own, which JavaScriptCore checks through the `Function` constructor without running it, is left out, so no source can close that function and run outside the check. `PluginManager.receive(_:from:)` passes a value a page script sent to `Plugin.receive(_:)`, starting the plugin first if it has not started, while the plugin is enabled and its granted sites cover the sending frame's document, with the tab redacted for the grant, and returns the reply as JSON. A page script can also list `excludes`, patterns it skips although its `matches` cover them, which the guard and `pageScriptsCover(_:of:)` apply.

Script plugins are packages with `plugin.json` (`docs/plugins.md`, Keys the script runtime reads). `PluginManager.stage(_:)` copies a folder, or extracts a `.zip` archive with `ditto`, or the `.zip` archive after the header of a `.crx` file of format version 3, whose public key it writes into the `manifest.json`, over a `key` the manifest has, as Chromium does (`CRXArchive`; the signatures are not checked), into `Plugins/<persona id>/Staging/<UUID>/` off the main thread and reads it as a `PluginPackage`: its manifest, its background script's path, its page scripts from their files, and its files. It refuses, with `PluginError.invalidPackage` and a sentence that names the field, a package without `plugin.json` at its top or in an archive's only folder, invalid JSON, a key the runtime does not read, a permission `PluginPermission` lacks, commands without a background script, menu or sidebar items that name unlisted commands, repeated identifiers, settings whose defaults do not suit them, paths that leave the package, page scripts that are not function bodies on their own, symbolic links, a built-in plugin's identifier, an identifier under `xyz.taeyoon.arch.` other than `xyz.taeyoon.arch.generated.`, which Arch keeps for its built-in plugins, an identifier that starts with `local.arch.browser.` or `local.arch.generated.`, which `PluginIdentifierMigration` renames at launch, and `plugins.json` or `plugins.unreadable.json` as an identifier, whose folder would take that file's name; a newer `apiVersion` throws `unsupportedAPIVersion`. `install(_:grant:isEnabled:)` moves the package to `<plugin id>/package/`, limits the grant to what the manifest asks for, and records the install (its identifier, origin, grant, and date) after the choices in `plugins.json`, where an install entry this build cannot read stays as it is; installing an installed identifier again replaces the package, keeps the plugin's place, storage, and secrets, and stops its running instance. `discard(_:)` deletes a staged package. `remove(_:)` stops the plugin and deletes its folder and its Keychain items in the Persona, whose accounts start with `<persona id>/`. At launch the manager lists the installed plugins after the built-in ones, each read from its package, and clears `Staging/`.

A script plugin's instance (`ScriptPlugin`) loads its background script into a hidden `WKWebView` of its own: a `PluginSchemeHandler` serves the package at `arch-plugin://<plugin id>/`, with a document at the root that runs the background script, every response carries the content security policy `default-src 'self'`, a compiled content rule list blocks every other load, Lockdown Mode takes away WebRTC, which neither covers, and the data store is non-persistent. A user script defines `arch` in the page's world, and `ScriptPluginBridge`, the web view's message handler with replies, performs its calls through the instance's context: storage, secrets, settings, badges, and copying. Commands and page script values reach the listeners that the background script set through `callAsyncJavaScript`. Its start, a command, or a page script value left unanswered for 10 seconds, or the end of its web content process, fails the instance: it releases its web view and fails the waiting calls, and the next use starts a new instance; at the third failure within five minutes the manager switches the plugin off with the reason, which Settings shows for the run. An instance without calls for 30 seconds stops the same way, and badges outlive it.

`PluginComposer` writes script plugins through the AI interface as the `pluginComposer` feature (Plugin Writer), which the user starts and which sends text only and needs a model with JSON output (`docs/ai.md`, Features that AI adds at run time). It sends the user's description with Arch's plugin reference (`PluginComposerInstructions.swift`) and takes a JSON reply of the manifest and the files. It refuses `sites`, `contributes.pageScripts`, files other than the background script, which alone runs, file names that are not plain `.js` names, files that do not parse as classic scripts (`JSCheckScriptSyntax`), and more than 256 KB of files, writes `plugin.json` with the current API version and the identifier `xyz.taeyoon.arch.generated.<UUID>`, which every version from one composer keeps, and stages the files with `stage(_:writtenBy:)`, which writes them into `Staging/<UUID>/` and reads them as it reads any package. A refused reply goes back to the model with the problem at most twice, a reply is requested again if it is not JSON, and one over 256 KB or one that the output limit of 8,192 tokens cut (`AIError.replyTooLong`) ends the request at once; then the composer throws `PluginComposerError.unusableReply`. A change sends the request, the last version's reply, and the change. The package's origin is `PluginOrigin.generated` with the requests and the model's name, which `plugins.json` records as `generated` in place of `source`.

Every installed plugin has a `PluginKind`: the manager runs script plugins itself, and the app gives it a `PluginRuntime` for each other kind, so far web extensions (`Extensions` module). Staging tells a package's kind by the manifest file at its top level or in an archive's only folder, `plugin.json` or a runtime's such as `manifest.json`, and reads the package through that runtime; an install with the identifier of an installed plugin of another kind is refused. `plugins.json` and the packages in `<plugin id>/package/` keep every kind alike, so the installed list does not depend on an engine. The manager tells each runtime the enabled plugins of its kind each time they change, makes their instances through it, has it delete what it keeps of a removed plugin, and switches a plugin off with the reasons the runtime reports once the plugin has failed to start on every engine it ran on, which Settings shows for the run. A runtime that cannot run on this Mac gives its plugins an `unavailability`, which keeps their contributions out and appears in Settings. `PluginPermission.nativeMessaging` is for web extensions only, and a `plugin.json` that asks for it is refused; `PluginManifest.extensionPermissions` holds a web extension's API permissions that no Arch permission stands for, which come with its install.

Site access modes, page script styles, events, the tab, page, history, download, network, and notification members of `PluginContext` and its `setEnabled(_:command:)` and `showPanel(_:)`, `PluginInvocation.source`, commands that take an argument, settings pages, script plugin panels, panels in the sidebar's place, revoking grants, Install in Another Persona, the `ai` permission, plugin hooks, and changing an installed plugin with AI are not built yet.

### Extensions module

`Extensions` runs Manifest V3 web extensions as plugins of the `webExtension` kind through `WebExtensionRuntime`, one per Persona. It reads `manifest.json` into a `PluginManifest` without any engine: the name, version, and description, a whole `__MSG_<name>__` text taken from `_locales/<locale>/messages.json` in the user's preferred languages and then the default locale; `tabs`, `clipboardWrite`, and `nativeMessaging` as Arch's permissions and the other API permissions as `extensionPermissions`; as sites, the patterns of `host_permissions` and of the content scripts' `matches` that Arch's match patterns hold (web pages on every port); and, for an `action`, an `action` command titled with its default title or the extension's name, which the palette lists. It refuses invalid JSON, a `manifest_version` other than 3, a missing name or version, a `key` that is not Base64, a message that the default locale lacks, and `permissions` or `optional_permissions` that are not lists of names and objects with one key, which Chromium refuses too; such an object counts by its key, as a permission with arguments. The extension's identifier is Chromium's: the first 128 bits of the SHA-256 digest of the public key in `key`, or else of the path the user installs it from, each hexadecimal digit as a letter from `a` to `p`, so installing from the same place again updates it; its plugin identifier is `extension.<identifier>`. The engines that run extensions, WebKit from macOS 15.4 and Chromium, are the host's `extensionRuntimeVersions`, less an engine whose application or the Persona's profile does not start, which never lends another engine's profile, and web extensions are unavailable only while there is none ("Web extensions need macOS 15.4 or later." below it). Each of them checks a package at staging without running it (`EngineExtensions.check(_:)`, which on WebKit reads it with `WKWebExtension(resourceBaseURL:)` and on Chromium reads its files), as well as the installed plugin it would update where an engine has no current answer; a package that every engine refuses is refused with the first engine's reason, such as "WebKit cannot run this extension: …". `plugins.json` keeps each answer in the install entry's `engineChecks` with the version of the engine's extension runtime, WebKit's framework version or the CEF version, so an entry without answers, as earlier builds wrote it, or with one from another version, as after a macOS update, is checked again in those engines, on or off, once the engines run for an enabled extension or a staging, and before its next load, and the names of engines this build does not know stay in the file. An enabled extension that no engine runs any more is switched off with the first engine's reason, and switching it on again checks it again. The runtime loads each enabled extension into the Persona's profiles only in the engines whose current answer runs it (`InstalledPlugin.engines`), with the API permissions its grant covers, those that come with the install, and its granted sites, every web page as `<all_urls>`, which extensions check for with `permissions.contains`. Each change to the engines waits for the previous change and applies per engine: an extension whose install changed loads again, while a recorded answer leaves a running copy alone; one switched off or removed unloads, and a removal also deletes its storage in the engines; an extension that an engine cannot start leaves that engine, which keeps the reason for the run (`engineFailures`) until the plugin is switched on again, and is switched off with each engine's reason only once it has failed on every engine it ran on. Each load passes the install's date, and once a pass's loads have ended, each engine may stop what it runs from an earlier launch and the app did not load (`stopUnloadedExtensions()`). No pass runs while no extension is enabled, so a profile that starts then stops them at once: the session reports each of the Persona's profiles as it starts and, when it makes the runtime, those that started before (`profileDidStart(with:)`). Its plugin instance runs the action on the invocation's tab and fails without a tab whose engine runs the extension. The runtime passes the windows that Browsing reports to the engines, lists the enabled extensions' actions for a tab, a pair under its version installed first and an extension without an action while the tab's engine keeps it from the tab's site, and answers the engines: popups go to the host; access that an extension requests while it runs asks with a sheet in the install sheet's sentences, which for a version of a pair names the pair and the asking version, never grants sites other than web pages or `nativeMessaging`, and needs Touch ID or the login password for every website, by the rule the install sheet also follows (`PluginGrant.confirmationReason(for:)`); native messages and ports need the extension's `nativeMessaging` grant from its install. `NativeMessaging` finds an app through its host manifest in Chromium's format, `<name>.json` in `NativeMessagingHosts/`, whose `name` matches, whose `type` is `stdio`, whose `path` is absolute, and whose `allowed_origins` lists `chrome-extension://<identifier>/`; a name is dot-separated runs of lowercase letters, digits, and `_`. It starts the app with that origin as its argument, writes without SIGPIPE, and exchanges messages as a 32-bit length in the Mac's byte order followed by UTF-8 JSON, up to 1 MB from the app: a single message ends the app after its first reply, and a port lasts until either side ends it. Two web extension plugins of a Persona can be versions of one extension, a pair (`PluginEngineVersions`, `engineVersions` in `plugins.json` as objects from engine name to plugin identifier, which keep the records and engine names the build ignores): each version runs only on the engine its record gives it, the runtime loads one extension per engine identifier in each engine, and each engine's calls reach that engine's version. At staging, a package matches an installed plugin outside a pair that has its identifier, or, while none has it, the first installed with the same name and a matching `author` or `homepage_url` and none that differs; the engines check the match and the plugins the package updates where they have no current answer, and the package can join the match for each engine that runs it while the match runs on the other. A version that joins a plugin with the same identifier gets the entry identifier `extension.<identifier>.webkit` or `.chromium`, which no package may have as its own. The engines know it by its package's identifier, so on its engine it takes over the data of the plugin's copy, which the review warns of when the package comes from another place and the plugin's package runs there, and a version whose record a build before engine versions dropped pairs again from its identifier. An update with an installed identifier goes to the version from the same source, else the one whose answers match, else the one the review chooses, keeps the pair and the dismissed notes, and cannot leave a version of a pair on no engine. Join With…, offered only while both engines run extensions, pairs two plugins whose current answers run each on its engine, starting with the one installed first on WebKit, and takes the switch of the one installed first; Separate Versions, refused for versions that share an identifier, and installing a package that could have joined as a separate plugin dismiss each plugin's note for the other's engines. The pair switches together, while a version that fails switches off alone; removing one version leaves the other in the pair's place with its grant, storage, and switch, and deletes the removed version's engine storage except in the engine its counterpart with the same identifier keeps. A pair contributes once, through its version installed first while it is on. An unpaired plugin offers a version for each engine that runs extensions while it runs on another, and asks for one where an engine with a current answer does not run it, a failure to start counting, until the user dismisses the note for that engine (`dismissedVersionNotes`); before Chromium runs extensions, nothing asks and Join With… does not show. Before the engines check or load an extension installed from a file without a `key`, the runtime writes into the installed copy's manifest a key whose bytes are the source's path, once per run; Chromium names an extension by the digest of its key, and otherwise by the folder it loads from, which is Arch's copy, so it then knows the extension by Arch's identifier, as WebKit does. A `.crx` file stages with the key of its header (Plugins module), and Chromium's package types for Install Chromium Version… add `.crx` files. The tabs and windows that extensions ask for open through the host in the asking engine. Allow on This Site reaches the engine that runs the tab's version. A question in the engine's own sentences, Chromium's for `permissions.request()`, asks with a sheet that names the pair and the asking version and says that the engine keeps the access until the extension is removed, needs Touch ID or the login password when the manifest's optional sites, or the sites it asks for that the install left out, which Chromium withholds and lets `permissions.request()` ask for again, include every website, and is refused without a sheet for an extension whose manifest lists `nativeMessaging` among its optional permissions without the install's grant, or whose optional lists do not read; a reload asks with Reload and Cancel, and the Chromium adapter refuses a store install without asking. `commands`, an options entry in Settings, and run-time grants that last across launches on WebKit are not built yet.

### AI module

`AI` is the provider-neutral AI interface designed in `docs/ai.md`. `AIClient.stream` takes a typed `AIRequest` (text, page, selection, file, download, tool call, and tool result parts) from a registered feature and streams `waiting`, `started`, `text`, `toolCall`, `usage`, and `finished` events; `reply` collects them, `run` performs tool rounds, and canceling the reading task or dropping the stream cancels the request. `AIService.shared` resolves the feature's route (a primary model and up to two fallbacks; features the user starts fall back to the default route, automatic ones never do), checks the daily automatic-request and monthly spending limits, checks every part against the feature's declared data kinds and the excluded sites (`file:` and `local-network` by default; internal pages always), strips queries and fragments, cuts page text to the scope and the model's input limit, waits in the provider's rate limiter (concurrent slots with user requests first, an optional per-minute bucket, and a cool-down after a 429, set before the freed slot goes to a waiting request, which requests answered 429 together start once), and moves to the next model only when a model fails before any text reached the caller. HTTP providers speak the `chatCompletions` or `messages` HTTP format against a configurable base URL (https, or http on a loopback host) through an ephemeral `URLSession` that refuses redirects to other hosts, with a 60-second first-byte and a 30-second chunk timeout. Keys live in the login keychain (service `xyz.taeyoon.arch.ai`), are read once per launch off the main thread, and never reach `ai.json`, which holds providers, routes, exclusions, and limits; `ai-usage.json` keeps 13 months of per-feature and per-model totals with costs estimated from user-entered prices (a file that does not decode is renamed to `ai-usage.json.unreadable`), and the last 50 requests stay in memory. `AIPageSource` is the protocol through which features read open tabs' pages. `AISettingsStore.allowsAI(on:)` and `setAllowsAI(_:on:)` back the site switch: allowing removes every exclusion that matches the address, and excluding adds its host, or `file:` for a local file. `title(of:)` and `estimatedCost(of:on:)` describe the model under an answer. Command-line providers run a tool the user installed and signed in to in the built-in terminal. Each request starts the tool with `posix_spawn` in its own process group, with pipes instead of a terminal, a new empty folder under `TMPDIR` as its working directory (removed once the tool has ended), and only `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH`, `LANG`, `TMPDIR`, `TERM=dumb`, and the configured variables; `PATH` is the executable's folder followed by the login shell's PATH, which `$SHELL -l -i -c` prints once per launch. The prompt goes to standard input: the instructions (with the schema when a JSON reply is asked for), then each message labeled `User:` or `Assistant:` with its parts as delimited blocks; tools get only text files. `{model}` in the arguments becomes the model's name, and an argument that contains it is left out for the tool's own default model, which has an empty name. Standard output is read as plain text a line at a time or as JSON lines whose dotted paths give text deltas, a final text, token counts, and an error, split into lines before UTF-8 decoding. A nonzero exit reports the last line of standard error, an exit without a reply is a malformed reply, output must start within 120 seconds and continue within 60 and ends a second after the tool exits even if a background process it started keeps standard output open, and cancellation sends SIGTERM to the process group and SIGKILL two seconds later. Requests with page, selection, file, or download parts skip command-line tools that the user has not marked as running without their own tools, and throw `blockedByPolicy(.commandLineToolWithPageData)` when only that rule left no model. `AIService.hooks`, an `AIHookCenter`, runs hooks: features subscribe to `pageLoaded`, `tabOpened`, and `downloadFinished` events with a priority, a delay, a timeout (30 seconds by default), and the kinds of action they may return. The hooks for one event run one at a time by priority and then feature ID, each seeing the actions applied before it; a newer event for the same tab or download cancels the older one's hooks and starts once they have stopped, and `cancel(subject:)`, switching the feature off or changing its route, cancelling the subscription, the timeout, and quitting stop hooks and drop their actions. A hook runs only for a registered automatic feature that is on, has a usable model of its own, is not paused, and is within the daily limit for automatic requests and the monthly spending limit, and only for an event whose site AI may read; its requests go out under its own feature whatever feature they name. The center keeps each feature's last hook error, a reached budget or `AIHookError.timedOut` among them, which a request that succeeds clears and a hook that sends no request leaves, and pauses a feature's hooks after three consecutive `authentication` or `providerUnavailable` request errors until Resume in its Settings ▸ AI row or a change to its route; a hook's own error does not end the count.

### Terminal module

`Terminal` is the built-in terminal where the user installs and signs in to command-line AI tools. Settings ▸ AI's Open Terminal shows its one window, which runs the user's login shell (`$SHELL`, else the account's shell) in the home folder on a pseudo-terminal from `posix_openpt`. `posix_spawn` starts `/bin/sh` in a new session; it opens the terminal again so the terminal becomes the session's controlling terminal (a terminal that `posix_spawn` opens does not, and neither does the one zsh opens itself), then replaces itself with the shell run with `-l`. Job control, Control-C, passwords read from `/dev/tty`, and window size changes work. Output reaches the screen in batches, one block on the main queue taking everything read since the last, and reading pauses while 64 KB wait, so a program that writes faster than the screen keeps up, such as `cat` of a large file, waits for the terminal and the windows stay responsive. Input that the program in front has not made room for waits in order, retried every 10 milliseconds without holding the write queue; the interrupt, quit, or suspend character typed meanwhile discards that input and the input the program has not read, as the terminal does when it receives the character, so Control-C stops a program that reads nothing after a long paste. The shell gets the app's environment with `TERM=xterm-256color`, `COLORTERM=truecolor`, and a UTF-8 `LANG` when none is set. The screen follows VT and xterm conventions: UTF-8 across reads, C0 controls, cursor movement, erasing, inserting and deleting characters and lines, scroll regions, 16, 256, and direct colors with bold, faint, italic, underline, and inverse, wide East Asian characters and emoji in two columns, combining marks (up to 32 scalars in a cell), the alternate screen, application cursor keys, bracketed paste, cursor visibility, titles, and replies to cursor position, status, and device attribute queries. It keeps 10,000 lines of scrollback, without the blank cells at the end of a line that did not wrap, and does not reflow lines on resize. Keys go through the input method, so Hangul composes at the cursor; Control with a letter sends its control character, also with input sources whose letters are not Latin. Dragging selects text and double-clicking selects a run without spaces, such as an address or a code; Copy, Paste, and Select All work from the Edit menu and the context menu. Paste sends line breaks as carriage returns; with bracketed paste on, the pasted text keeps tabs and carriage returns but no other control character, so an escape sequence in copied text cannot end the paste early and run the rest. Closing the window while a program other than the shell runs in front asks first, then hangs up the terminal; quitting Arch then brings the terminal forward and asks the same way. After the shell exits, the window keeps its output, and Open Terminal starts a new shell.

## Working Rules

1. Write new code for each feature, with interfaces, names, and layout designed for Arch.
2. Maintain `Package.swift` by hand. Add one target per new module.
3. Route every AI call through the AI interface. No feature calls a provider directly.
4. Write documentation, comments, and commit messages in English.
5. Document the current state only. Do not include a change history. When a queue task finishes, remove its row and fold the result into Current State and `docs/features.md` in the same commit.
6. Stage by path (`git add <paths>`) and keep one purpose per commit. Queue tasks use the `Task(<ID>):` subject; other work uses the prefixes in `.githooks/commit-msg`.
7. Work on `main`. Branches named `cloud/…` or `sync/…` move work between machines; delete them after use.
8. Never record the code-signing identity, its team identifier, or a signed bundle in the repository, the documents, or a report. `build/` stays ignored.
9. Before the final `Docs:` commit of a batch, have Codex rewrite the batch's added comments and document text through its CLI (`codex exec` without a model flag; confirm the model and reasoning level in its startup output). Ask it to add no information, preserve meaning, and remove empty wording, then review its changes.
10. Report a check as passed only after running it.

## Build Procedure

```bash

swift build
./scripts/bundle_app.sh     # writes build/Arch.app
open build/Arch.app
```

- `scripts/setup_cef.sh` needs the GitHub CLI signed in with access to `taeyoon0137/arch-chromium`. It keeps the archive in `Frameworks/cef-download` only once its checksum matches the pin, so a run after an interrupted download fetches it again. `ARCH_CEF_ARCHIVE=<path to the archive> ./scripts/setup_cef.sh` installs a distribution from a local archive instead, to try a build of `arch-chromium` before its release.
- `ARCH_SIGN_IDENTITY` overrides the signing identity; `ARCH_START_URL` opens a page at launch; `ARCH_CEF_FRAMEWORK_PATH` and `ARCH_CEF_HELPER_PATH` let a bare `.build/debug/Arch` find CEF.
- State lives in `~/Library/Application Support/Arch`: `session.json` (beside it, `session.unreadable.json` for a file that did not decode and `session-v<version>.json` for one from a newer build), `permissions.json`, `history.sqlite`, `site-search.json` (beside it, `site-search.unreadable.json` for a file that did not decode), `imports.json` (beside it, `imports.unreadable.json` for a file that did not decode), `Plugins/<persona id>/`, `NativeMessagingHosts/` (the host manifests of the native apps that web extensions may reach), and `Cache/Chromium`, which holds the default Persona's Chromium profile in `Default` and each other Persona's in `Persona-<UUID>`. ## Engine Plan

| Engine | Role | Work location |
|---|---|---|

## Work Queue

### How to use the queue

Each task carries the reasoning it needs, so that work can be split across models by capability:

- `high`: a design choice, a change to the Objective-C++ bridge or the engine protocols, a change to the `session.json` schema, window architecture, or threading. Use the most capable model available.
- `medium`: a view or session method inside an existing module that follows an existing pattern (for example `DownloadsView` or `togglePinned`). A mid-tier model can take it with the files and the done condition below.
- `low`: a mechanical edit, a document update, or a verification by checklist. Any model.

Rules for every tier:

1. Take tasks at or below your tier. Read the files the task names before editing, and keep to them. If the task needs a file, a protocol member, or a decision it does not list, stop, write the blocker into the task row (`blocked: …`), and leave the code unchanged.
2. Respect the order within a phase and the dependencies in the task text. Phases I and II run before III to V and VII; VI is independent, and VII builds on V.11.
3. One task per commit with the `Task(<ID>):` subject, staged by path. Run `swift build` for every code change and `scripts/bundle_app.sh` plus a launch when the task says "from the bundle".
4. Finish by updating this file (remove the row, update Current State) and the feature row in `docs/features.md` in the same commit, then go through the After each task list in `AGENTS.md`.
5. Verification steps use a fresh Application Support folder unless the step says otherwise.

## Decisions

- History visits: one visit per page change per tab. A reload, a repeated load of the same URL in the same tab, and the initial load of a restored tab do not add visits. The palette ranks by visit count, so pages that reload often would otherwise crowd out typed destinations. A hash change counts as a visit because its address is one the user may revisit.
- Permissions and dialogs default to the safe answer in the protocol: deny and dismiss. Feature code shows the user interface.
- Downloads save with an unused name to the downloads folder chosen in Settings. A save panel appears only when Settings asks where to save each download.
- The page context menu holds only items both engines can run. Look Up, Share, Services, Learn and Ignore Spelling, saving or copying an image, media controls, and Undo stay out on both; they can come back as app features that work on both engines.
- AppKit does not quit while a window shows a sheet with more than one button, so quitting first answers every sheet, and CEF shuts down only at `NSApplicationWillTerminateNotification`, once the quit is certain. A page dialog stops its page, so a navigation the user starts answers the dialog first on both engines; CEF resets its dialog state as soon as that navigation starts, so the end of loading, not the reset, ends the suppression of new dialogs.
- Calling a DevTools protocol method on a Chromium tab attaches a client until the browser closes. While attached, the client makes Chromium ignore an unresponsive renderer, stopping the `beforeunload` and unload timeouts; a hung page with a `beforeunload` handler cannot be closed. Features use the protocol only when CEF has no other route. The History menu therefore calls the page's `history.go`, first stopping any main frame navigation in progress because Chromium ignores page history requests during it. The menu has no effect on hung or crashed pages, pages that cannot run scripts (such as those served with a CSP sandbox), or pages that replace `History.prototype.go`; Back and Forward still work.
- Clearing or deleting history, from the History menu or the History window, changes the visit store only. Neither engine lets the app remove entries from a tab's back-forward list, so open tabs keep their earlier pages in Back, Forward, and the History menu until they close. The store keeps one row per address with its last visit. As a result, the History window lists each page once, under the day of its last visit, and clearing a range removes pages last visited in it, including their earlier visits.
- Pages keep each engine's own default styles. Of the differences between them, only two are worth evening out from the app: WebKit draws Korean, Japanese, and Chinese pages that set no font in a serif face where Chromium uses a sans-serif one, and its field placeholders are lighter (`#A9A9A9` against `#757575`). Chromium already uses the better value in both cases, and WebKit could take an app style sheet only through a private API or a `<style>` element that a strict CSP blocks and reports, so the app adds none.
- The History menu and Back show each engine's own back-forward list. WebKit combines script navigations without a user gesture into one entry, so a WebKit tab can list fewer pages than a Chromium tab on the same site.
- Engine choice is per tab. A tab opened by a page inherits that page's engine; other new tabs use the default engine; the user can switch a tab's engine at any time. Cookies are shared by copying between the engines' stores of one Persona: a copy carries the cookies the source added, changed, or deleted since the stores last agreed, and site storage such as local storage stays per engine. Clear Site Data is the exception: it removes the site's cookies from both stores together while the copies wait.
- Chromium's renderer, GPU, and utility processes run without the macOS sandbox for now: the runtime sets CEF's `no_sandbox`, and the helper starts no sandbox context. The first Chromium build turned it off without recording a reason. A page that takes over its renderer process can therefore act with the user's rights, so II.16 turns the sandbox on.
- Use private APIs only behind flags on `flags://`: one for all private APIs, one for each API, and one for each feature that uses one. Check each API's availability quietly, in the background when it is registered or just before its first use. If a feature's API is missing or switched off, the feature falls back to public behavior or stays hidden. You may fork CEF or WebKit when a feature needs it.
- Features use macOS facilities by default on both engines so Arch behaves like other Mac apps. For example, Chromium's picture in picture uses AVKit rather than Chromium's own window.
- Out of scope: a browser-side password manager; page translation, unless an engine offers it to embedding apps; and features specific to one browser rather than common to browsers, such as per-site CSS and JavaScript and notes. App icon choice is not offered for now; whether to add sound effects is undecided.
- A Persona owns its spaces and keeps cookies, sessions, site storage, and installed plugins separate. Favorites stay alive across spaces within their Persona. The default Persona keeps each engine's default storage (WebKit's default data store and CEF's global request context), so the upgrade to Personas moved no site data and signed nobody out; every other Persona has storage of its own named by its UUID. Cookies copy between the engines only within a Persona. A tab or space never moves to another Persona, because its pages would lose their storage. A deleted Persona's stored data goes at the next launch, before any engine starts, because an engine cannot remove a profile it has loaded, and only for the IDs that `session.json` lists in `removedPersonaIDs`, never because a Persona is missing.
- Every piece of state has exactly one owner. State that can differ between two windows open at once, such as what a window shows, focuses, or edits, belongs to that window's `BrowserWindowModel`. State bound to one Persona's engine storage (its contexts, browsers, cookie copying, plugin manager, and web extension runtime) belongs to its `PersonaEngines`, from first use until quit. The engine applications, CEF initialization, crash totals, and the primary engine belong to the session's engine section. Everything else the user owns (Personas, spaces, favorites, tabs, the closed list, downloads and the pages kept open for them, each stored with the runtime that created it, permissions, zoom, and persistence) belongs to `BrowserSession`. `BrowserSession.swift` keeps the session's members in one file, in sections by area, because most serve several areas and the lists they change keep their setters private to that file. A part that stands on its own, such as the sheet queue (`TabSheetQueue`), cookie copying (`CookieSync`), the answers to permission requests (`SitePermissionAnswers`), and download notifications (`DownloadNotifier`), is a separate type owned by the session.
- At most one window shows a tab, because an engine's view has one superview. A window shows its selected tab and, in a split view, those of that tab's other panes that no other window shows. Explicit selection moves a tab: a sidebar click, a palette tab row, the tab switcher, ⌘-numbers, Next and Previous Tab, a favorite's tab, a tab's own request (a question it needs to show, or the return button of its picture-in-picture window), and selection by sync or a plugin. The window that shows the tab first gives it up, selecting its fallback when the tab is its selected tab or leaving the pane otherwise, and only then does the selecting window run its own side effects, so the window losing the tab lets go of its docked developer tools before the other docks them. Automatic selection never takes a tab that another window shows: switching spaces, the fallback after a tab closes, restore, a new window, and the losing window's fallback. With no free tab, the window shows the empty page.
- Code comments and documents cite the window rules, the Persona rules, and the open decisions of the multiple windows design by number, as in "window rule 2". `docs/windows-personas.md` numbers them under Decisions and Open decisions.
- The app shell names the app's Application Support folder and gives it to the session and `PluginIdentifierMigration`. The session keeps its own files there (`BrowserSession.userDataDirectory`; WebKit keeps website data where the system puts it for the app) and makes the stores that keep theirs there, history, remembered permissions, and site search, which Settings, the History window, the palette, and imports reach through the session. `AIService.shared`, which views of several modules read, names the same folder for `ai.json` and `ai-usage.json`.
- The model runs on the main thread. Both adapters call every delegate method, completion handler, and change closure of the engine protocols there (`docs/engine-protocol.md`). `AI` and `Plugins` are main actor types; `BrowserSession`, `BrowserWindowModel`, and `Tab` are not isolated yet (I.18), and the comment at the top of `BrowserWindowModel.swift` says how their members reach main actor code until then. Work moved off the main thread, such as the history store's queries and the session file's writes, runs on its own queues and reports back on the main thread. With tools version 5.10, `Package.swift` builds every target in the Swift 5 language mode, in which the compiler checks calls into main actor code but not whether the values that cross threads are `Sendable`.
- Arch has its own plugin system with more capabilities than browser extensions. It includes built-in plugins for later features. WebKit extensions and Chromium-format extensions run as one kind of plugin; password managers such as 1Password come as plugins.
- Chromium DevTools show inside the page area. Arch's engine fills the bridge's view with the DevTools front-end, in Chromium's docked mode without a `Browser` and without the front-end's docking controls, and the app places that view beside the page or, undocked, in a window of its own, so the Developer menu's sides, the shared sizes, and the margin handle apply. The front-end's own docking, which the device toolbar and the screenshot commands require, stays off, and Workspaces folder access is declined, because the tools have no dialog host in a view. WebKit's Web Inspector opens inside the page through the private `_inspector` object behind private API flags. With them off, `isInspectable` still lets the browser bundled with macOS inspect WebKit tabs.
- AI features use providers the user connects through an API key or a command-line tool signed in through the built-in terminal. The user chooses providers per feature. Arch ships no model or provider account. All AI features, hooks, and features that AI adds at run time use one AI interface, designed in `docs/ai.md`.
- Now Playing and the media keys belong to the app on both engines. Chromium's own media controls stay off because they would use the same process-wide centers. WebKit's GPU process registers its own Now Playing client for the app. No public API turns it off, so a WebKit tab can also appear through it.
- Arch remembers permission answers without asking whether to, because a one-time choice could not hold on Chromium. Chromium's own prompt keeps every Allow and Don't Allow in the profile, and CEF's prompt callback has no one-time answer. Settings ▸ Websites changes and removes answers, and the session copies each change into Chromium's content settings. Screen recording is never remembered.
- CEF builds from source in the separate private repository `taeyoon0137/arch-chromium` rather than in this one. It holds CEF's own history: `master` and the CEF branch mirror upstream, and Arch's changes are commits on `arch-<CEF branch>`, so moving to a new CEF branch replays them. Each release carries one distribution with its SHA-256 and its symbols, and this repository pins one release, so every app commit names the engine it builds with.
