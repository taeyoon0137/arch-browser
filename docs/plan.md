# Arch Browser Development Plan

This plan gives the context needed to continue work in another session, on another Mac, or with a less capable model. Progress lives only here and in `docs/features.md`; there is no external context store.

## Goals

- Build a sidebar-first macOS browser with its own implementation. `docs/features.md` lists every planned feature and its status.
- Run no servers of our own. Use alternatives such as iCloud for features that need servers, including sync (`docs/features.md`, sections 5 and 8).
- Give both engines the same experience. Context menus, dialogs, sheets, find, downloads, extensions, and tools use the app's own interface and work alike whatever a tab's engine; only engine-drawn surfaces such as popups may differ. `docs/features.md` notes any feature an engine cannot support and why.
- Keep features lightweight. Delegate autofill to Apple Passwords or 1Password. Features use macOS facilities by default on both engines to fit macOS as closely as possible. Follow the Platform integration table in `docs/features.md`.
- Prefer public APIs. Use private APIs only behind flags on `flags://`. Check each API's availability quickly at runtime (see Decisions).
- Offer AI features through one AI interface. The user connects providers they subscribe to with an API key or a command-line tool in the built-in terminal. They choose a provider and model for each feature. Arch ships no model or provider account.
- Use ARCH prefixes throughout: `ARCH*` for packages, `Arch` for the app module, and `ARCHKit` for the core layer.
- The browser is for internal use. No distribution is planned. Manage replacement names, images, fonts, and similar items outside this repository.

## Approach

- Write new code for each feature. Start from a row in `docs/features.md`. Design the smallest module that delivers the feature and add it to `Package.swift`.
- Design type names, module boundaries, method signatures, and file layout for Arch. A row in `docs/features.md` describes what a feature does, not how to build it.
- Add engine protocol members only when a feature needs them. The current protocols are a starting point, not a list of requirements to implement.
- Build AI features on the AI interface and plugin system. This lets built-in features, hooks, and features that AI adds at run time use the same calls.
- The sidebar holds navigation, the address field, favorites, and tabs grouped by space. The window background shows the current space's tint. Nothing sits above the page. Only the code is written anew.
- Use the system framework whenever macOS provides the user experience. Do not build or retain an engine-specific version; for example, picture in picture on Chromium uses AVKit. Keep Chromium's existing native integrations. Route the remaining engine events to these frameworks and disable the engine's equivalent user interface.

| Engine abstraction | `ARCHEngine` protocols are complete. Both adapters route page events through `EngineWebContentsUIDelegate`; feature code implements only the callbacks it handles, and the defaults give the safe answer (dialogs dismiss, permissions deny). `ScriptMediaSession` gives both adapters one media session. It follows the media each document's script reports and shows the playing document, or otherwise the last to report. Between reports, it advances the position at the playback rate. Both adapters report a link the user clicks with Shift and without Command to `EngineWebContentsNavigationDelegate` as a user-initiated `newWindow` action; the WebKit adapter asks the navigation delegate about every navigation, the Chromium adapter only about these links. `EngineWebContents.readableContent(limit:completion:)` returns the main frame's visible text (headings as `#` lines, list items as `- ` lines, paragraphs separated by blank lines), its address, title, `lang`, and the selection outside fields and editable areas. Both adapters run the same script, `EngineReadableContent.script`, which skips scripts, styles, templates, hidden and `aria-hidden` subtrees, the content of closed `details`, field values, and editable regions, follows open shadow roots and their slots, and stops at the limit. Page scripts (`EnginePageScript`) run in each new document of a web contents, from its configuration's list or, after `setPageScripts`, from the next document on, at document start or once the document is parsed, in the main frame or every frame. Each is a function expression that the engine calls with its world's channel: `channel.send(value)` passes the value as JSON to the `pageScriptDelegate` and returns a promise of the reply, and `channel.onMessage(listener)` receives what `postPageScriptMessage(_:toWorld:)` delivers to the main frame. `executeJavaScript(_:inWorld:completion:)` calls a function with a world's channel in the main frame, opening the channel if the document has none, and returns the string it returns. Both adapters hand the delegate an `EnginePageScriptReply`, which sends the first reply only and sends nil for a reply the delegate drops, so a script's promise always settles. A page that a web contents opens starts with its scripts. |
| WebKit adapter | `ARCHEngineWebKit` adds to its user agent the version tokens that full browsers on this system send; without them, some sites serve pages for old browsers. A script in its own content world reports whether each document's media elements play sound. It describes the last element to play sound, its position, and the page's Media Session metadata. A script in the page's world records the page's Media Session action handlers and runs them for the media keys. It reports and restores `interactionState` as a tab's restorable state, preserving the back-forward list and page positions. It enables element fullscreen, so the Fullscreen API moves the element into WebKit's own full-screen window, as in the system's browser. Every web view sits in a page view of its own and sets `isInspectable`, so the browser bundled with macOS can inspect it. While the private API flags allow it, ⌥⌘I opens WebKit's Web Inspector through the private `_inspector` object (`show`, then `attach`). WebKit attaches it beside the web view inside the page view and resizes the web view. The inspector stays with the tab across tab switches. Its toolbar docks it to another side or into its own window. New web views then turn on developer extras (`_developerExtrasEnabled`), so their context menu offers Inspect Element. Its `WebKitWebView` subclass hands WebKit's context menu to the delegate in `willOpenMenu(_:with:)`, keeping only WebKit's own editing and spelling items (matched by tag), and learns the clicked link, image, and selection from a script in its own content world; menus a page element provides, such as a video's playback speed menu, and elements the script cannot see, such as those in a closed shadow root, keep WebKit's menu. It forwards JavaScript dialogs, HTTP authentication, links with schemes it does not load, media capture permission with the origin's port when it is not the default (after the system's own camera and microphone permission), and web content process termination to the delegate. Each Persona's context has its own data store: the default Persona uses `WKWebsiteDataStore.default()`, and any other `WKWebsiteDataStore(forIdentifier:)` with the Persona's UUID, whose data, caches included, WebKit keeps in `~/Library/WebKit/xyz.taeyoon.arch/WebsiteDataStore/<uuid in lowercase>`. `removeStoredData` deletes such a store with `removeDataStoreForIdentifier:completionHandler:` at launch, before the engine starts. It deletes cookies accepted by a test through `WKHTTPCookieStore`. It removes other site data with `WKWebsiteDataStore.removeData`, using records that match the given origins' hosts, one per registrable domain. A closed page leaves its media presentations, pauses its media, and moves to a blank page without its delegates, because a web view keeps its page for as long as anything holds it. Its navigation policy reports a link clicked with Shift and without Command, unless it is marked for download, as `newWindow`, as Chromium reads the click. It reads a page's readable text with that script through `callAsyncJavaScript` in its own content world. Page scripts run as `WKUserScript`s in a content world of their own per world, after a channel script that defines the world's channel there; a `WKScriptMessageHandlerWithReply` added only to that world carries the channel, and a world keeps its handler once added. The web contents' `WKUserContentController` subclass holds the page scripts. WebKit removes user scripts only all at once, so replacing page scripts adds the controller's other scripts again, telling them apart by a marker comment at the start of each page script's source. A popup uses its opener's content controller and so shares its page scripts. `executeJavaScript(_:inWorld:completion:)` runs the channel script first and then the function through `evaluateJavaScript(_:in:in:)`; `postPageScriptMessage` delivers through `callAsyncJavaScript`. History, content blocking, and page state restore are stubs. |
| Chromium adapter | `ARCHEngineChromium` embeds a CEF browser (Alloy style) beside the sidebar through `CEFBridge`, with an external message pump on the main run loop and the `ArchHelper` subprocess. It implements loading, navigation with the back-forward list (from CEF's navigation entries; selecting an entry checks its URL against the menu's URL, stops any main frame navigation in progress, then calls the page's `history.go`, because CEF has no equivalent call and the DevTools protocol's call would leave a debugger attached), title, URL, and loading state, favicon URLs, zoom level, popups as new tabs that keep `window.opener`, closing, restored tabs that load their last address (CEF cannot fill a back-forward list), the page's audible state and media (the helper's renderer process adds a script to each frame before page scripts run; Closing a browser detaches its view in `DoClose`, so CEF never closes the app's window. JavaScript `alert`, `confirm`, `prompt`, and `beforeunload` dialogs go to the delegate through `CefJSDialogHandler`, and closing a tab runs the page's `beforeunload` handlers first, except while the tab has a download in progress or interrupted: asking would mean closing the browser, which stops the download, so that tab closes at once, and its kept page answers its own handlers with Leave when it moves to a blank page. While the runtime runs, a page's own `window.close()`, or its opener's, does not close a browser that such a download needs: `DoClose` leaves the browser's view in place, so CEF keeps the browser open, and the delegate learns on the next turn of the run loop that the page closed itself. The bridge tells these closes from the app's own, which `close` and `tryCloseWithCompletion:` request. `CefContextMenuHandler::RunContextMenu` hands each context click to the delegate: the bridge copies CEF's parameters, shows the app's `NSMenu` from a run loop block once CEF's current work returns, so CEF keeps running while the menu tracks, and cancels CEF's request exactly once when the menu closes or the browser goes, so Chromium's own menu and commands never run. Its spelling and edit items run on the frame the menu opened on. Cookies, stored data, and permission settings go through each Persona's request context (`ARCHCEFRequestContext`): the default Persona uses CEF's global context, whose profile is `Default` under the root cache path `Cache/Chromium`, and any other Persona a context whose profile is `Persona-<UUID>` beside it. Browsers use a new context at once; its cookie, storage, and permission calls wait in order until Chromium reports the context and its cookie store initialized. Browsers of different Personas never share a render process, and a popup keeps its opener's context. Chromium keeps a profile's HTTP and code caches at the same relative path under `~/Library/Caches`. `removeStoredData` removes nothing while CEF runs; at launch it renames a Persona's profile directories under both roots and deletes them in the background, and `makeApplication` deletes renamed leftovers before CEF starts. HTTP authentication requests for sites and proxies reach the delegate through `GetAuthCredentials` as a `URLAuthenticationChallenge`, with a failure count the adapter keeps until a page finishes loading; the `disable-chrome-login-prompt` switch keeps Chromium's own sign-in window from taking them first. Navigations and popups to schemes Chromium does not load stop in `OnBeforeBrowse` and `OnBeforePopup` and go to the delegate as links for other apps. Its developer tools open through `ShowDevTools` in a window CEF creates for a Chrome-style browser. A DevTools client reports the window when it appears, shortly after `OnAfterCreated`, and when the tools close. At quit, the runtime closes every browser and runs CEF's work for up to two seconds until they close. It then shuts down. Shutting down with browsers open crashed after Chrome-style developer tools had opened. It deletes cookies accepted by a test by visiting the context's cookie manager and reports after that store flushes. It clears an origin's other storage with the DevTools protocol's `Storage.clearDataForOrigin` in a separate hidden browser of the same context. That browser then closes, so no tab keeps a DevTools client. The bridge turns off Chromium's own media key handling and Now Playing (`--disable-features=HardwareMediaKeyHandling`), which would use the same process-wide `MPNowPlayingInfoCenter` and `MPRemoteCommandCenter` as the app. `OnOpenURLFromTab` and `OnBeforePopup` ask the navigation delegate about a link the user clicked with Shift, which Chromium gives the new window disposition; a link the delegate allows loads in place, as Alloy style does, or opens as a popup. It reads a page's readable text through a process message to the helper's renderer process, which evaluates the script in the main frame's page world and replies with its JSON string (`evaluateScript:completion:`, which shares its evaluation with the theme color); a request without a reply ends after ten seconds, when the renderer quits, or when the browser closes. Page scripts run in the page's main world: the bridge passes them to the renderer in the browser's extra info, and in a process message to each of the browser's frames when they change and to each frame created after a change; each renderer keeps them per browser object. CEF does not order that message before the frame's first document, so in a renderer process that had none of the browser's frames, such as after a cross-site navigation, the first document may still run the scripts the browser was created with (needs verification). The helper's `OnContextCreated` makes the document's channel opener before the page's scripts run, so every channel, also one that `executeJavaScript(_:inWorld:completion:)` opens later, calls the built-ins as they were then. It opens each world's channel with a native function that it passes to the channel script as an argument, so it never reaches `window`, and runs the scripts before the page's own; channels keep their state in objects without prototypes, and document-end scripts wait for `DOMContentLoaded`. The page can still see the values a script sends and receives through built-ins it replaces, such as a `then` getter on `Object.prototype` for object replies. Values a script sends carry a request number unique in its renderer process; the browser answers through the sending frame. `executeJavaScript(_:inWorld:completion:)` shares the process message of `readableContent`, and `postPageScriptMessage` sends one to the main frame. For a popup it does not stop, `OnBeforePopup` hands CEF a browser object of the bridge's own, with its own client, a container view of the opener's size, and the opener's page scripts in its extra info, and returns false, so CEF creates the popup in the opener's browsing context and request context, as CEF's sample client does on macOS. The page keeps the window `window.open` returns, and the popup keeps `window.opener`, which sign-in popups need to report back. `OnBeforePopup` stops a popup while the runtime shuts down, when the opener's `ChromiumWebContents` has no UI delegate to adopt it, as WebKit stops one, and for a Document Picture-in-Picture window, which would become a tab, so the page keeps its own interface. The bridge holds the object until the popup's `OnAfterCreated`, when the opener's `ChromiumWebContents` wraps it in a new one and reports it to the UI delegate with Chromium's disposition, or until `OnBeforePopupAborted` drops it. CEF owns a popup's page only once the opener shows the popup, which Chromium does after `OnAfterCreated` in the same task, and closing the popup before then crashes CEF, as CEF's `CreateInternal` and `AddNewContents` read the browser's released platform delegate. So a popup that the UI delegate dropped closes on the next turn of the run loop. Extensions, content blocking, and page state restore are stubs. | Plugins module | `Plugins` holds the parts of the plugin system in `docs/plugins.md` built so far. A built-in plugin is a Swift type that conforms to `BuiltInPlugin` and declares a `PluginManifest`: a reverse-DNS `PluginID` (at least two dot-separated labels of ASCII letters, digits, and `-`, at most 128 characters, lowercased so that identifiers that differ only in case name one plugin and one folder), a name, a version, a summary, the permissions it asks for (`tabs` and `clipboard` so far), the sites it may reach as match patterns, and its contributions: commands, menu items, sidebar items, settings, and page scripts. A `MatchPattern` is `scheme://host/path` or `<all_urls>` and covers http and https addresses only: the host is `*`, a name, or `*.` and a name for its subdomains too, a pattern covers every port, and each `*` in the path matches any run of characters of the address's path and query. A command can have a `PluginShortcut`, written like `ctrl+opt+r`: the modifiers `ctrl`, `opt`, `shift`, and `cmd`, each at most once, and a key (a printable ASCII character other than `+`, `plus`, `space`, an arrow, or `f1` to `f20`), with `cmd` or `ctrl` unless the key is a function key. The app passes its built-in plugin types to the session, which creates a `PluginManager` for each Persona when a tab or window of the Persona first needs it and keeps it in the Persona's `PersonaEngines`, with its files in `Plugins/<persona id>/` in the app's Application Support folder. The manager gives built-in plugins everything their manifests ask for and enables those that are on by default, except the plugins the user switched on or off in that Persona, which `plugins.json` records (a file that does not decode moves to `plugins.unreadable.json`). Its `PluginContributionIndex` holds the enabled plugins' palette commands, their menu items for each location in one section per plugin, with titles falling back to their commands' (a command with a shortcut and no item in the Plugins menu gets one there, and only the first of its items there has the shortcut; a page context item shows when the click has one of its contexts, where `page` means no link, image, media, selection, or field), their sidebar items, and their page scripts. The manager starts a plugin's code at its first command, panel, or page script value: it creates the plugin and activates it with a `PluginContext` scoped to the plugin, its grant, its storage, and its secrets. Uses that arrive during activation wait for it, and a failed activation starts again at the next use. Switching a plugin off drops its contributions and badges and calls its `deactivate()` once its activation ends; switching it on again starts a new instance. An instance's context stops acting when the plugin is switched off, its Persona is deleted, or the activation fails: its storage and secrets only read, its other actions throw `stopped`, and its badges do nothing. Deleting a Persona closes its manager (`close()`): its plugins leave the list, their running instances stop, and storage changes that have not reached the files are dropped. The next launch's removal pass calls `PluginManager.removeData(ofPersona:in:)`, which deletes the Keychain items of every plugin whose account starts with `<persona id>/` and the Persona's `Plugins/<persona id>/` folder before any manager of the Persona exists. The invocation's tab carries its title and address only when the grant has `tabs` or its sites cover the page; a page context menu item's link, image, and selected text and a space menu item's space pass as they are. The context throws `permissionDenied` for calls the grant does not cover, reads the plugin's settings (the user's value, or the default for one the user has not changed or whose stored value no longer suits its field), and sets badges on the plugin's own sidebar items. A failed command beeps. `Plugin.panel(for:)` gives a sidebar item's panel each time the item opens it. Each plugin's storage keeps JSON values (`PluginValue`) by key in `Plugins/<persona id>/<plugin id>/storage.json`, up to 5 MB counted as the bytes of each key plus the JSON of its value; a write that grows it past the limit throws `quotaExceeded`, and a value JSON cannot hold, such as one nested more than 510 levels deep, throws an encoding error. Changes reach the file atomically 0.5 seconds after the last one and at quit. A file that does not decode moves to `storage.unreadable.json`, and the plugin starts empty. Setting values live in the same file under keys that start with `arch.setting:`, which the plugin's own storage refuses with `reservedKey` and leaves out. Secrets, secret settings among them, are generic passwords in the login keychain with the service `local.arch.browser.plugin.<plugin id>` and the account `<persona id>/<key>`. The built-in Page Address plugin adds Copy Page Address, which copies a tab's address, with ⇧⌘C, in the Plugins menu, in the page context menu on the page itself, and as Copy Address in a tab row's context menu for that row's tab, and a setting that copies a Markdown link of the title and address instead. A built-in plugin's page scripts (`PluginPageScript`) carry their JavaScript, their match patterns, when they run, and whether they run in every frame. The index gives the engines the scripts of the enabled plugins, each plugin's in its world `ARCHPlugin.<plugin id>`. Each script's function first checks the document's `location` against the script's patterns and the plugin's granted sites with a JavaScript copy of `MatchPattern.matches(_:)`, which calls no built-in function and reads only own properties, so built-ins a page replaced cannot change its answer. Then it runs the script as the body of a function with the world's channel as `arch`. A script whose source does not parse as a function body on its own, which JavaScriptCore checks through the `Function` constructor without running it, is left out, so no source can close that function and run outside the check. `PluginManager.receive(_:from:)` passes a value a page script sent to `Plugin.receive(_:)`, starting the plugin first if it has not started, while the plugin is enabled and its granted sites cover the sending frame's document, with the tab redacted for the grant, and returns the reply as JSON. ## Working Rules

1. Write new code for each feature, with interfaces, names, and layout designed for Arch.
2. Maintain `Package.swift` by hand. Add one target per new module.
3. Route every AI call through the AI interface. No feature calls a provider directly.
4. Write documentation, comments, and commit messages in English.
5. Document the current state only. Do not include a change history. When a queue task finishes, remove its row and fold the result into Current State and `docs/features.md` in the same commit.
6. Stage by path (`git add <paths>`) and keep one purpose per commit. Queue tasks use the `Task(<ID>):` subject; other work uses the prefixes in `.githooks/commit-msg`.
7. Work on `main`. Branches named `cloud/…` or `sync/…` move work between machines; delete them after use.
8. Never record the code-signing identity, its team identifier, or a signed bundle in the repository, the documents, or a report. `build/` stays ignored.
9. Before the final `Docs:` commit of a batch, have Codex rewrite the batch's added comments and document text through its CLI (`codex exec` without a model flag; confirm the model and reasoning level in its startup output). Ask it to add no information, preserve meaning, and remove empty wording, then review its changes.
10. Report a check as passed only after running it.

## Build Procedure

```bash
./scripts/setup_cef.sh      # once per checkout
swift build
./scripts/bundle_app.sh     # writes build/Arch.app
open build/Arch.app
```

- `ARCH_SIGN_IDENTITY` overrides the signing identity; `ARCH_START_URL` opens a page at launch; `ARCH_CEF_FRAMEWORK_PATH` and `ARCH_CEF_HELPER_PATH` let a bare `.build/debug/Arch` find CEF.
- State lives in `~/Library/Application Support/Arch`: `session.json` (beside it, `session.unreadable.json` for a file that did not decode and `session-v<version>.json` for one from a newer build), `permissions.json`, `history.sqlite`, `site-search.json`, `Plugins/<persona id>/`, and `Cache/Chromium`, which holds the default Persona's Chromium profile in `Default` and each other Persona's in `Persona-<UUID>`. Chromium keeps each profile's HTTP and code caches in `~/Library/Caches/Arch/Cache/Chromium`, where the removal pass also deletes a deleted Persona's directory, and WebKit keeps the other Personas' stores in `~/Library/WebKit/xyz.taeyoon.arch/WebsiteDataStore`. Delete these folders for a first-launch test. `defaults delete xyz.taeyoon.arch ARCHAskedDefaultBrowser` brings the default-browser prompt back.
- For a scripted check, run `build/Arch.app/Contents/MacOS/Arch 2> /tmp/arch.log &`, then inspect `session.json`, `sqlite3 … history.sqlite 'select * from visits'`, and the log. `open -a build/Arch.app https://example.org` sends a link to the running app. `pkill -9 -f "Arch.app/Contents/Frameworks/Arch Helper.app/Contents/MacOS/Arch Helper --type=renderer"` crashes every page's renderer; a bare `type=renderer` pattern would also kill other Chromium-based apps' renderers.
- Launch through `open` or the Finder for any check that involves a system permission prompt. A binary started from a shell is attributed to the shell's parent, so the camera prompt never appears and the page reports a denied request.

Regression checklist, run from the bundle on the Chromium engine with a fresh Application Support folder:

1. ⌘F opens the find bar focused; typing shows "n of m"; Return and ⇧Return move through matches; Escape closes the bar and the page keeps keyboard focus; switching tabs closes it.
2. ⌘⇧J and the library button toggle the library, which pushes the sidebar aside and dims its first 60 points; clicking that part or swiping brings the sidebar back, and swiping past the first space brings the library in; a file download shows its progress on the button and appears in the library; pause, resume, and cancel change the row; a download that finishes with the library closed adds to the button's badge until the library opens; Clear removes finished rows. ## Work Queue

### How to use the queue

Each task carries the reasoning it needs, so that work can be split across models by capability:

- `high`: a design choice, a change to the Objective-C++ bridge or the engine protocols, a change to the `session.json` schema, window architecture, or threading. Use the most capable model available.
- `medium`: a view or session method inside an existing module that follows an existing pattern (for example `DownloadsView` or `togglePinned`). A mid-tier model can take it with the files and the done condition below.
- `low`: a mechanical edit, a document update, or a verification by checklist. Any model.

Rules for every tier:

1. Take tasks at or below your tier. Read the files the task names before editing, and keep to them. If the task needs a file, a protocol member, or a decision it does not list, stop, write the blocker into the task row (`blocked: …`), and leave the code unchanged.
2. Respect the order within a phase and the dependencies in the task text. Phases I and II run before III to V and VII; VI is independent, and VII builds on V.11.
3. One task per commit with the `Task(<ID>):` subject, staged by path. Run `swift build` for every code change and `scripts/bundle_app.sh` plus a launch when the task says "from the bundle".
4. Finish by updating this file (remove the row, update Current State) and the feature row in `docs/features.md` in the same commit, then go through the After each task list in `AGENTS.md`.
5. Verification steps use a fresh Application Support folder unless the step says otherwise.

## Decisions

- History visits: one visit per page change per tab. A reload, a repeated load of the same URL in the same tab, and the initial load of a restored tab do not add visits. The palette ranks by visit count, so pages that reload often would otherwise crowd out typed destinations. A hash change counts as a visit because its address is one the user may revisit.
- Permissions and dialogs default to the safe answer in the protocol: deny and dismiss. Feature code shows the user interface.
- Downloads save with an unused name to the downloads folder chosen in Settings. A save panel appears only when Settings asks where to save each download.
- The page context menu holds only items both engines can run. Look Up, Share, Services, Learn and Ignore Spelling, saving or copying an image, media controls, and Undo stay out on both; they can come back as app features that work on both engines.
- AppKit does not quit while a window shows a sheet with more than one button, so quitting first answers every sheet, and CEF shuts down only at `NSApplicationWillTerminateNotification`, once the quit is certain. A page dialog stops its page, so a navigation the user starts answers the dialog first on both engines; CEF resets its dialog state as soon as that navigation starts, so the end of loading, not the reset, ends the suppression of new dialogs.
- Calling a DevTools protocol method on a Chromium tab attaches a client until the browser closes. While attached, the client makes Chromium ignore an unresponsive renderer, stopping the `beforeunload` and unload timeouts; a hung page with a `beforeunload` handler cannot be closed. Features use the protocol only when CEF has no other route. The History menu therefore calls the page's `history.go`, first stopping any main frame navigation in progress because Chromium ignores page history requests during it. The menu has no effect on hung or crashed pages, pages that cannot run scripts (such as those served with a CSP sandbox), or pages that replace `History.prototype.go`; Back and Forward still work.
- Clearing or deleting history, from the History menu or the History window, changes the visit store only. Neither engine lets the app remove entries from a tab's back-forward list, so open tabs keep their earlier pages in Back, Forward, and the History menu until they close. The store keeps one row per address with its last visit. As a result, the History window lists each page once, under the day of its last visit, and clearing a range removes pages last visited in it, including their earlier visits.
- Pages keep each engine's own default styles. Of the differences between them, only two are worth evening out from the app: WebKit draws Korean, Japanese, and Chinese pages that set no font in a serif face where Chromium uses a sans-serif one, and its field placeholders are lighter (`#A9A9A9` against `#757575`). Chromium already uses the better value in both cases, and WebKit could take an app style sheet only through a private API or a `<style>` element that a strict CSP blocks and reports, so the app adds none.
- The History menu and Back show each engine's own back-forward list. WebKit combines script navigations without a user gesture into one entry, so a WebKit tab can list fewer pages than a Chromium tab on the same site.
- Engine choice is per tab. A tab opened by a page inherits that page's engine; other new tabs use the default engine; the user can switch a tab's engine at any time. Cookies are shared by copying between the engines' stores of one Persona, which adds and updates cookies; a cookie deleted in one engine stays in the other until it expires or the site replaces it, and site storage such as local storage stays per engine. Clear Site Data is the exception: it removes the site's cookies from both stores together while the copies wait.
- Use private APIs only behind flags on `flags://`: one for all private APIs, one for each API, and one for each feature that uses one. Check each API's availability quietly at launch and again just before use. If a feature's API is missing or switched off, the feature falls back to public behavior or stays hidden. You may fork CEF or WebKit when a feature needs it.
- Features use macOS facilities by default on both engines so Arch behaves like other Mac apps. For example, Chromium's picture in picture will use AVKit (VI.2) rather than Chromium's own window.
- Out of scope: a browser-side password manager; page translation, unless an engine offers it to embedding apps; and features specific to one browser rather than common to browsers, such as per-site CSS and JavaScript and notes. App icon choice is not offered for now; whether to add sound effects is undecided.
- A Persona owns its spaces and keeps cookies, sessions, site storage, and installed plugins separate. Favorites stay alive across spaces within their Persona. The default Persona keeps each engine's default storage (WebKit's default data store and CEF's global request context), so the upgrade to Personas moved no site data and signed nobody out; every other Persona has storage of its own named by its UUID. Cookies copy between the engines only within a Persona. A tab or space never moves to another Persona, because its pages would lose their storage. A deleted Persona's stored data goes at the next launch, before any engine starts, because an engine cannot remove a profile it has loaded, and only for the IDs that `session.json` lists in `removedPersonaIDs`, never because a Persona is missing.
- Every piece of state has exactly one owner. State that can differ between two windows open at once, such as what a window shows, focuses, or edits, belongs to that window's `BrowserWindowModel`. State bound to one Persona's engine storage (its contexts, browsers, cookie copying, and plugin manager, and later its extension controller) belongs to its `PersonaEngines`, from first use until quit. The engine applications, CEF initialization, crash totals, and the primary engine belong to the session's engine section. Everything else the user owns (Personas, spaces, favorites, tabs, the closed list, downloads and the pages kept open for them, each stored with the runtime that created it, permissions, zoom, and persistence) belongs to `BrowserSession`.
- At most one window shows a tab, because an engine's view has one superview. A window shows its selected tab and, in a split view, those of that tab's other panes that no other window shows. Explicit selection moves a tab: a sidebar click, a palette tab row, the tab switcher, ⌘-numbers, Next and Previous Tab, a favorite's tab, a tab's own request, and selection by sync or a plugin. The window that shows the tab first gives it up, selecting its fallback when the tab is its selected tab or leaving the pane otherwise, and only then does the selecting window run its own side effects, so the window losing the tab lets go of its docked developer tools before the other docks them. Automatic selection never takes a tab that another window shows: switching spaces, the fallback after a tab closes, restore, a new window, and the losing window's fallback. With no free tab, the window shows the empty page.
- Arch has its own plugin system with more capabilities than browser extensions. It includes built-in plugins for later features. WebKit extensions and Chromium-format extensions run as one kind of plugin; password managers such as 1Password come as plugins.
- Chromium DevTools attach beside the page as a child window of the browser window. Docking inside the window needs a CEF patch (VI.3). WebKit's Web Inspector opens inside the page through the private `_inspector` object behind private API flags. With them off, `isInspectable` still lets the browser bundled with macOS inspect WebKit tabs.
- AI features use providers the user connects through an API key or a command-line tool signed in through the built-in terminal. The user chooses providers per feature. Arch ships no model or provider account. All AI features, hooks, and features that AI adds at run time use one AI interface, designed in `docs/ai.md`.
- Now Playing and the media keys belong to the app on both engines. Chromium's own media controls stay off because they would use the same process-wide centers. WebKit's GPU process registers its own Now Playing client for the app. No public API turns it off, so a WebKit tab can also appear through it.
- Arch remembers permission answers without asking whether to, because a one-time choice could not hold on Chromium. Chromium's own prompt keeps every Allow and Don't Allow in the profile, and CEF's prompt callback has no one-time answer. Settings ▸ Websites changes and removes answers, and the session copies each change into Chromium's content settings. Screen recording is never remembered.
