# Arch Browser Development Plan

This plan gives the context needed to continue work in another session, on another Mac, or with a less capable model. Progress lives only here and in `docs/features.md`; there is no external context store.

## Goals

- Build a sidebar-first macOS browser with its own implementation. `docs/features.md` lists every planned feature and its status.
- Run no servers of our own. Use alternatives such as iCloud for features that need servers, including sync (`docs/features.md`, sections 5 and 7).
- Give both engines the same experience. Context menus, dialogs, sheets, find, downloads, extensions, and tools use the app's own interface and work alike whatever a tab's engine; only engine-drawn surfaces such as popups may differ. `docs/features.md` notes any feature an engine cannot support and why.
- Keep features lightweight. Delegate autofill to Apple Passwords or 1Password. On both engines, use macOS system frameworks for every feature that is part of the platform user experience. Follow the Platform integration table in `docs/features.md`.
- Exclude all AI features. This implementation contains no AI code or extension point for AI.
- Use ARCH prefixes throughout: `ARCH*` for packages, `Arch` for the app module, and `ARCHKit` for the core layer.
- The browser is for internal use. No distribution is planned. Manage replacement names, images, fonts, and similar items outside this repository.

## Approach

- Write new code for each feature. Start from a row in `docs/features.md`. Design the smallest module that delivers the feature and add it to `Package.swift`.
- Design type names, module boundaries, method signatures, and file layout for Arch. A row in `docs/features.md` describes what a feature does, not how to build it.
- Add engine protocol members only when a feature needs them. The current protocols are a starting point, not a list of requirements to implement.
- AI is out of scope. For features that combine AI and non-AI capabilities, keep only the non-AI part.
- The sidebar holds navigation, the address field, favorites, and tabs grouped by space. The window background shows the current space's tint. Nothing sits above the page. Only the code is written anew.
- Use the system framework whenever macOS provides the user experience. Do not build or retain an engine-specific version. Keep Chromium's existing native integrations. Route the remaining engine events to these frameworks and disable the engine's equivalent user interface.

Tabs open, close, pin, reorder, switch, and reopen; unpinned tabs not activated for a configurable number of hours are archived to the closed list (100 entries) by a timer and at restore. Several spaces with a tint each. Favorites are shared by all spaces and reuse an open tab for the same host. The command palette (⌘L edits the current address, ⌘T opens a new tab) accepts URLs and search queries, lists matching open tabs, and lists history suggestions. A sidebar control slides it in from the sidebar's side in 0.32 seconds and a shortcut raises it from below in 0.16 seconds; it animates its own arrival so that its contents move with it. The find bar floats over the page (⌘F, ⌘G, ⌘⇧G, Escape). The library button (⌘⇧J) pushes the favorites and space pages aside for the library: downloads at the top, then Reopen Closed Tab and Settings. While files download, the button shows a download symbol over their combined progress, and afterwards a badge counts the downloads that finished while the library was closed. CEF stops a download when the page that started it closes, so a Chromium page whose tab closes or switches engines while one of its downloads is in progress, paused, or interrupted stays open on a blank page, without the tab, until its own downloads no longer need it. A Chromium page that closes itself with `window.close()` cannot be kept, so its unfinished downloads are reported as cancelled. A paused WebKit download, or a failed one that left resume data, resumes through its own web view, or through a hidden web view in the same data store once the tab has closed; files save to the downloads folder with an unused name, or through a save panel when the profile asks for a location. Popups become tabs; `window.close()` closes the tab. A page whose process quits and does not come back (WebKit at once, Chromium after its one automatic reload) is covered by a notice with a Reload button; the session is the engines' application delegate and keeps their crash count for the tab close log. A tab that opens straight onto a file closes once the file's download starts, without a closed-list entry or a history visit, and a restored tab like that does not download the file again. Spaces, favorites, tabs, the closed list, and the selection persist in `session.json`; quitting keeps the open tabs because the bridge does not report the browsers that close when the runtime shuts down. A sheet asks before a site gets a permission such as the camera; the system's own camera and microphone prompt follows. Permission and page dialog sheets wait in a queue per tab and show one at a time, only while their tab is selected; closing a tab gives its waiting sheets the safe answer. JavaScript `alert`, `confirm`, and `prompt` show sheets titled with the page's host on both engines. When the user reloads, goes back or forward, or loads another address while a page dialog is open, the dialog gets its safe answer and closes, and the page cannot open another until that load ends; Back or Forward without an entry leaves the dialog open. Such a cancellation ends only the page's own dialogs: a permission, sign-in, leave-page, or other-app question stays. A sheet put away because another tab became selected, as when a link from another app opens a tab, shows again when its tab returns. Closing a tab on the Chromium engine asks with a leave-page sheet when the page's `beforeunload` handler wants to stay, unless one of its downloads is in progress, paused, or interrupted, when the tab closes at once; WebKit has no public `beforeunload` callback, so its tabs close at once. Quitting gives every open and waiting sheet its safe answer, so no sheet holds the app open. When a site or proxy asks for HTTP authentication, a sheet asks for a user name and password on both engines. It names the site's realm, says when the last attempt failed, warns when the connection is unencrypted, and keeps the credential in memory for the session only. A link with a scheme neither engine loads, such as `mailto:`, does not navigate the page and opens no tab: when macOS has an app for it, a sheet with that app's name and icon asks before the link opens there. A tab asks one such question at a time. After the user chooses Cancel, the site (its host, or its scheme for a page without one) asks no more on its own until the tab moves to another site; a link the user clicks or an address the user types still asks. Right-clicking a page shows the same menu on both engines, built by the tab: up to five spelling suggestions or No Guesses Found, then Open Link in New Tab (web links only, as a background tab in the page's space and engine) and Copy Link, Open Image in New Tab and Copy Image Address, then Cut, Copy, Paste, and Select All in a field, or Copy for a selection that is not on a link, image, or media; Back, Forward, and Reload show only when none of those apply. |

## Working Rules

1. Write new code for each feature, with interfaces, names, and layout designed for Arch.
2. Maintain `Package.swift` by hand. Add one target per new module.
3. Exclude all AI features. Do not add AI code or extension points for AI.
4. Write documentation, comments, and commit messages in English.
5. Document the current state only. Do not include a change history. When a queue task finishes, remove its row and fold the result into Current State and `docs/features.md` in the same commit.
6. Stage by path (`git add <paths>`) and keep one purpose per commit. Queue tasks use the `Task(<ID>):` subject; other work uses the prefixes in `.githooks/commit-msg`.
7. Work on `main`. Branches named `cloud/…` or `sync/…` move work between machines; delete them after use.
8. Never record the code-signing identity, its team identifier, or a signed bundle in the repository, the documents, or a report. `build/` stays ignored.
9. Before the final `Docs:` commit of a batch, run a prose pass over the comments and documents the batch added with the `prose-writing` skills (Codex without a model flag; confirm the model and reasoning level in its startup output), then review the result.
10. Report a check as passed only after running it.

## Build Procedure

```bash
./scripts/setup_cef.sh      # once per checkout
swift build
./scripts/bundle_app.sh     # writes build/Arch.app
open build/Arch.app
```

- `ARCH_SIGN_IDENTITY` overrides the signing identity; `ARCH_START_URL` opens a page at launch; `ARCH_CEF_FRAMEWORK_PATH` and `ARCH_CEF_HELPER_PATH` let a bare `.build/debug/Arch` find CEF.
- State lives in `~/Library/Application Support/Arch`: `session.json`, `history.sqlite`, and `Cache/Chromium`. Delete the folder for a first-launch test. `defaults delete local.arch.browser ARCHAskedDefaultBrowser` brings the default-browser prompt back.
- For a scripted check, run `build/Arch.app/Contents/MacOS/Arch 2> /tmp/arch.log &`, then inspect `session.json`, `sqlite3 … history.sqlite 'select * from visits'`, and the log. `open -a build/Arch.app https://example.org` sends a link to the running app. `pkill -9 -f "Arch.app/Contents/Frameworks/Arch Helper.app/Contents/MacOS/Arch Helper --type=renderer"` crashes every page's renderer; a bare `type=renderer` pattern would also kill other Chromium-based apps' renderers.
- Launch through `open` or the Finder for any check that involves a system permission prompt. A binary started from a shell is attributed to the shell's parent, so the camera prompt never appears and the page reports a denied request.

Regression checklist, run from the bundle on the Chromium engine with a fresh Application Support folder:

1. ⌘F opens the find bar focused; typing shows "n of m"; Return and ⇧Return move through matches; Escape closes the bar and the page keeps keyboard focus; switching tabs closes it.
2. ⌘⇧J and the library button toggle the library; a file download shows its progress on the button and appears in the library; pause, resume, and cancel change the row; a download that finishes with the library closed adds to the button's badge until the library opens; Clear removes finished rows. The save panel path (`promptForDownloadPath`) has no setting yet; V.8 adds one.
3. After visiting three pages, ⌘L lists them under the typed text; choosing one navigates; a reload does not raise its visit count.
4. `open -a build/Arch.app https://example.org` opens a tab in the running app and at launch.
5. The first launch asks to set the default browser; Set as Default shows the system confirmation; afterwards the menu item is disabled.
6. A page requesting the camera gets Arch's sheet, then the system prompt; Allow reaches the page, Don't Allow reports a denied request.
7. Killing the renderer helper reloads the page once; a second crash on the same page shows the notice with Reload, Reload brings the page back, and the app keeps running.

## Work Queue

### How to use the queue

Each task carries the reasoning it needs, so that work can be split across models by capability:

- `high`: a design choice, a change to the Objective-C++ bridge or the engine protocols, a change to the `session.json` schema, window architecture, or threading. Use the most capable model available.
- `medium`: a view or session method inside an existing module that follows an existing pattern (for example `DownloadsView` or `togglePinned`). A mid-tier model can take it with the files and the done condition below.
- `low`: a mechanical edit, a document update, or a verification by checklist. Any model.

Rules for every tier:

1. Take tasks at or below your tier. Read the files the task names before editing, and keep to them. If the task needs a file, a protocol member, or a decision it does not list, stop, write the blocker into the task row (`blocked: …`), and leave the code unchanged.
2. Respect the order within a phase and the dependencies in the task text. Phases I and II run before III to V; VI is independent.
3. One task per commit with the `Task(<ID>):` subject, staged by path. Run `swift build` for every code change and `scripts/bundle_app.sh` plus a launch when the task says "from the bundle".
4. Finish by updating this file (remove the row, update Current State) and the feature row in `docs/features.md` in the same commit, then go through the After each task list in `AGENTS.md`.
5. Verification steps use a fresh Application Support folder unless the step says otherwise.

## Decisions

- History visits: one visit per page change per tab. A reload, a repeated load of the same URL in the same tab, and the initial load of a restored tab do not add visits. The palette ranks by visit count, so pages that reload often would otherwise crowd out typed destinations. A hash change counts as a visit because its address is one the user may revisit.
- Permissions and dialogs default to the safe answer in the protocol: deny and dismiss. Feature code shows the user interface.
- Downloads save to the downloads folder with an unused name; a save panel appears only when the profile asks for a location.
- The page context menu holds only items both engines can run. Look Up, Share, Services, Learn and Ignore Spelling, saving or copying an image, media controls, and Undo stay out on both; they can come back as app features that work on both engines.
- AppKit does not quit while a window shows a sheet with more than one button, so quitting first answers every sheet, and CEF shuts down only at `NSApplicationWillTerminateNotification`, once the quit is certain. A page dialog stops its page, so a navigation the user starts answers the dialog first on both engines; CEF resets its dialog state as soon as that navigation starts, so the end of loading, not the reset, ends the suppression of new dialogs.
- Calling a DevTools protocol method on a Chromium tab attaches a client that stays until the browser closes. While one is attached, Chromium ignores an unresponsive renderer, so the `beforeunload` and unload timeouts stop and a hung page with a `beforeunload` handler can no longer be closed. Features use the protocol only when CEF has no other route. The History menu therefore moves through the page's `history.go`, after stopping a main frame navigation still under way, because Chromium ignores a page's history request during one. A hung or crashed page, a page that cannot run scripts (such as one served with a CSP sandbox), or one that replaces `History.prototype.go` ignores the menu, while Back and Forward still work.
- Clear History empties the visit store only. Neither engine lets the app remove entries from a tab's back-forward list, so open tabs keep their earlier pages in Back, Forward, and the History menu until they close.
- The History menu and Back show each engine's own back-forward list. WebKit folds script navigations that run without a user gesture into one entry, so a WebKit tab can list fewer pages than a Chromium tab on the same site.
- Engine choice is per tab. A tab opened by a page inherits that page's engine; other new tabs use the default engine; the user can switch a tab's engine at any time. Cookies are shared by copying between the engines' stores, which adds and updates cookies; a cookie deleted in one engine stays in the other until it expires or the site replaces it, and site storage such as local storage stays per engine.
