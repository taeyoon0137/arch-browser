# Engine protocol design

## Purpose and principles

- Protocols in `ARCHEngine` separate the Swift layer from the web engine. `ARCHEngineChromium` is the primary engine. It uses Chromium through the Chromium Embedded Framework (CEF). The `WKWebView` adapter serves as the secondary engine and the debug engine. The selection model allows each profile or tab to use a different engine.
- Adapters call every delegate method, completion handler, and change closure of these protocols on the main thread; feature code also calls the protocols there. CEF's UI thread is the main thread, and the bridge forwards reports from CEF's other threads to it.
- Feature code depends only on these protocols. It never depends directly on an engine framework. Add protocol members only when a feature needs them. Treat the current set as a starting point, not a checklist to complete. `docs/features.md` lists the features the protocols serve.
- Keep features lightweight. Delegate password, card, and address autofill to Apple Passwords (iCloud Keychain and passkeys) or a third-party provider such as 1Password. Both adapters route engine events to the system framework wherever macOS provides the user experience. The Chromium engine disables its own equivalent UI for these features. See the Platform integration table in `docs/features.md`. Prefer Apple APIs for picture-in-picture (PiP), CSS and JavaScript injection, and translation. These include WebKit's built-in PiP, `WKUserScript`, `WKUserContentController`, and the Translation framework.

## Web extensions

`EngineExtensions` represents an engine's web extensions in one browser context. It follows the app's interactions with extensions, so every engine that runs them answers the same calls:

- The app passes an extension as `EngineExtension`: its identifier, which the extension reads as `runtime.id`, its package folder, the API permissions and match patterns the user granted, and when the package was installed. `check(_:)` reads a package folder as `load` would without starting it and throws with the reason the engine cannot run it. `load` replaces a loaded extension with the same identifier and starts its background and content scripts; `unload` stops it and keeps its storage; `removeData(of:)` deletes its storage. The app calls `stopUnloadedExtensions()` after each pass of loads, and as a profile starts while it loads no extension there, since no pass reaches the profile then. From the first call on, an engine that keeps extensions between launches can stop those the app has not loaded in the run, without stopping and restarting any the app is about to load.
- `action(of:for:)` reads an extension's action for a tab (label, icon, badge, whether it is enabled, and whether the engine kept the extension from the tab's site), `performAction(of:for:)` runs it as a click does, and `grantSiteAccess(of:for:)` allows the extension on the tab's site. An engine answers only for its own web contents.
- `setWindows(_:focusedWindowID:)` reports the app's windows (`EngineExtensionWindow`: an identity, tabs of any engine in order, the active tab, and the AppKit window that shows it) each time they change. The engine answers extensions' questions about windows and tabs from the latest report and tells them what opened, closed, moved to another window, and became active since the previous report. A window closes after the tabs that left it for another window have moved. A window is omitted if an earlier window in the report has its identity, as a session file can list two spaces with one identifier.
- `EngineExtensionsDelegate` is the app: it opens tabs (`openTabWith`: an address or the new tab page, a window as `setWindows` reported it, whether active, and an index among that window's tabs of the engine) and windows (`openWindowWith`: addresses and focus, a new window that lists only the tabs it opened), each completing once the app has reported it. It activates and closes tabs, learns when an action changes, shows an action's popup (`EngineExtensionPopup`: a popover that the engine filled, on WebKit `WKWebExtensionAction.popupPopover`, which sizes itself and closes with the popup, or a popup page's view, `EngineExtensionPopupView`, with its preferred size and its size and close reports, which the app shows in a popover of its own), asks the user about access requested at run time (`EngineExtensionAccess`: a permission, a site pattern, or a page) and the engine's own questions (`EngineExtensionPrompt`: more access in the engine's sentences or a reload of a tab; the Chromium adapter refuses a store install's question without asking the delegate), and passes native messages and ports (`EngineNativeMessagingPort`) as JSON.
- WebKit: `check(_:)` reads the package with `WKWebExtension(resourceBaseURL:)`, which throws only when it cannot read a manifest. Other problems stay in its `errors` and do not count as a refusal. The controller's configuration follows the context's store (non-persistent, default, or with the store's identifier), and its default data store is the context's. Each web contents is a `WKWebExtensionTab` through an object it keeps for its lifetime. Each reported window is a `WKWebExtensionWindow` object kept for the window's lifetime. Content scripts run only in pages of a persistent store, since WebKit treats the web views of a non-persistent store as private. `removeStoredData(forStorage:)` also deletes the extension data records of the identifier. Extensions' requests for tabs, options pages among them, and windows reach the delegate through the controller delegate, which follows only a window's addresses and focus. WebKit loads an extension's page only in a web view made from the extension context's `webViewConfiguration`, and no other page there, so a web contents that starts at a loaded extension's page uses it, and a web page that such a page opens in a new window gets a web contents of its own. A web contents keeps its web view, so the navigation policy cancels a main frame navigation across that line and hands the UI delegate a replacement that loads it (`webContents(_:didCreateReplacement:)`), whose tab replaces the old one for the extensions (`didReplaceTab(_:with:)`) once `setWindows` lists it in the old one's place. A web contents at a page of an extension that has not loaded waits for it and then hands over a replacement (`docs/plan.md`, Decisions). `stopUnloadedExtensions()` does nothing, since the controller runs only the contexts the app loaded in the run.
- Chromium: each profile's own Chromium extension system loads a package unpacked (`CefExtensionRuntime::LoadUnpacked`), so the app's identifier must come from the manifest's `key`, which the app writes into an installed copy without one. `check(_:)` reads the package's files for problems that prevent Chromium's loader from running it, since CEF's runtime has no call that reads a package without installing it. `load` switches the extension on and sets its host permissions to every site its manifest asks for when the grant has them all, comparing schemes and hosts in lowercase and leaving out the patterns for `file:` and `ftp:` pages, which no extension reaches on Arch's engine. Otherwise, as also for a pattern with a port or one for another scheme, such as `wss:`, which no grant holds, it passes the grant's sites with the click setting (`CefExtensionRuntime::SetSiteAccess`): Chromium grants the manifest's sites that they cover as runtime host permissions that the profile keeps, replacing those of the previous load, and withholds the others until a click or `grantSiteAccess(of:for:)`, which grants the origin of the tab's page next to them. A `wss:` pattern is never covered, and a pattern with a port only where a granted pattern covers its host, since match patterns cover every port of their host. `unload` switches it off, `removeData(of:)` uninstalls it, and from the first `stopUnloadedExtensions()` on, the adapter switches off every extension that Chromium starts with the profile but the app has not loaded in the run. A first load in the run keeps the copy Chromium started with only if the package was installed before the engine started. Arch's engine loads the runtime's packages without file access, also when Chromium reloads them or keeps them from an earlier launch, so an extension runs on no `file:` page, even with host permissions that apply on every site, and `tabs.create` and `tabs.update` refuse `file:` addresses. Each reported window is a client window (`CefExtensionWindow`) over a hidden stand-in `NSWindow`, because CEF reads a client window's frame and state from an AppKit window it keeps for life; the stand-in answers with the frame and state of the window that shows it. A request for a window is answered once the client window lists every tab the app gave it. The bridge's default client logs and closes the browsers of Chromium's own windows, as `identity.launchWebAuthFlow` opens. Actions come from `CefExtensionRuntime::GetActions`, which gives an extension without an action in its manifest the disabled action Chromium makes for it, so that its site access shows, a popup page from `CefExtensionRuntimeHandler::OnShowPopup` as a view, and tab, window, and prompt requests from the handler. `extensionRuntimeVersion` is the CEF version.

## Excluded from the protocols

- Autofill: saving or filling passwords, cards, and addresses. Apple Passwords and 1Password handle them; the extent of system password autofill in `WKWebView` needs verification.
- AI: models and ranking. `readableContent` reads page text for any feature and contains no AI code.
- Instrumentation: metrics, tracing, and crash reporting.
- Encryption keys for sync: sync uses CloudKit (`docs/plan.md`, V.9).

Chromium-specific UI callbacks, including translation bubbles, extension installation consent, and Web UI dialogs, remain outside the protocols.

## Engine switching

- `EngineKind` identifies `webKit` and `chromium`. `EngineRegistry` holds registered engines. `UserDefaults` stores the default engine under `ARCHDefaultEngine`.
- A web contents belongs to the engine of the browser that creates it. `BrowserSession` runs one application per engine and, for each Persona, one profile and browser per engine, so tabs of both engines share a session: new tabs use the default engine (`EngineRegistry.defaultKind`) and tabs a page opens use that page's engine and Persona. The address pill's site settings switch a tab's engine by loading its page in a web contents from the other engine's profile of the same Persona; each Persona's `CookieSync` in `Browsing` copies cookies between its two profiles through `allCookies`, `setCookies`, `removeCookies(where:)`, and `cookiesDidChange`. A copy carries the cookies the source added, changed, or deleted since the two stores last agreed, a record it keeps across launches in `CookieSync/<persona id>.json` without cookie values, and leaves a cookie that only the target changed. A copy keeps each cookie's `SameSite` policy as far as the target store can hold it (Tier 2, Cookies): a cookie without a policy in WebKit reaches Chromium as `SameSite=None` when it is secure. A copy writes only the cookies the target lacks or holds with another value, flag, or expiry (`EngineCookie.hasSameContents(as:)`), keyed by name, domain, and path, so a cookie that comes back unchanged keeps the target's policy: a Chromium cookie without a policy, which WebKit reads as `SameSite=None`, stays without one in Chromium.
- Each engine keeps profile data in its own directory, and each Persona other than the default one has storage of its own in each engine, named by the Persona's UUID. Cookies are shared by copying between the engines' stores of one Persona (`CookieSync`); other site data stays per engine. Sidebar and tab models belong to the feature modules. These models are independent of the engine.

## Current state and next steps

Both adapters build and run in the app, and each implements every protocol member. Every member has a caller in feature code or is a report that an adapter makes, except `executeJavaScript(_:inWorld:completion:)` and `postPageScriptMessage(_:toWorld:)`, which the page members of the plugins' context will call (V.11), and which the agents' page scripts will also call (`docs/agents.md`); a member that no feature uses goes, and comes back with the feature that needs it. The agents design adds no member in its first build; its navigation checks make the Chromium adapter ask the navigation delegate about every main frame navigation and redirect (VII.12). It plans two optional members, each with its own task: trusted input (`EngineWebContents.input`, VII.21) and a page file chooser report on the UI delegate (VII.22), plus isolated script worlds on Chromium in Arch's engine (VI.6). `docs/plan.md` Current State lists what each adapter implements and what it does not. Its Work Queue lists engine gaps in Phase II and changes requiring a CEF source build in Phase VI.

These adapter rules supplement the member signatures:

- The app's profiles all keep their data. The WebKit adapter's tests make a profile over `WKWebsiteDataStore.nonPersistent()`, which keeps nothing on disk, through the adapter's internal `makeBrowserContext(storageIdentifier:dataStore:)`; its web extensions then keep nothing either.
- `go(to:)` loads an earlier or later page from the same controller's back-forward list. It ignores the current page and items from another tab's list, so an item kept after its menu closes cannot load a different page.
- The Chromium adapter calls the DevTools protocol only when CEF has no other route. An attached DevTools client stays until the browser closes and prevents Chromium from timing out a hung page (`docs/plan.md`, Decisions).
- `removeSiteData(for:)` removes WebKit's data records for each origin's site (registrable domain), the unit those records use. On Chromium, it calls `Storage.clearDataForOrigin` for each origin in a hidden browser that then closes, so no tab keeps a DevTools client. It leaves cookies to `removeCookies(where:)`, which the session runs on both engines together.
- Both adapters report media through a script in each document and share `ScriptMediaSession`, which shows the playing document, otherwise the one that reported last.
- Page scripts run in each new document, from the first one on or, after `setPageScripts`, from the next. Each `EnginePageScript` is a function expression that the engine calls with its world's channel: `channel.send(value)` passes the value as JSON to `pageScriptDelegate` and returns a promise of the reply, and `channel.onMessage(listener)` receives what `postPageScriptMessage(_:toWorld:)` delivers to the main frame. Both adapters hand the delegate an `EnginePageScriptReply`, so a reply the delegate drops counts as nil. WebKit gives each world a `WKContentWorld` of its own with a `WKScriptMessageHandlerWithReply` added only to that world. It removes user scripts only all at once, so `setPageScripts` adds the content controller's other scripts again. A WebKit popup uses its opener's content controller and so shares its page scripts. Chromium runs every world in the page's main world. The bridge passes the scripts to the renderer in the browser's extra info, in a process message to each frame when they change, and to each frame created after a change. CEF does not order that message before the frame's first document, so in a renderer process that had none of the browser's frames, such as after a cross-site navigation, the first document may still run the scripts the browser was created with (needs verification). The helper's `OnContextCreated` makes the document's channel opener before the page's scripts run, so every channel, also one that `executeJavaScript(_:inWorld:completion:)` opens later, calls the built-ins as they were then. It opens each world's channel with a native function that it passes to the channel script as an argument, so the function never reaches `window`, and runs the scripts before the page's own; document-end scripts wait for `DOMContentLoaded`. The page can still see the values a Chromium page script sends and receives through the built-ins it replaces, such as a `then` getter on `Object.prototype`, which a promise reads when it settles with an object reply. A Chromium popup's renderers start with its opener's scripts, which the bridge passes in the popup's extra info. `executeJavaScript(_:inWorld:completion:)` uses the same process message as `readableContent` on Chromium.
- A popup keeps its opener on both engines, so the page reaches it through the window `window.open` returns and it reaches the page through `window.opener`. Each adapter reports it through `webContents(_:didCreateNewWebContents:targetURL:disposition:)`. WebKit's `createWebViewWith` returns a web view made from the configuration WebKit hands over and reports `newForegroundTab`. Chromium's `OnBeforePopup` hands CEF a browser object of the bridge's own, with its own client and container view, and CEF creates the popup in the opener's browsing context and request context; once `OnAfterCreated` reports it, the adapter wraps it in a `ChromiumWebContents` and reports Chromium's disposition. On both engines, a page opens a popup only while its web contents has a UI delegate. A Chromium popup that the UI delegate drops closes on the next turn of the run loop, once CEF owns its page, one that CEF cannot create never reaches the delegate, and a Document Picture-in-Picture window opens none. On both engines, a popup for another app goes to `openExternally`, and a Shift-clicked link that the navigation delegate cancels opens no popup. The Chromium adapter reports `webContentsDidRequestActivation` only for the return button of its picture-in-picture window, and the WebKit adapter not at all: CEF's Alloy style ignores Chromium's `ActivateContents`, which `focus()` on a popup and `window.open` with its name reach, and `WKUIDelegate` has no such callback.
- `readableContent(limit:completion:)` runs `EngineReadableContent.script` in the main frame: WebKit in its own `WKContentWorld`, Chromium in the page's world through a process message to the helper's renderer, because `ExecuteJavaScript` returns no value and the DevTools protocol would attach a debugger.
- A link the user clicks with Shift and without Command reaches `EngineWebContentsNavigationDelegate` as a user-initiated `newWindow` action on both engines. WebKit reads the click's modifier flags in `decidePolicyFor`, and a link marked for download is not one; Chromium gives such a link the new window disposition and asks from `OnOpenURLFromTab` and `OnBeforePopup`. The WebKit adapter asks the navigation delegate about every navigation, the Chromium adapter about these links only. When the delegate cancels, the link neither loads nor opens a popup.
- Both adapters load a page's icon through `FaviconLoader`, outside the engine and every profile's store, without cookies or stored credentials. They keep no cookies set by the response. An icon request therefore never carries one Persona's sign-in to a site for another Persona's tab, and an icon that a site shows only to signed-in users does not load, so the tab shows none. A page names its icon's URL, so only web and data URLs load, and a `file` URL reads nothing from the Mac. A body past 1 MB, also one whose length the response does not state, and a download not finished after 30 seconds load no icon, so a page cannot make the app buffer an endless response.
