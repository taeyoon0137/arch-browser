# Engine protocol design

## Purpose and principles

- Protocols in `ARCHEngine` separate the Swift layer from the web engine. `ARCHEngineChromium` is the primary engine. It uses Chromium through the Chromium Embedded Framework (CEF). The `WKWebView` adapter serves as the secondary engine and the debug engine. The selection model allows each profile or tab to use a different engine.
- Adapters call every delegate method, completion handler, and change closure of these protocols on the main thread, and feature code calls the protocols there. CEF's UI thread is the main thread, and the bridge hands what CEF reports on its other threads to the main thread.
- Feature code depends only on these protocols. It never depends directly on an engine framework. Add protocol members only when a feature needs them. Treat the current set as a starting point, not a checklist to complete. `docs/features.md` lists the features the protocols serve.
- Keep features lightweight. Delegate password, card, and address autofill to Apple Passwords (iCloud Keychain and passkeys) or a third-party provider such as 1Password. Both adapters route engine events to the system framework wherever macOS provides the user experience. The Chromium engine disables its own equivalent UI for these features. See the Platform integration table in `docs/features.md`. Prefer Apple APIs for picture-in-picture (PiP), CSS and JavaScript injection, and translation. These include WebKit's built-in PiP, `WKUserScript`, `WKUserContentController`, and the Translation framework.

## Tier 2: optional engine capabilities

`Engine.capabilities` lists the capabilities below that an engine's adapter implements; an entry marked Planned or None is not in its list. Feature code reads the list where it must know before an engine starts, as the session does before it starts an engine for web extensions, and tests optional members such as `devTools` directly.

| Capability | Chromium | WebKit |
|---|---|---|
| `extensions` (Manifest V3 extensions) | Planned (VI.1) | From macOS 15.4, `EngineBrowserContext.extensions` with one `WKWebExtensionController` per context, which every web view of the context uses. See Web extensions below |
| `devTools` | CEF's developer tools in a window the adapter reports through `EngineDevTools.window`. The app places it beside the page. A panel cannot be chosen | WebKit's Web Inspector through the private `_inspector` object behind private API flags. It attaches inside the page view, so `window` is nil and `isPlacedByApp` is false. Without the flags, none; the adapter sets `isInspectable` |
| `pdfController` | Planned | Built-in PDF support |
| `pictureInPicture` | Planned (VI.2): system PiP through AVKit using decoded video frames. Requires a patched CEF source build (needs verification) | System PiP through WebKit (AVKit). Users enter PiP from video controls. `closeAllMediaPresentations` exits PiP. No custom code |
| `sessionRestore` (a page's back-forward list from `restorableState`) | None: CEF cannot fill a back-forward list, so a restored tab loads only its last address | `interactionState` |

## Web extensions

`EngineExtensions`, an engine's web extensions in one browser context, is shaped by what the app does around an extension, so that each engine that runs them answers the same calls:

- The app hands an extension over as `EngineExtension`: its identifier, which the extension reads as `runtime.id`, its package folder, and the API permissions and match patterns the user granted. `load` replaces a loaded extension with the same identifier and starts its background and content scripts; `unload` stops it and keeps its storage; `removeData(of:)` deletes its storage.
- `action(of:for:)` reads an extension's action for a tab (label, icon, badge, whether it is enabled), and `performAction(of:for:)` runs it as a click does. An engine answers only for its own web contents.
- `setWindows(_:focusedWindowID:)` reports the app's windows (`EngineExtensionWindow`: an identity, tabs of any engine in order, the active tab, and the AppKit window that shows it) each time they change. The engine answers extensions' questions about windows and tabs from the last report and tells them what opened, closed, moved to another window, and became active since the report before. A window whose identity an earlier window in the report has is left out, as a session file can list two spaces with one identifier.
- `EngineExtensionsDelegate` is the app: it activates and closes tabs, learns that an action changed, shows the popover with an action's popup (on WebKit, `WKWebExtensionAction.popupPopover`, which sizes itself and closes with the popup), asks the user about access requested at run time (`EngineExtensionAccess`: a permission, a site pattern, or a page), and passes native messages and ports (`EngineNativeMessagingPort`) as JSON.
- WebKit: the controller's configuration follows the context's store (non-persistent, default, or with the store's identifier), and its default data store is the context's. Each web contents is a `WKWebExtensionTab` through an object it keeps for its lifetime, each reported window a `WKWebExtensionWindow` object kept while the window stays. Content scripts run only in pages of a persistent store, since WebKit treats the web views of a non-persistent store as private. `removeStoredData(forStorage:)` also deletes the extension data records of the identifier.

## Excluded from the protocols

- Autofill: saving or filling passwords, cards, and addresses. Apple Passwords and 1Password handle them; the extent of system password autofill in `WKWebView` needs verification.
- AI: models and ranking. `readableContent` reads page text for any feature and contains no AI code.
- Instrumentation: metrics, tracing, and crash reporting.
- Encryption keys for sync: sync uses CloudKit (`docs/plan.md`, V.9).

Chromium-specific UI callbacks, including translation bubbles, extension installation consent, and Web UI dialogs, remain outside the protocols.

## Engine switching

- `EngineKind` identifies `webKit` and `chromium`. `EngineRegistry` holds registered engines. `UserDefaults` stores the default engine under `ARCHDefaultEngine`.
- A web contents belongs to the engine of the browser that creates it. `BrowserSession` runs one application per engine and, for each Persona, one profile and browser per engine, so tabs of both engines share a session: new tabs use the default engine (`EngineRegistry.defaultKind`) and tabs a page opens use that page's engine and Persona. The address pill's site settings switch a tab's engine by loading its page in a web contents from the other engine's profile of the same Persona; each Persona's `CookieSync` in `Browsing` copies cookies between its two profiles through `allCookies`, `setCookies`, and `cookiesDidChange`. A copy keeps each cookie's `SameSite` policy as far as the target store can hold it (Tier 2, `cookies`): a cookie without a policy in WebKit reaches Chromium as `SameSite=None` when it is secure. A copy writes only the cookies the target lacks or holds with another value, flag, or expiry (`EngineCookie.hasSameContents(as:)`), so a cookie that comes back unchanged keeps the target's policy: a Chromium cookie without a policy, which WebKit reads as `SameSite=None`, stays without one in Chromium.
- Each engine keeps profile data in its own directory, and each Persona other than the default one has storage of its own in each engine, named by the Persona's UUID. Cookies are shared by copying between the engines' stores of one Persona (`CookieSync`); other site data stays per engine. Sidebar and tab models belong to the feature modules. These models are independent of the engine.

## Current state and next steps

Both adapters build and run in the app, and each implements every protocol member. `docs/plan.md` Current State lists what each adapter implements and what it does not. Its Work Queue lists engine gaps in Phase II, the members no feature uses yet (I.19), and changes requiring a CEF source build in Phase VI.

These adapter rules supplement the member signatures:

- `go(to:)` loads an earlier or later page from the same controller's back-forward list. It ignores the current page and items from another tab's list, so an item kept after its menu closes cannot load a different page.
- The Chromium adapter calls the DevTools protocol only when CEF has no other route. An attached DevTools client stays until the browser closes and prevents Chromium from timing out a hung page (`docs/plan.md`, Decisions).
- `removeSiteData(for:)` removes WebKit's data records for each origin's site (registrable domain), the unit those records use. On Chromium, it calls `Storage.clearDataForOrigin` for each origin in a hidden browser that then closes, so no tab keeps a DevTools client. It leaves cookies to `removeCookies(where:)`, which the session runs on both engines together.
- Both adapters report media through a script in each document and share `ScriptMediaSession`, which shows the playing document, otherwise the one that reported last.
- Page scripts run in each new document, from the first one on or, after `setPageScripts`, from the next. Each `EnginePageScript` is a function expression that the engine calls with its world's channel: `channel.send(value)` passes the value as JSON to `pageScriptDelegate` and returns a promise of the reply, and `channel.onMessage(listener)` receives what `postPageScriptMessage(_:toWorld:)` delivers to the main frame. Both adapters hand the delegate an `EnginePageScriptReply`, so a reply the delegate drops counts as nil. WebKit gives each world a `WKContentWorld` of its own with a `WKScriptMessageHandlerWithReply` added only to that world. It removes user scripts only all at once, so `setPageScripts` adds the content controller's other scripts again. A WebKit popup uses its opener's content controller and so shares its page scripts. Chromium runs every world in the page's main world. The bridge passes the scripts to the renderer in the browser's extra info, in a process message to each frame when they change, and to each frame created after a change. CEF does not order that message before the frame's first document, so in a renderer process that had none of the browser's frames, such as after a cross-site navigation, the first document may still run the scripts the browser was created with (needs verification). The helper's `OnContextCreated` makes the document's channel opener before the page's scripts run, so every channel, also one that `executeJavaScript(_:inWorld:completion:)` opens later, calls the built-ins as they were then. It opens each world's channel with a native function that it passes to the channel script as an argument, so the function never reaches `window`, and runs the scripts before the page's own; document-end scripts wait for `DOMContentLoaded`. The page can still see the values a Chromium page script sends and receives through the built-ins it replaces, such as a `then` getter on `Object.prototype`, which a promise reads when it settles with an object reply. A Chromium popup's renderers start with its opener's scripts, which the bridge passes in the popup's extra info. `executeJavaScript(_:inWorld:completion:)` uses the same process message as `readableContent` on Chromium.
- A popup keeps its opener on both engines, so the page reaches it through the window `window.open` returns and it reaches the page through `window.opener`. Each adapter reports it through `webContents(_:didCreateNewWebContents:targetURL:disposition:)`. WebKit's `createWebViewWith` returns a web view made from the configuration WebKit hands over and reports `newForegroundTab`. Chromium's `OnBeforePopup` hands CEF a browser object of the bridge's own, with its own client and container view, and CEF creates the popup in the opener's browsing context and request context; once `OnAfterCreated` reports it, the adapter wraps it in a `ChromiumWebContents` and reports Chromium's disposition. On both engines, a page opens a popup only while its web contents has a UI delegate. A Chromium popup that the UI delegate drops closes on the next turn of the run loop, once CEF owns its page, one that CEF cannot create never reaches the delegate, and a Document Picture-in-Picture window opens none. On both engines, a popup for another app goes to `openExternally`, and a Shift-clicked link that the navigation delegate cancels opens no popup. The protocols have no callback for a page that asks to bring its popup forward: CEF's Alloy style ignores Chromium's `ActivateContents`, which `focus()` on a popup and `window.open` with its name reach, and `WKUIDelegate` has no such callback.
- `readableContent(limit:completion:)` runs `EngineReadableContent.script` in the main frame: WebKit in its own `WKContentWorld`, Chromium in the page's world through a process message to the helper's renderer, because `ExecuteJavaScript` returns no value and the DevTools protocol would attach a debugger.
- A link the user clicks with Shift and without Command reaches `EngineWebContentsNavigationDelegate` as a user-initiated `newWindow` action on both engines. WebKit reads the click's modifier flags in `decidePolicyFor`, and a link marked for download is not one; Chromium gives such a link the new window disposition and asks from `OnOpenURLFromTab` and `OnBeforePopup`. The WebKit adapter asks the navigation delegate about every navigation, the Chromium adapter about these links only. When the delegate cancels, the link neither loads nor opens a popup.
- Both adapters load a page's icon through `FaviconLoader`, outside the engine and every profile's store, without cookies or stored credentials, and keep no cookie the response sets. An icon request therefore never carries one Persona's sign-in to a site for another Persona's tab, and an icon that a site shows only to signed-in users does not load, so the tab shows none.
